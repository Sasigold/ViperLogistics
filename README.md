# ViperLogistics — מערכת ניהול כוח אדם להשכרת ציוד לאירועים

מערכת Web מודרנית (Multi-Tenant) לניהול עובדים, נהגים, ראשי צוות, קבלנים ושיבוצים
עבור חברת השכרת ציוד לאירועים. עברית מלאה (RTL) + Dark Mode.

## סטאק

- **Frontend:** Vite + React 19 + TypeScript, Tailwind CSS v4, TanStack Query + Virtual,
  FullCalendar v6 (חינמי), Recharts, ExcelJS, Zustand
- **Backend:** Supabase — Postgres 17 עם RLS מלא, Auth, Edge Functions, Realtime
- **כתובות:** Nominatim (OSM) דרך Edge Function פרוקסי, עם שכבת Adapter הניתנת להחלפה ל-Google Places

### ייבוא אירועים ומשימות מאקסל

הקובץ הוא **שלושה גיליונות**: "אירועים", "משימות" ו"הסבר". גיליון המשימות מקושר
לאירועים דרך עמודת "מזהה שורה" — מזהה חופשי שחי רק בתוך הקובץ ואינו נשמר במסד;
זו הדרך לתאר כמה משימות לאירוע אחד בלי לכפול את שורת האירוע. גיליון "הסבר" נוצר
בקובץ הדוגמה בלבד, ונושא את הערכים החוקיים כפי שהם *בזמן ההורדה*.

המיפוי הוא **לפי טקסט הכותרת ולא לפי מיקום**, ולכן עמודה חדשה אינה שוברת קובץ
שכבר נמצא אצל המשתמשים, ואפשר גם למחוק עמודות שאין בהן צורך. קובץ בן גיליון אחד
עדיין נקלט — אז נוצרים האירועים בלי משימות מפורטות.

**גיליון "אירועים"**

| עמודה | חובה | הערות |
|---|---|---|
| מזהה שורה | לא | לקישור לגיליון המשימות בלבד. באירוע יחיד אפשר להשאיר ריק |
| שם לקוח במערכת | כן | חייב להיות זהה לשם הלקוח במערכת; נפתר בדפדפן, לפני שנשלחת שורה |
| שם לקוח האירוע, מספר אירוע, מיקום, הערות למיקום, נפח במטר, כמות משאיות, איש קשר, טלפון איש קשר, הערות | לא | |
| תאריך אירוע | כן | `YYYY-MM-DD`; מתקבל גם `DD/MM/YYYY` |
| ללא חניה / סבלות / איסוף מספק | לא | "כן" או "לא". תא ריק אינו "לא" אלא "לא נכתב" |
| ספקים | לא | שמות מופרדים בפסיק. הספק חייב להיות מוגדר **אצל אותו לקוח** |
| שדות מותאמים של הלקוח | לפי ההגדרה | עמודה לכל שדה, לפי `form_fields` (0053). שדה שהוגדר "חובה" נבדק בשרת |

**גיליון "משימות"**

| עמודה | חובה | הערות |
|---|---|---|
| מזהה שורה (של האירוע) | כן | אלא אם בקובץ אירוע אחד בלבד |
| סוג משימה | כן | לפי השם או לפי ה-code האנגלי (`setup`/`teardown`) |
| כותרת, תאריך משימה, יציאה מהמחסן, תחילה בשטח, כמות שעות, כמות עובדים, משאית, מיקום המשימה, הערות | לא | תאריך ריק נלקח מתאריך האירוע |
| אופן ביצוע | לא | חייב להיות בחיתוך: פעיל ∩ מותר לסוג המשימה ∩ מותר ללקוח |
| מחסן יציאה | לא | לפי שם המחסן |
| זמן נסיעה בכיוון אחד / נדרש ראש צוות | לא | דריסות של מנוע התמחור. NULL = לפי אזור הגיאופנס והמחשבון |
| מחיר ללקוח | לא | מה שגובים. נכנס **נעול** (`is_manual`) ואינו נדרס בחישוב אוטומטי |
| קבלן | לא | לפי שם הקבלן; פותח שורת `task_contractor_terms` על מחיר ברירת המחדל שלו |
| מחיר לקבלן | לא | מה שמשלמים לו. מחייב שגם עמודת "קבלן" מלאה באותה שורה |

**מה שהייבוא עושה בשרת** (`bulk_import_events` → `create_event` +
`app.apply_import_tasks`):

- **שמות נפתרים בשרת** — סוג משימה, אופן ביצוע, מחסן, קבלן וספק. הלקוח הוא
  היוצא מן הכלל: הרשימה ממילא בזיכרון הדפדפן, וההודעה על שם שגוי צריכה להיאמר
  לפני שנשלחת שורה אחת.
- **הקמה ופירוק אינן מוכפלות.** הן נוצרות לכל אירוע בטריגר, ושורה בגיליון
  המשימות *ממלאת* את הקיימת. שורה שנייה מאותו סוג באותו קובץ היא משימה נוספת
  אמיתית ולכן כן נוצרת.
- **שורה שנפסלה מתגלגלת כולה** — האירוע והמשימות שלו אינם נוצרים, והשגיאה
  מדווחת עם מספר השורה. אין אירוע חצי-מיובא.
- **עמודות הכסף דורשות מפתח משלהן, ומראש:** `pricing.edit` (מחיר ללקוח וזמן
  נסיעה), `tasks.delegate` (קבלן), `contractors.edit_pricing` (מחיר לקבלן).
  הבדיקה היא פר-קובץ ולא פר-שורה: קובץ שנושא מפתח שאין למעלה אותו נדחה כולו,
  ולא מיובא חלקית. שדות התכנון עצמם אינם דורשים את מפתחות השדה שלהם — הכתיבה
  רצה תחת `app.system_write`, אחרת "מותר לייבא אירועים" היה גורר בשקט את
  `tasks.reschedule` ואת כל השאר.
- **סטטוס אירוע וסטטוס משימה אינם מיובאים.** לשניהם מחזור חיים משלהם (0036,
  0063) עם מעברים מותרים והרשאת פרסום, ותא באקסל אינו הדרך לעקוף אותו.

הייצוא כותב את אותן עמודות בדיוק, ולכן קובץ שיצא יכול לחזור פנימה. מה שהמייבא
אינו רשאי לראות יוצא ריק — `task_pricing` ו-`task_contractor_terms` מסוננות
ב-RLS, ופרטי איש הקשר יושבים ב-`event_contacts` מאותה סיבה.

חוזה הקובץ עצמו — הכותרות, הנרמול והבנייה של התבנית ושל קובץ הדוגמה — יושב ב-
`src/features/importExport/eventsWorkbook.ts` ונבדק בלי ExcelJS; הצד השרתי ב-
`0052_import_event_tasks.sql` וב-`0076_import_events_full_fields.sql`.

### מפרט האירוע

לכל אירוע יש **מפרט** — המסמך שהלקוח שולח. בכותרת דף האירוע יושב כפתור "מפרט"
עם מונה הגרסאות, ואותו כפתור יושב גם בכרטיס המשימה במגירת הלו״ז — מנהל קבלן
ועובד קבלן אינם פותחים את `/events/:id`, והמשימה היא המקום שבו הם פוגשים את
האירוע. שניהם פותחים מסך אחד בשני מצבים:

- **צפייה** — הגרסה הפעילה מוטמעת במסך: PDF ב-`<object>`, תמונה כתמונה, וקישור
  חיצוני ב-iframe עם מוצא "פתיחה בלשונית חדשה" (אתרים רבים חוסמים הטמעה).
  HEIC מקבל כרטיס הורדה: אין דפדפן שמרנדר אותו, וריבוע שבור גרוע מהודעה.
- **השוואה** — שתי גרסאות זו לצד זו, החדשה מימין והישנה משמאל, כל אחת עם בורר
  גרסה משלה. בטלפון הן נערמות אנכית.

מתחת לשתיהן יושבת היסטוריית הגרסאות: מי העלה, מתי, ומה שם הקובץ.

**הגרסה הפעילה נגזרת ואינה מסומנת** — היא ה-`version` הגבוה ביותר שאינו מוסר.
אין דגל `is_current` שיכול לסתור את המספור, והסרת הגרסה העליונה מחזירה את
הקודמת לתפקיד בלי שום כתיבה נוספת. המספור עצמו נקבע בשרת תחת נעילה פר-אירוע,
ולכן שתי העלאות במקביל אינן יכולות לקבל אותו מספר. מספר של גרסה שהוסרה אינו
חוזר לשימוש.

הקבצים יושבים ב-bucket **פרטי** בשם `event-specs`, בנתיב `<event_id>/<uuid>.<ext>`.
זה החוזה: הפוליסה על `storage.objects` קוראת את מזהה האירוע מהתיקייה הראשונה,
ולכן ההרשאה על הקובץ היא בדיוק ההרשאה על האירוע — בלי טבלת הצטלבות ובלי סנכרון.
אין URL ציבורי; כל תצוגה עוברת ב-`createSignedUrl` לרבע שעה.

**צפייה במפרט היא חלק מצפייה באירוע** (0102). ‏`events.specs_view` פתוח בברירת
המחדל של המרשם לכל שלושת סוגי המשתמש, ופוליסת ה-select שואלת שתי שאלות בלבד:
האם הקורא מחזיק את המפתח, והאם האירוע נפתח לו. ה-`exists` על `events` הוא מה
שמחיל את כל היקפי הראייה, ולכן עובד שרואה רק את האירוע ששובץ אליו רואה רק את
המפרט שלו. עד 0102 היו שתי שכבות שסגרו את זה: הפוליסה דרשה `user_kind = 'staff'`
(ולכן לקוח וקבלן קיבלו רשימה ריקה), ו-0079/0080 כתבו לשלושת תפקידי השטח דחייה
גורפת על כל מודול האירועים, שהמפרט נלכד בה. מי שנוסע לאירוע הוא בדיוק מי שצריך
לקרוא את המסמך, וההכרעה התהפכה. המפתח נשאר קיים — אפשר עדיין לשלול אותו מאדם
או מתפקיד, וזו רק חדלה להיות ברירת המחדל.

**ניהול המפרט נשאר של הצוות.** ‏`events.specs_manage` נגזר מ-`events.edit`,
שפתוח למשתמש לקוח בברירת המחדל של סוג המשתמש — ולכן 0102 סוגר אותו למשתמשי
פורטל בשכבת ה-kind, שמדברת אחרי המענק האישי ואחרי התפקיד. עד אז הנתיב הזה היה
פתוח ובלתי נראה: לקוח יכול היה להוסיף גרסת **קישור** (הדלי חוסם קובץ, לא שורה),
ואיש — גם לא הוא עצמו — לא ראה אותה, כי ה-select היה סגור.

העלאה היא INSERT
תחת RLS; **הסרה עוברת ב-RPC** ‏(`remove_event_spec`), כי פוסטגרס מחילה את פוליסת
ה-select גם על השורה החדשה ב-UPDATE, ולכן שורה אינה יכולה להעלים את עצמה מעיני
מי שמחק אותה — אותה סיבה בדיוק ש-`soft_delete` הוא `security definer`. הקובץ
נשאר בדלי: ההיסטוריה יורדת מהמסך ואינה נמחקת. כל העלאה, הסרה ושחזור נרשמים
ביומן הפעילות של האירוע.

הסכמה ב-`0077_event_specs.sql` (עם הידוקי ה-linter ב-0078 ופתיחת הצפייה ב-
`0102_spec_travels_with_the_event.sql`), החבילה ב-`supabase/tests/16_event_specs.sql`,
הלוגיקה הטהורה ב-`src/features/events/specs.ts` (נבדקת ב-`specs.test.ts`) והמסך
ב-`EventSpecsModal.tsx` — שנפתח מדף האירוע ומ-`TaskDrawer.tsx`.

### ניהול רכבים

`trucks` הייתה מאז 0002 טבלת עזר של שם ומספר רישוי, וכל תפקידה היה להיות ערך
ב-dropdown של שיבוץ. ‏0089 מוסיף לצדה את **הרכב כנכס**: `vehicles`, עם מסמכים,
תאריכי פקיעה, בעלות, נהג וכרטיס דלק.

**שתי הטבלאות נשארות שתיים, והרכב הוא מקור האמת.** `vehicles.truck_id` הוא קישור
אופציונלי ו-1:1 לשורת השיגור, וטריגר דוחף מהרכב את מספר הרישוי והשם אל המשאית
המקושרת — כיוון אחד בלבד. כך כל מה שנשען על `trucks` (‏`tasks.truck_ids`,
`task_assignments`, `work_board_view`, `assignment_conflicts`, סקופ ההרשאות)
ממשיך לעבוד בלי לדעת שהמודול קיים, והכפילות אינה יכולה לסטות בשקט. רכב בלי
קישור פשוט אינו ניתן לשיבוץ, ובכרטיס שלו יושב כפתור "יצירת משאית מהרכב".

**סוגי המסמכים הם קטלוג, לא רשימה בקוד.** `vehicle_document_kinds` נזרעת עם טסט,
רישיון רכב, ביטוח חובה/מקיף/צד ג׳, אישור גז, רישיון מנוף, טכוגרף, רישיון מוביל
ואגרת רישוי, ונערכת ב-`/settings` → "סוגי מסמכי רכב". לכל סוג יש `alert_days`
משלו — על ביטוח חובה מתריעים חודש מראש כי החידוש לוקח יום, ועל רישיון מנוף
שלושה חודשים כי הוא דורש בדיקה מתוזמנת — ו-`is_required`, שממנו נגזרת ספירת
"מסמכי חובה חסרים".

**מצב התוקף מחושב בשרת ולא בלקוח.** ה-view ‏`vehicle_document_status` מחזיר
`valid | expiring | expired | no_expiry` מול הסף של הסוג, והוא מה שהמסך,
הדשבורד והסוויפ קוראים — שלושתם אינם יכולים לחלוק זה על זה.

הקבצים יושבים ב-bucket **פרטי** בשם `vehicle-docs`, בנתיב `<vehicle_id>/<uuid>.<ext>`,
בדיוק בחוזה של `event-specs`: הפוליסה קוראת את מזהה הרכב מהתיקייה הראשונה,
ולכן ההרשאה על הקובץ היא ההרשאה על הרכב. אין URL ציבורי, וההסרה עוברת ב-RPC
‏(`remove_vehicle_document`) מאותה סיבה שכתובה למעלה על המפרט.

**הנהג הוא היסטוריה, לא עמודה.** `vehicle_driver_assignments` מחזיקה טווחי
תאריכים עם הצמדה פתוחה אחת לכל רכב; `assign_vehicle_driver` סוגר את הקודמת
ופותח את החדשה באותה טרנזקציה. `vehicles.current_driver_id` ו-`current_driver_name`
מדונרמלים כדי שהרשימה תיקרא בשאילתה אחת, ונכתבים **רק** מהטריגר — כתיבה ישירה
עליהם נדחית, אחרת העמודה הנגזרת הופכת למקור אמת שני.

**ה-PIN של כרטיס הדלק אינו נקרא בשאילתה של מי שאין לו את המפתח.** הכרטיס יושב
בטבלה נפרדת, `vehicle_fuel_cards`, שהקריאה ממנה דורשת `fleet.view_fuel_card`
והכתיבה `fleet.manage_fuel_card`. זו אינה הקפדה עודפת אלא ההבדל בין הפרדה
אמיתית לבין הסתרה בלקוח: התקדים ברפו לשדה רגיש הוא `field_registry`, שחוסם
*כתיבה* אך אינו מסתיר את הערך בקריאה — מי שמחזיק `fleet.view` היה מקבל את הקוד
ב-PostgREST בלי לפתוח את המסך. ‏RLS היא row-level, ולכן השורה הרגישה חייבת להיות
שורה משלה. מאותה סיבה הביקורת על הטבלה הזו אינה `app.audit()` הגנרית אלא טריגר
שמחליף את `pin_code` ואת `card_number` ב-`***`: מי שינה ומתי כן נרשם, אבל
`audit_log` נקרא במפתח אחר לגמרי, והוא לא ייהפך לדלת האחורית.

**התראות פקיעה.** שני סוגים בקטלוג — `vehicle_document_expiring` ו-
`vehicle_document_expired` — כי "עוד 30 יום" הוא מידע ו"פג" הוא אירוע, ומנהל
צריך יכולת לכבות את הראשון בלי לכבות את השני. `fleet_expiry_sweep()` עובר על
המסמכים החיים מול שלושה ספים (הסף של הסוג, 7 ימים, ויום הפקיעה) ושולח דרך
`app.notify` לכל מי שמחזיק `fleet.view` ולנהג הקבוע של הרכב.

שתי תכונות שלו ראויות לציון: הוא **אידמפוטנטי** — כל (מסמך, תאריך פקיעה, סף)
שנשלח נרשם, ותאריך הפקיעה הוא חלק מהמפתח, ולכן חידוש המסמך דורך את ההתראה
מחדש מעצמו בלי איפוס ידני; והוא שולח **התראה אחת לכל מסמך בכל הרצה** גם
כששלושה ספים בשלו יחד (מסמך שנרשם כשהוא כבר פג), כי שלוש שורות פעמון על אותו
ביטוח הן בדיוק מה שגורם לאנשים לכבות התראות. הספים הנבלעים נרשמים ומוחזרים
כ-`suppressed`.

אין `pg_cron` ברפו ואין אירוע שורה שאומר "עבר יום", ולכן ההרצה היא חיצונית:
`supabase/functions/fleet-expiry-sweep` (ראו "התפעול המשותף"). מנהל צי יכול גם
ללחוץ "בדיקת תוקף" במסך — הסוויפ אידמפוטנטי, ולחיצה חוזרת אינה עולה דבר.

הסכמה ב-`0089_vehicles.sql`, סקשני הדשבורד ב-`0090_fleet_dashboard_sections.sql`,
החבילה ב-`supabase/tests/19_vehicles.sql`, הלוגיקה הטהורה ב-
`src/features/vehicles/vehicles.ts` (נבדקת ב-`vehicles.test.ts`) והמסכים ב-
`src/features/vehicles/`.

### יומן פעילות של אירוע

בדף האירוע יושב יומן שמתעד שני דברים באותו ציר זמן: **שינויים** ו**מלל חופשי**.

- שינוי בשדה מעקב באירוע (כמות משאיות, תאריך, סטטוס, לקוח, מיקום, נפח, הערות, תוספות,
  איש קשר, ספקים) נרשם אוטומטית בטריגר — עם הערך הקודם, הערך החדש, מי שינה ומתי.
  הערכים נשמרים כפי שקוראים אותם: מזהה סטטוס הופך לשם הסטטוס, בוליאני ל"כן/לא", תאריך ל-DD/MM/YYYY.
- מי שמחזיק `events.activity_note` יכול להוסיף רשומת מלל חופשי — הסיבה שמאחורי השינוי,
  שיחה עם הלקוח, כל דבר ששווה לזכור.
- היומן לקריאה בלבד אחרי הכתיבה: אין פוליסת UPDATE, ומחיקה שמורה לאדמין.
  שינויים שנעשו בשמירה אחת מקובצים לרשומה אחת בתצוגה.
- `events.activity_log` נגזר מ-`events.view` ו-`events.activity_note` מ-`events.edit`,
  ולכן מי שכבר רואה או עורך אירועים מקבל את היומן בלי הגדרה נוספת.

### נוכחות ומשמרות

**המשמרת אינה טבלה.** היא נגזרת מהמשימות ששובצו לעובד, ב-`app.planned_shifts`,
ולכן היא לעולם לא מתיישנת מול שינוי בשעות המשימה. שלושה כללים מרכיבים אותה:

- **מהיכן מתחילים** — `task_assignments.work_site` (ו-`task_contractor_workers.work_site`)
  קובע פר-משובץ אם הוא יוצא מהמחסן או מגיע לשטח. מי שיוצא מהמחסן מתחיל ב-
  `warehouse_start_time`, כל השאר ב-`onsite_start_time`.
- **מאיזה מחסן** — `warehouses` היא טבלה, והמחסן הוא תכונה של **הלקוח**
  (`customers.warehouse_id`): לכל לקוח מחסן אחד, ומשם יוצאים לכל המשימות שלו.
  `tasks.warehouse_id` קיים כדריסה למשימה בודדת, והוא גם הדרך היחידה שמשימה
  עצמאית — כזו שאין לה לקוח — תוכל לנקוב במחסן. אין נפילה ל"המחסן הקרוב
  ביותר": היא הייתה מתירה לעובד להחתים מהמחסן של לקוח אחר. רדיוס פר-מחסן
  גובר על הגלובלי, ודריסה אישית של העובד גוברת על שניהם.
- **מתי מסיימים** — סיום העבודה בשטח, ועוד זמן הנסיעה חזרה **למי שיצא
  מהמחסן**. הנסיעה הזו היא, בהגדרה, החזרה מהמשימה האחרונה אל המחסן, ולמי
  שהגיע ישירות לשטח אין למה לחזור — הוא סיים כשהעבודה נגמרה. עד 0079 היא
  נוספה לכולם, ולכן גם שולמה. זמן הנסיעה עצמו נשלף מ-`app.task_travel_hours`,
  אותה הכרעה בדיוק שמשמשת את מנוע התמחור (דריסה על המשימה גוברת, אחרת אזור
  הגיאופנס של מיקום האירוע).
- **איחוד** — שתי משימות שהפער ביניהן קטן מ-`merge_gap_minutes` (ברירת מחדל שעתיים)
  הן משמרת אחת, והסיום שלה נלקח מהמשימה האחרונה בה.

**שלושה מרכיבים, שלוש שורות.** עד 0083 שעת היציאה מהמחסן הייתה גם ההתחלה של
המשימה הראשונה, ולכן משימה בת שלוש שעות הוצגה כ-06:00–10:00: הנסיעה נבלעה
בתוכה, ומי שקרא לא ידע מתי הוא באמת מתחיל לעבוד. עכשיו `warehouse_start_at`
הוא שדה משלו (null למי שמגיע לשטח), `start_at` הוא תחילת העבודה, והנסיעה חזרה
יושבת ב-`totals.travel_hours` — וסך המשמרת נשאר מה שהגזירה קובעת. ראש הצוות של
האירוע מקבל מתוך המשימה גם את איש הקשר של הלקוח וגם את נקודת ההתחלה של כל אחד
מהצוות: מי במחסן בשש ומי באתר בשבע.

**שתי הנסיעות מסומנות בצ׳יפ, ולא רק אחת.** בציר השעות, צ׳יפ של משמרת שעובדים
בה כמה אנשים נושא פס מקווקו בראשו שגובהו הוא בדיוק הנסיעה מהמחסן אל השטח —
והסיום, שכולל את הנסיעה חזרה מאז ומתמיד, נראה עד עכשיו כמו שעת סיום עבודה
רגילה. עכשיו יש גם פס תחתון, מסוף העבודה ועד ההגעה למחסן, ובין שניהם יושב מה
שהוא באמת עבודה בשטח (וזה גם הטווח שנכתב בגוף הצ׳יפ). הפס התחתון נגזר
מ-`travel_hours` של המשמרת עצמה ולא מהפרש בין שני אנשים, ולכן הוא מופיע גם
כשכל הקבוצה יוצאת מהמחסן — המקרה שאין לו פס עליון. בצ׳יפ של משמרת יחידה
(טבלת השיבוץ) הסימון הוא אייקון משאית לצד השעות, ובחלונית הרחיפה מופיעה שעת
סיום העבודה לצד משך הנסיעה. שני הפסים חסומים בגובהם, ואם יחד הם חורגים הם
מצטמצמים באותו יחס — כדי שהצ׳יפ לא יאבד את שמות העובדים.

מגירת "פרטי המשמרת" (`shift_task_breakdown`) מחשבת את הרצף מהמשימות ולא מהשורה
שנלחצה, ולכן היא חייבת לחשב **את אותו דבר**: עד 0079 היא החזירה `max(end_at)` —
סיום העבודה בשטח — בעוד שהגזירה מוסיפה את הנסיעה, ואותה משמרת נגמרה בשעה אחת
בלוח ובשעה אחרת במגירה שנפתחה מתוכו. לחיצה על משימה בתוך הרצף פותחת את פרטיה
באותה מגירה (חזרה בכפתור), ולא מנווטת החוצה: מתוך המשמרת השאלה היא "מה אני עושה
כאן", והקישור לדף האירוע יושב בתוך הפאנל למי שרשאי לפתוח אותו.

החישוב יושב ב-SQL ולא בדפדפן במכוון: לוח המשמרות, שער "מותר לך להתחיל?" בשעון,
ועמודת מתוכנן-מול-בפועל בדוח חייבים להסכים, ומימוש שני היה הופך את הראשון לעותק
שמתיישן. מאותה סיבה `app.attendance_calc` היא פונקציה טהורה: התצוגה המקדימה במסך
ההגדרות רצה עליה עצמה דרך `preview_attendance_pay`.

**השעון כותב רק דרך RPC.** ל-`attendance_entries` אין פוליסת INSERT לעובד. הכתיבה
עוברת ב-`attendance_clock_in`/`attendance_clock_out`, ושם נאכפים שני הכללים
שנקבעו פר-עובד: "נדרש מיקום" (החתמה מחוץ לרדיוס נדחית) ו"מותר להתחיל לפני
המשימה". בדיקה שהייתה יושבת בדפדפן בלבד היא קוסמטית — הטבלה חשופה דרך PostgREST.

נקודת הייחוס נגזרת במשמרת עצמה ולא בשעון: מי שיוצא מהמחסן נמדד בכניסה מול
המחסן, ומי שמגיע לאתר מול האתר. ביציאה, מי שהגיע לאתר נמדד מולו — משם הוא גם
התחיל — ולמי שיצא מהמחסן יש **שתי** נקודות סיום לגיטימיות, האתר והמחסן שאליו
חזר, ונבחרת הקרובה מביניהן (0082). קודם לכן היציאה נמדדה מול האתר בלבד, והעובד
שעמד במחסן שאליו המערכת עצמה שלחה אותו — היא סופרת לו את הנסיעה הזו — נחסם.
שתי הנקודות כבר יושבות על שורת המשמרת (`start_lat/lng` ו-`end_lat/lng`), ולכן
אין כאן שליפה חדשה אלא בחירה, ומי שרחוק משתיהן עדיין נחסם.

שני חריגים מכוונים בחסימת המיקום: קריאה חסרה נדחית תמיד (זה בשליטת העובד), אבל
אתר או מחסן בלי קואורדינטות מתקבל ומסומן `no_site_coords` (זה פער נתונים במשרד), ודיוק
ה-GPS מנוכה מהמרחק לפני ההשוואה כדי לחסום רק מי שמוכח מחוץ לטווח. פתח המילוט הוא
`attendance_record_entry`, שבגופו אין בכלל בדיקת מיקום — ולכן אין דגל שעובד יכול
להעביר כדי להגיע לפטור.

**עובד מדווח, מנהל מכריע.** שעון שלא עבד — סוללה, קליטה, או שכחה — לא אמור להיגמר
בשעות שנעלמו, ולכן `attendance_submit_entry` נותן לעובד לדווח משמרת שהסתיימה.
הדיווח נכתב לאותה טבלה עם `status = 'pending'`, ו**אינו נספר בשום סיכום** עד
ש-`attendance_review_entry` מכריע: `attendance_report` מוציא כל שורה שאינה
`approved` מהסיכומים ומהצבר השבועי שמזין את התקרה השבועית, ומחזיר אותה כשורה
מסומנת עם השכר שישולם *אם* תאושר. דחייה מחייבת נימוק, והוא מה שהעובד רואה.

הדיווח מוגבל בגופו של ה-RPC — חלון אחורה (`self_entry.max_backdate_days`), אורך
מרבי, איסור על דיווח עתידי, ואיסור על חפיפה לשעות שכבר נרשמו, שנבדק שוב ברגע
האישור כדי שהחתמת שעון שנוצרה בינתיים לא תשולם פעמיים. שעת סיום היא חובה: משמרת
פתוחה היא מצב שהשעון מנהל. `attendance.status` (וגם `reviewed_by`/`reviewed_at`)
רשומים ב-`field_registry` תחת `attendance.approve_entry` — בלי זה פוליסת ה-UPDATE
שמתירה לעובד לגעת בשורה שלו הייתה מתירה לו גם לאשר את עצמו. `attendance.submit_entry`
הוא יכולת של כל עובד, `attendance.approve_entry` נגזר מ-`attendance.edit_entry`,
וההתראה למאשרים נשלחת דרך `app.profiles_with` — הצד ההפוך של `app.has`.

**השכר מחושב בקריאה ולא נשמר.** אין טבלת שכר ואין חישוב מחדש: הרשומה מחזיקה שעות,
`worker_pay_settings` מחזיקה תעריף, השלמה לשעות והאם העובד זכאי לשעות נוספות,
ו-`app_settings['attendance.overtime']` מחזיקה את המדרגות. `attendance_report`
מחזיר את השעות לכולם ואת הסכומים רק למי שמחזיק `attendance.view_pay` — מאותה
שאילתה, כי רכז משמרות צריך את הראשון בלי השני.

**ההשלמה נמדדת מתחילת המשמרת, ולכן איחור מקצר אותה.** "מובטחות 6 שעות" שילמו
6 שעות גם למי שהגיע ברבע השעה השנייה, כלומר תמרצו בדיוק את מה שהן נועדו לכסות.
מ-0084 התקרה יורדת בגובה האיחור — הגיע ב-10:15 למשמרת של 10:00, התקרה היא 5:45,
והאיחור עולה לו את עצמו פעם אחת ולא פעמיים. מעל סף שנקבע פר-עובד
(`late_topup_forfeit_minutes`) ההשלמה נשמטת כליל: זו החלטה של המשרד על איחור
שאינו "כמה דקות", והיא יושבת בכרטיס העובד ולא בקוד. בלי משמרת משובצת אין נקודת
ייחוס, ולכן אין איחור.

**שתי תוספות שאינן שעות, לצד הבונוס.** `team_lead_bonus` הוא סכום לכל משימה
במשמרת שבה העובד רשום כראש צוות — נספר על המשימות עצמן ולא על המשמרת כיחידה —
ו-`shift_bonus` הוא סכום קבוע לכל משמרת. שלושתם (עם הבונוס הידני) יוצאים
כשורות נפרדות בפירוט ומצטרפים ל-`bonus`, שממשיך להיות מה שהוא היה: כמה מהסכום
אינו שעות. אף אחד מהם אינו נוגע במדרגות השעות הנוספות ובתקרה השבועית, מאותו
נימוק שהוציא את הבונוס מהן ב-0033.

**דיווח ידני נושא מיקום במילים.** זה בדיוק המקרה שבו אין GPS לאמת מולו — השעון
לא עבד — ולכן `clock_in_place` ו-`clock_out_place` הם חובה בדיווח, רשומים
ב-`field_registry` תחת `attendance.edit_entry`, ומכאן ניתנים לתיקון בידי מי
שמאשר. ההשלמה, השעות הנוספות והסכומים נגזרים מהשעות ומהגדרות העובד, ולכן תיקון
שעות מעדכן אותם מאליו.

**בונוס למשמרת הוא שורה, לא שעות.** `attendance_entry_bonus` מחזיקה סכום שקלי
פר-משמרת, ו-`app.attendance_calc` מוסיפה אותו כשורה נפרדת ב-`lines` ולסך
לתשלום. הוא במכוון אינו נוגע ב-`paid_hours`, במדרגות השעות הנוספות ובתקרה
השבועית: שעות פיקטיביות היו הופכות בונוס של 100 ש״ח לשווה יותר לעובד שממילא
עשה שעות נוספות באותו יום. הסך של המשמרת כבר כולל אותו, ולכן הוא נספר בסך
החודשי של העובד בלי חיבור נוסף — ו-`totals.bonus` קיים רק כדי לומר כמה מהסכום
אינו שעות.

הוא **טבלה נפרדת ולא עמודה על `attendance_entries`**, מאותו נימוק שהוציא את
`hourly_rate` ל-`worker_pay_settings`: `ae_select` מתירה לכל מי שמחזיק
`attendance.view_all` לקרוא כל שורת נוכחות, ועמודת סכום שם הייתה נקראת ישירות
דרך PostgREST בידי רכז משמרות שאינו רשאי לראות שכר. הפוליסה על הטבלה הנפרדת
בודקת את הרשאת הכסף עצמה, ו-`attendance_report` משמיט את `bonus` ואת
`bonus_note` מהשורה לפי אותה הכרעה שמשמיטה את `total`.

הכתיבה עוברת ב-`attendance_set_bonus` ולא בפרמטר על `attendance_save_entry`,
כי היא נשמרת במפתח אחר: `attendance.manage_bonus` (נגזר מ-`attendance.manage_pay`)
ולא `attendance.edit_entry`. מי שמתקן שעות אינו בהכרח מי שרשאי לקבוע סכום כסף.
אפס מוחק את הבונוס במקום לאפס אותו, ובונוס על רשומה שנדחתה נחסם — הוא לא היה
משולם לעולם.

**עובד קבלן מחתים כמו כל אחד אחר.** הוא מקבל שורת `profiles` עם
`contractor_worker_id` שמקשר אותה לשורת הסגל, ולא נתיב הרשאות מקביל: `app.has`
מחזיר `false` כשאין profile, ולכן בלי השורה הזו שום דבר במערכת לא היה עובד עבורו.
התפקיד `contractor_worker` נסגר במפורש על המודולים `portal` ו-`contractors`, אחרת
הוא היה יורש מברירות המחדל של `contractor_user` את דף הכספים של הקבלן על כל מה שבו.
בכל השאר הוא עובד מן השורה: אותם `/calendar`, `/board`, `/my/schedule`,
`/my/attendance` ו-`/attendance` של כל עובד, מצומצמים בזרוע הקבלן של
`tasks_select` למשימות שפורסמו והוא רשום עליהן.

**הגשר נוצר בשיבוץ, לא לפניו.** לקבלן שתי רשימות עובדים: `contractor_workers`,
הסגל שהוא מקליד בעצמו, ו-`profiles` עם `contractor_id` — החשבונות. חשבון
שהמשרד יצר במסך העובדים נושא `contractor_id` בלי `contractor_worker_id`, ולכן
לא היה בשום רשימה שאפשר לשבץ ממנה. `contractor_assignable_workers` מאחד את
השתיים, ו-`contractor_assign_worker` יוצר את שורת הסגל וכותב את הקישור ברגע
השיבוץ הראשון. זה אינו נוחות: `app.planned_shifts_many` מצרפת דרך
`profiles.contractor_worker_id`, ולכן בלי הגשר העובד היה משובץ ובכל זאת בלי
משמרת ובלי יכולת להחתים. הסרה משיבוץ אינה מוחקת את שורת הסגל — הורדה ממשימה
אינה פיטורים.

> `navigator.geolocation` דורש הקשר מאובטח. בפרודקשן ובלוקלהוסט זה קיים; שרת פיתוח
> שנגישים אליו דרך כתובת IP ברשת המקומית לא יוכל לבקש מיקום.

### רווחיות פר-משימה

`task_pnl` (0070) עונה על "כמה חייבתי ללקוח, וכמה זה עלה לי בפועל" ברזולוציה
של משימה. שלוש הכרעות מרכיבות אותו.

**ההקצאה לא נכתבה מחדש.** ‏`app.payroll_task_alloc` (0041) כבר פיזרה את שכר
המשמרת בין המשימות שבה — משוקלל לפי `hours_count`, בנפילה לחלוקה שווה — אלא
שסיכמה ל-`by_customer` לפני ההחזרה. 0070 מחלץ את החישוב ל-`app.payroll_task_amounts`
ומשאיר את הקורא הישן עטיפה דקה מעליו, בפלט זהה. אותה תזה של 0039 ו-0044:
מימוש שני של אותו חישוב מתיישן.

**שני בסיסי מדידה, ומוצהרים.** ההכנסה היא `task_pricing.price`, שמחושב
מ-`worker_count` × `hours_count` — כלומר **מהתכנון**. העלות נמדדת מהשעות
**שהוחתמו**. אפשר היה להריץ מחדש את `app.price_calc` עם השעות שבפועל ולהציג
"מחיר לפי ביצוע", אבל מספר כזה מעולם לא הוצג ללקוח ולא חויב, ובטבלה לצד עלות
אמיתית הוא נקרא ככסף; הוא גם היה ריק בדיוק במשימות המעניינות, כי
`app.recalc_task_price` מחזירה מחיר רק ללקוח ב-`pricing_mode='auto'` בלי
`is_manual`. במקומו כל שורה נושאת **מתוכנן מול בפועל בשעות ובראשים** — עובדה
שמסבירה למה השוליים זזו, ולא תרחיש נגדי.

**הרווח כאן כולל נטל מעביד, וזה מפריד אותו מ-`/reports/profitability`.**
‏`app.margin_summary` (0044) מחסרת שכר בלי הנטל; `task_pnl` מחסרת
`payroll × (1 + pct/100)`, כמו `finance.profit_summary` (0069). ההפרש בין שני
המסכים הוא בדיוק `payroll × pct/100`, והוא מוצהר ב-`meta`.

`app.task_pnl_rows` היא **`security definer` במכוון**: ‏`task_contractor_terms`
נקראת רק בידי מי שמחזיק `contractors.view_pricing`, ושאילתת invoker בידי קורא
שמחזיק את צרור הרווח אבל לא את המפתח הזה הייתה מחזירה אפס — עלות קבלן 0 ורווח
מנופח בגובה כל הקבלנות, בלי שום סימן. מה שהופך את זה לשקול הוא
ש-`app.margin_require()` כבר סירבה לכל היקף נתונים מצומצם.

הצרור נושא מפתח אחד מעבר לזה של `margin.*`: **`dashboard.all_workers`**. שכר
פר-משימה על משימה שמשובץ אליה עובד אחד הוא השכר של אותו עובד לאותו יום, וזה
בדיוק הקו ש-`app.payroll_by_worker` כבר מותחת. מה שאינו חוסם הוא `customers.view`:
השורה כאן היא משימה ולא לקוח, ולכן המפתח משמיט את שם הלקוח ואינו סוגר את הדוח.

## אבטחה והרשאות

כל הרשאה היא **שורה ברישום** (`permission_registry`) עם מפתח מנוקד — `tasks.assign.worker`,
`contractors.edit_pricing` — ולא ערך enum. הוספת יכולת חדשה היא `INSERT`, ולכן מודול שייכתב
בעתיד מקבל הרשאות מלאות ומופיע במסך הניהול בלי שינוי קוד.

ההכרעה נעשית במקום אחד, `app.has(key)`, בסדר הזה:

| # | שכבה | טבלה |
|---|---|---|
| 1 | אדמין | `profiles.is_admin` |
| 2 | חריגה אישית (מותר/חסום) | `user_permission_grants` |
| 3 | תפקידים שהמשתמש חבר בהם | `role_permissions` |
| 4 | ברירת מחדל לסוג משתמש | `kind_permission_defaults` |
| 5 | ברירת מחדל של המפתח | `permission_registry.default_allowed` |
| 6 | המפתח הרחב שממנו נגזר | `permission_registry.implied_by` |
| 7 | חסימה | — |

שלב 6 הוא מה שמאפשר לפצל הרשאה גסה לדקות בלי לשבור: `tasks.reschedule` נגזר מ-`tasks.edit`,
ולכן מי שקיבל "עריכת משימות" ממשיך להזיז משימות עד שאדמין יחליט אחרת. תפקיד צר "סוגר מודול"
(חסימה מפורשת) כדי לא לרשת יכולות בטעות.

**איפה זה נאכף**

| שכבה | מנגנון |
|---|---|
| שורות — אילו נתונים רואים | `permission_scopes` בתוך פוליסות ה-SELECT: לקוחות, קבלנים, סוגי משימה, סטטוסים, חלון תאריכים, "רק מה שמשויך אליי" |
| עמודות — עריכה | טריגר גנרי אחד, `app.enforce_field_perms()`, שקורא את `field_registry` לפי שם הטבלה. יושב על הטבלה ולא על ה-RPC ולכן מכסה את כל נתיבי הכתיבה |
| עמודות — צפייה | תצוגות `*_secure` שנוצרות מ-`field_registry`, מיסוך `work_board_view`, ו-`event_activity_feed` שמשמיט שינויים בשדות שאסור לקורא לראות |
| פעולות | `app.require(key)` בתוך ה-RPCs |

**‏`is_admin` אינו GRANT.** שכבת ההרשאות של האפליקציה יושבת *מעל* הרשאות
Postgres ואינה מחליפה אותן, ולכן פונקציית `public` שהיא **security invoker**
חייבת שהקורא יוכל להריץ גם כל עוזר ב-`app` שהיא קוראת לו — אחרת התוצאה היא
`permission denied for function …` (42501) לכל משתמש, מנהל מערכת כולל.
זה מה שהשבית את "רווחיות לפי משימה" מיום שנכתבה: `public.task_pnl` הוא
invoker במכוון (ספירת ה-`truncated` חייבת לראות את מה שהקורא רואה), ו-0070
שלל מ-`authenticated` את ההרצה של `app.task_pnl_rows` שהוא קורא לו. ‏0087
מחזיר את ההענקה, כמו ש-0044 עושה לעוזרים של `customer_profitability`.
בדיקה שרצה בזהות superuser לא יכולה לגלות את זה — GRANTs נעקפים שם — ולכן
0087 נושא בהערותיו את השאילתה שמאתרת את הדפוס בכל המסד.

**מנהל מערכת אינו עובד, ואינו מוגבל בהיקף נתונים.** במסד הוא שורת `staff` עם
`profiles.is_admin`, וכך זה נשאר: `user_kind` מכריע עשרות פוליסות, את
`permission_roles.user_kind` ואת `kind_permission_defaults`, וערך אנום רביעי
היה נוגע בכולן כדי לתאר מישהו שממילא עוקף את כולן. מה שהשתנה (0085) הוא
המקומות שבהם ההבחנה באמת חסרה:

- **הטופס שואל "סוג משתמש" בארבע אפשרויות**, ו"מנהל מערכת" היא אחת מהן: היא
  פותחת שורת `staff` **בלי תפקיד צוות**. עד כאן היה צריך לרשום מנהל כ"צוות",
  והטופס ממלא `worker` כברירת מחדל — כך שהמנהל נכנס לרוסטר לוח המשמרות
  ולרשימות השיבוץ. מי שגם מנהל וגם עובד נפתח כ"צוות" ומקבל את המתג "מנהל
  מערכת"; רק הוא, ולא כל מנהל, מקבל שעון נוכחות ומשמרות.
- **הרוסטר הוא של עובדים.** ‏`app.shift_roster` דורש תפקיד צוות (או שורת סגל
  אצל קבלן, או שיבוץ בפועל בטווח המוצג), ולא "כל פרופיל `staff`". שורה שאי
  אפשר לשבץ אליה היא שורה שלעולם תישאר ריקה.
- **‏`app.scope_rows` שותקת לאדמין.** זו הייתה הסיבה ל"למה כמנהל מערכת אין לי
  הרשאה לרווחיות לפי משימה": שערי הכספים (0041/0044/0058/0059/0069/0070/0074)
  נועלים קורא ש"היקף הנתונים שלו מצומצם", ודי היה בתפקיד ישן שנושא היקף —
  `worker`/`driver`/`team_lead` נושאים `own` על `tasks` מאז 0011 — כדי לסגור
  את כולם בפניו. `app.has` עוקף את שכבת ההרשאות לאדמין וכל פוליסת RLS נפתחת
  ב-`app.is_admin() or`; רק שאלת ההיקף המשיכה להיענות מהטבלה.

**מי אתה, לא רק מה מותר לך.** מפתח עונה על "מה מותר", ולמנהל מערכת הוא עונה
תמיד כן. זה נכון להרשאות ולא למסך ששייך לאדם מסוים, ולכן `NavItem` ו-`handle`
של נתיב נושאים גם `audience` — פרדיקט על מי שקורא, לצד המפתח:

| פרדיקט | מי | מה הוא גודר |
|---|---|---|
| `forEmployees` | מנהל מערכת רק אם יש לו תפקיד צוות; כל השאר כרגיל | `/my/schedule`, `/my/attendance` |
| `forContractors` | מי שיש לו `contractor_id`, או `contractor_user` | `/my/staff` |

התפריט (`visibleNavSections`) ו-`RouteGate` קוראים את אותו פרדיקט, ולכן מה
שאינו בתפריט גם אינו נפתח בהקלדת הנתיב.

**מסך אחד לכולם.** ללקוח ולקבלן אין מסכים משלהם. הם נכנסים לאותו shell, לאותם
נתיבים ולאותם קומפוננטים כמו עובד, וכל הבדל בין מה שהם רואים נובע ממפתח במרשם
או מ-RLS — לא מ-`user_kind`. עמודה שנשענת על join שה-RLS מרוקן (צוות, ראש צוות,
קבלן) נושאת `viewPerm` ונעלמת, ולא מוצגת ריקה; סקשן בדשבורד שאין עליו מפתח חוזר
`null` מ-`dashboard_stats` ולא מצויר; ופילטר שיש בו אפשרות אחת נשמט.

מה שהחזיק את זה קודם הייתה הפניה לפי `user_kind`, שהייתה גם מה שמנע ממסך צוות
להיות נגיש ב-URL. במקומה כל נתיב מצהיר על המפתח שלו ב-`handle`, ו-`RouteGate`
דוחה נתיב שלא הצהיר על כלום. זה חזק יותר: ההפניה חסמה סוג משתמש אחד מתת-עץ אחד,
והשער חוסם כל משתמש מכל נתיב שאין לו את המפתח שלו.

הקבלן היה האחרון שנשאר מחוץ לזה. `/portal` היה shell שלם עם chrome משלו, וארבע
לשוניות שהחזיקו את לוח השנה, הלו״ז, הסגל והנוכחות שלו; ההפניה שהחזיקה אותו שם
היא גם מה שהפך `board.view` ו-`calendar.view`, שהתפקידים שלו כבר החזיקו מ-0066,
לקוד שאי אפשר להגיע אליו. ‏0071 מסיר אותה, וכל לשונית הופכת לנתיב שכבר קיים:
‏`/calendar`, `/board`, `/attendance`, `/my/staff`. ‏`/portal` נשאר כדף הכספים
שלו, בתוך ה-shell כמו כל מסך אחר.

מה שאפשר את זה הוא ששכבת ה-`default_allowed` של ארבעת מפתחות ה-`portal.*`
כובתה: כל עוד כל איש staff פתר אותם `true`, לא היה אפשר לגדר בהם נתיב, וזו
בדיוק הסיבה שהחסימה נעשתה בהפניה ידנית ולא בשער. הקבלנים ממשיכים להחזיק אותם
דרך `kind_permission_defaults` ודרך התפקיד.

**מה שהלקוח רואה בכספים הוא כמה הוא הוציא — ולא כמה אנחנו הכנסנו.** אלה אותו
`task_pricing.price` משני צדדים, וללקוח הוצג הצד שלנו: `pricing.view`, שהוא
צריך כדי לקרוא את התמחור של המשימות שלו, גורר `pricing.revenue` וממנו
`finance.income_view`; ו-`dashboard.view` גורר `reports.view`. אף אחד מהם לא
הוענק — כולם נגזרו. ‏0074 סוגר את השלושה בשכבת ה-kind *וגם* בשכבת התפקיד
(שגוברת עליה, ולכן שורת allow קיימת הייתה מנצחת חסימה של ה-kind), ופותח
במקומם מפתח אחד, `finance.customer_spend`, שאינו נגזר משום דבר. ללקוח גם אין
נוכחות — לא שעון, לא משמרות ולא דוח — לא למנהל ולא לעובדים שלו.

**מה שעובד השטח רואה.** אותו לוח, אותו לוח שנה ואותו דף אירוע כמו כולם —
מצומצמים בשלושה מפתחות שנרשמו ב-0079 כדי שיהיה אפשר לכבות בהם כלים בלי לכבות
את המסך:

| מפתח | מה הוא שולט בו | ברירת המחדל של "עובד" |
|---|---|---|
| `calendar.filter` | שורת הסינון, החיפוש והצ׳יפים בלוח השנה | כבוי |
| `board.filter` | שורת הסינון והחיפוש בלו״ז | כבוי |
| `board.columns` (מ-0011) | בורר התצוגה ובורר השדות בלו״ז | כבוי |
| `board.open_task` | פתיחת כרטיס המשימה בלחיצה | כבוי |

שלושתם `implied_by` של מפתח הגישה של המודול, ולכן מי שכבר פותח את המסך ממשיך
להחזיק אותם בלי שורת הענקה — התוספת אינה מורידה דבר מאיש, היא רק מאפשרת דחייה.
הדחייה עצמה נכתבה לתפקיד **"עובד"** בלבד; נהג, ראש צוות וכל תפקיד שהוגדר במערכת
ממשיכים כרגיל, ומי שרוצה להתנהג כמו עובד שטח נקבע במסך ההרשאות ולא במיגרציה.

בלי `board.columns` הלו״ז אינו "בלי בורר" אלא **נעול על תצוגה אחת** — טבלה בכל
רוחב מסך, גוון לכל אירוע, ימים ריקים גלויים, צפיפות מינימלית, מיון לפי שעה
ופרוס. ‏`localStorage` אינו נקרא ואינו נכתב במצב הזה: העדפה שנשמרה בדפדפן הזה
בתפקיד אחר הייתה משנה מסך שאין בו כפתור להחזיר אותה. ובלי `board.open_task`
לחיצה על משימה מובילה **לדף האירוע** — כרטיס המשימה הוא מסך עריכה, ומי שאינו
עורך צריך את מה שסביב המשימה ולא את השדות שלה.

`events.view` נפתח לתפקיד "עובד" באותה מיגרציה, ושאר מודול האירועים נכתב מחדש
כדחייה מפורשת — כולל מפתחות שנרשמו אחרי 0011 (יומן הפעילות, המפרט) והיו נדלקים
לו בהיסק מ-`events.view`. "לראות את האירוע" אינו "לראות את מי שינה בו מה".

**המפרט יצא מהכלל הזה ב-0102.** הדחייה הגורפת נכתבה על מודול שלם ולא כהכרעה על
המסמך עצמו, והתוצאה בשטח הייתה הפוכה מהכוונה: מי שנוסע לאירוע — עובד, נהג, ראש
צוות, עובד קבלן ומנהלו — הוא בדיוק מי שצריך לקרוא את מה שהלקוח שלח, והוא היחיד
שלא ראה אותו. שורות הדחייה על `events.specs_view` נמחקו (ולא הופכו ל-true, כדי
שהתפקיד יישען שוב על המרשם), והמפתח נרשם מחדש כ-`default_allowed` לשלושת סוגי
המשתמש. יומן הפעילות **לא** זז — הוא באמת "מי שינה בו מה" ולא מסמך העבודה.

**דף האירוע אינו רשימת האירועים.** ‏`events.view` שלט בשלושה דברים בבת אחת —
זרוע ה-staff ב-`events_select`, הנתיב `/events/:id` והנתיב `/events` — ולכן
0079 פתח לעובד גם קטלוג שאין לו בו מה לעשות. ‏0082 מוציא את הרשימה למפתח
`events.list` (נגזר מ-`events.view`, ולכן איש אינו מאבד אותו) וסוגר אותה
לשלושת תפקידי השטח. השובל בכותרת מקשר לאב רק כשהאב באמת נפתח לקורא, אחרת
"אירועים" הוא טקסט ולא קישור אל "אין לך הרשאה".

**משימה שטרם פורסמה אינה מזמינה גם את האירוע שלה.** ‏0063 קבעה את הכלל בצד
המשימות — מי שכל זיקתו למשימה היא השיבוץ רואה רק את מה שפורסם — אבל
`events_select` נשענה על אותה זיקה בדיוק בלי לשאול על הסטטוס, ולכן טיוטה
שהרכז עוד עובד עליה הופיעה בלוח השנה של העובד. ‏`app.on_event_as_staff` (0082)
מרכזת את השאלה, כמו שזרוע הקבלן כבר עשתה מאז 0066.

**ראש הצוות של האירוע אינו מפתח — הוא תפקיד על השורה.** אותו אדם הוא ראש צוות
באירוע אחד ועובד מן השורה בבא, ולכן `app.is_event_team_lead` נבדקת פר-אירוע
ולא במרשם. היא פותחת שלושה דברים שראש צוות בשטח צריך כדי לנהל את היום ושעובד
מן השורה אינו צריך: יומן האירוע, הוספת תיעוד בו, ושם וטלפון של איש הקשר. המסך
מכריע את אותה שאלה מ-`team_lead_id` שכבר מגיע בלו״ז, בלי שאילתה נוספת, והשרת
מכריע אותה בעצמו בפוליסות על `event_activity` ועל `event_contacts`.

**"חסר" הוא מדידה, לא נתון.** ‏`showOutcome` כבר החזיק את "מתוך" ואת "נוספות"
אצל מי שמאשר את המשמרת ולא אצל מי שעבד אותה, ואריח "שעות חסרות" נשאר מחוצה לו
בטעות. הוא מצטרף אליהם. מנגד, פתיחת שורת נוכחות חדלה לדרוש מפתח עריכה: המגירה
כבר מציירת כל שדה כ-`disabled` למי שאין לו מפתח, ולכן העובד פותח את המשמרת שלו
וקורא ממה היא מורכבת — והשכר שלו מופיע גם בשעון עצמו, מאותו `attendance_report`
שמשמיט סכומים למי שאין לו `attendance.view_own_pay`.

> ‏`app.event_visible` (0005) הייתה `security definer` ששואלת רק
> `has('events.view')` — בלי היקפי השורות. כל עוד לא היה לעובד שטח את המפתח
> הזה ההשמטה לא הזיקה; מרגע ש-0079 הדליק לו אותו היא החזירה `true` על **כל**
> אירוע, ואיתה נפתחו הפוליסות שנשענות עליה. ‏0082 מחזיר אותה ל-invoker: היא
> מפסיקה לשכפל את `events_select` ומתחילה לשאול אותה, ולכן היא לא יכולה עוד
> לסטות ממנה.

**מי שרואה את המשימה רואה של מי היא.** שם הלקוח *במערכת* הוסתר מעובד השטח בלי
החלטה — הוא מגיע מטבלה שהמפתח לפתיחתה, `customers.view`, הוא מפתח מודול שלם
(פרטי קשר, תמחור, שדות טופס), ו-`work_board_view` הוא `security_invoker`.
‏0079 מצר אותו: **הזהות בלבד** — שם וצבע — נגלית דרך `app.customer_identities`,
view בסכמה שאינה חשופה ב-PostgREST, שה-view של הלוח מצטרף אליו במקום ל-
`customers`. השורה עצמה כבר סוננה ב-`tasks_select`, ולכן "של מי המשימה" אינו
מידע נוסף; הרחבה של `customers_select` לעומת זאת הייתה פותחת גם את
`contact_phone`. ‏`shift_task_breakdown` כבר עשה בדיוק את זה מאז 0034, ולכן
הכלל אינו חדש — הוא רק חדל להיות מקומי.

**אדם אחד יכול להיות גם עובד שעתי שלנו וגם קבלן שמביא סגל.** מה שמנע את זה
לא היה הסכימה — `profiles_contractor_kind` הוא גרירה חד-כיוונית ולא בלעדיות,
ופרופיל `staff` תמיד היה רשאי לשאת `contractor_id` — אלא שלוש שורות ששאלו
`v_kind = 'contractor_user'` במקום לשאול אם יש למשתמש קבלן. ‏0075 מחליף את
השאלה, ומוסיף תפקיד `staff_contractor` עם `user_kind` **ריק**: תפקיד בלי סוג
עובר את המסנן של `app.my_role_ids()` לכל אחד, ושכבת התפקידים היא `bool_or`
ולכן הוא רק מוסיף. סוג המשתמש חוזר לתאר איפה החשבון נולד, לא מה מותר לו.

> תפקיד שמוצמד למשתמש מסוג לא תואם נבלע בשקט ב-`app.my_role_ids()` — הוא
> מסומן במסך ואינו מעניק דבר. מסך ההרשאות מציג אותו עכשיו כ"אינו בתוקף" עם
> כפתור הסרה, ושינוי סוג משתמש מנקה את מה שהפקיע.

- קבלן **אינו יכול** לשנות מיקום/זמן/לקוח/כמות — משטח הכתיבה היחיד שלו הוא
  `task_contractor_workers` (החלפת עובדים מהסגל שלו בלבד, עד הכמות שהוגדרה),
  והוא עובר ב-`contractor_assign_worker` ולא בכתיבה ישירה.
- שיבוץ מפוצל למפתח פר-תפקיד (עובד / נהג / ראש צוות / משאית), ותמחור קבלנים מופרד
  לצפייה / עריכה / סימון תשלום.
- `users.set_admin` אינו נגזר משום הרשאה אחרת — "עריכת משתמשים" אינה דרך להפוך לאדמין.
- מנהל קבלן אינו מחזיק את המפתחות ה*משרדיים* `contractors.assign_workers` ו-
  `contractors.manage_workers`. הוא החזיק אותם מאז 0011, שם הם נועדו לתאר את
  הסגל של עצמו, ו-`contractor_assign_worker` קיבל אותם כ"היקף זר" — כלומר הם
  פתחו לו לשבץ על משימה של קבלן אחר. `portal.*` נותן לו את שלו, וזה הכול.
- **קוד שגיאה מתאר מחלקה, לא סיבה.** `42501` שמור ל-`app.require` ול-RLS;
  כלל עסקי שנשא אותו הוצג למשתמש כ"אין לך הרשאה" גם כשההרשאה שלו תקינה.
  ‏`errorMessage` מעדיף עכשיו הודעה שנכתבה בגוף ה-RPC על פני התווית של הקוד.
- Audit Log על כל שינוי, Soft Delete עם סל מיחזור, התראות Realtime.
  ליומן הביקורת אין מסך — הוא נקרא דרך ה-API בלבד, מאחורי `settings.audit_log`.

**הוספת הרשאה למודול חדש** — במיגרציה:

```sql
select app.register_module('billing', 'חיוב', 'חשבוניות ותשלומים', 'Wallet', 120);
select app.register_permission('billing.view', 'billing', 'צפייה בחיוב', p_category => 'access');
select app.register_permission('billing.issue_invoice', 'billing', 'הפקת חשבונית',
       p_dangerous => true, p_implied_by => 'billing.view');
select app.register_field('invoice', 'total', 'סכום', 'billing', 'invoices', 'total',
       p_sensitive => true, p_edit_permission_key => 'billing.issue_invoice');
create trigger invoices_field_perms before update on invoices
  for each row execute function app.enforce_field_perms();
select app.rebuild_secure_view('invoices');
```

ובצד הלקוח, המסך החדש מצהיר על המפתח שלו בטבלת הנתיבים:

```tsx
{ path: '/billing', handle: { perm: PERM.BILLING_VIEW }, element: page(<BillingPage />) },
```

נתיב בלי `handle.perm` נדחה ל-`RouteGate` ולא נפתח. זו הכוונה: השאלה "מי רשאי
לפתוח את זה" נשאלת ברגע שמוסיפים נתיב, ולא נזכרים בה אחר כך.

## התראות

שלושה ערוצים: **פעמון** במערכת, **מייל**, ו**התראה למכשיר** (Web Push, בדפדפן
ובאפליקציה המותקנת). `app.notify()` — הנקודה היחידה שכל ההתראות עוברות בה —
כותב את שורת הפעמון ורושם שורת משלוח לכל ערוץ שמותר, ו-`notify-dispatch`
מנקז אותן.

### מי מקבל מה

ההכרעה יושבת כולה ב-`app.notification_enabled(profile, type, channel)`
(‏0046), ולקוח שקורא ל-`my_notification_settings()` מקבל אותה מוכנה. הסולם,
והראשון שנוגע מכריע:

1. נמען לא פעיל או מחוק ⇐ לא
2. הערוץ כבוי במערכת ⇐ לא
3. הסוג ב-`muted_types` של הערוץ ⇐ לא
4. חריג אישי שקבע מנהל (`notification_policy_overrides`)
5. מדיניות הקהל (`notification_policies`)
6. ברירת המחדל בקטלוג (`notification_types`)

המצב שמתקבל הוא אחד מארבעה, ומ-0086 כל אחד מהם מצביע על תשובה אחת: `off`
ו-`opt_in` ⇐ לא נשלח, `opt_out` ו-`forced` ⇐ נשלח. שני הזוגות נשארים כי הם
ברירות המחדל שבקטלוג ומה ששמור כבר בטבלת המדיניות.

**אין למשתמש דעה.** עד 0086 ישבה בתחתית הסולם שכבה חמישית — ההעדפה האישית
ב-`notification_preferences` — וכל עובד יכול היה לכבות לעצמו "שובצתי למשימה".
היא ירדה: שורה שנכתבה פעם אחת המשיכה להכריע לנצח, המנהל ראה במטריצה "דלוק
כברירת מחדל" והעובד לא קיבל, ושניהם צדקו. הטבלה נשארת (השורות הן תיעוד של מה
שאנשים ביקשו בעבר) ואינה נקראת עוד; `set_notification_preference` מחזירה 42501,
וה-RLS שלה נסגר למי שמנהל התראות. מה שנשאר בידי המשתמש הוא רישום *המכשיר*
ל-push — הרשאת דפדפן, לא העדפה.

הקהלים הם `admin`, `staff`, `contractor_user`, `customer_user`. שימו לב
ש-`admin` אינו `user_kind` אלא `profiles.is_admin`, והוא גובר — אחרת כל שינוי
שנועד לעובדים היה חל גם על המנהלים.

**המנהל קובע הכול** ב-`/settings` ← לשונית "התראות", מאחורי המפתח
`notifications.manage` (נגזר מ-`settings.edit`): שם נדלקים הערוצים, שם נקבעת
המדיניות לכל קהל, ושם נקבעים החריגים לאדם בודד. **המשתמש** רואה
ב-`/my/notifications` מה יגיע אליו, לקריאה בלבד — ולכן `notifications.preferences`
הוא מפתח של צפייה.

סוג התראה חדש נרשם ב-`app.register_notification_type(...)` ומופיע משם בשני
המסכים. אין רשימה מקבילה ב-TSX, ובדיקה ב-`07_notifications.sql` נכשלת אם טריגר
פולט סוג שלא נרשם.

### מייל

**הערוץ כבוי בברירת מחדל.** שדרוג לא אמור להתחיל לשלוח מיילים מעצמו. להפעלה:

```sql
update app_settings
   set value = jsonb_set(value, '{enabled}', 'true'::jsonb)
 where key = 'notifications.email';
```

באותו מפתח יושבים גם `from` (כתובת השולח) ו-`muted_types` — סוגים שלא יישלחו
במייל גם כשהערוץ דלוק, ולא משנה מה המשתמש ביקש.

### התראה למכשיר (Web Push)

**גם הוא כבוי בברירת מחדל, ובשני מקומות בלתי תלויים:** מפתח ההגדרות, וברירת
המחדל בקטלוג שהיא `opt_in`. שלושה שלבים להפעלה, פעם אחת:

```sh
# 1. זוג מפתחות VAPID
deno run -A jsr:@negrel/webpush/cmd/generate-vapid-keys > vapid.json

# 2. הסודות לפונקציה. המפתח הפרטי אינו עולה למסד לעולם.
supabase secrets set VAPID_KEYS="$(cat vapid.json)" \
                     VAPID_SUBJECT="mailto:ops@yourdomain.com"
```

```sql
-- 3. המפתח הציבורי והדלקת הערוץ. אפשר גם מהמסך, בלשונית ההתראות.
update app_settings
   set value = jsonb_build_object(
         'enabled', true,
         'vapid_public_key', '<המפתח הציבורי מתוך vapid.json>',
         'muted_types', '[]'::jsonb)
 where key = 'notifications.push';
```

המפתח **הציבורי** יושב ב-`app_settings` כי הדפדפן זקוק לו כדי להירשם, והוא
פומבי מעצם הגדרתו. המפתח **הפרטי** אינו שם ולא יהיה שם: `app_settings` פתוחה
לקריאה לכל משתמש מאומת דרך PostgREST (‏0005), ולכן כל סוד שיושב בה גלוי לכל
עובד וכל לקוח.

שלוש נקודות תפעוליות:

- **החלפת זוג המפתחות מבטלת כל מנוי קיים.** אחרי רוטציה יש להריץ
  `truncate push_subscriptions` ולבקש מכולם להפעיל מחדש מהמסך.
- **‏iOS:** ‏Web Push עובד מ-16.4, ורק כשהאפליקציה מותקנת במסך הבית. המסך
  מזהה את המצב ומסביר מה לעשות במקום להציג כפתור שאינו עושה דבר.
- **חובה HTTPS** (‏`localhost` נחשב מאובטח).

מנוי שמת (‏410/404 משירות הדחיפה) נמחק אוטומטית על ידי `notify-dispatch`, ושורות
המשלוח שלו נופלות איתו בקסקייד.

### התפעול המשותף

**משתני סביבה ל-`notify-dispatch`:** `NOTIFY_DISPATCH_SECRET` (בלעדיו הפונקציה
מסרבת ולא רצה פתוחה), `RESEND_API_KEY` למייל, ו-`VAPID_KEYS`/`VAPID_SUBJECT`
ל-push. בלי מפתח הספק המשלוח מסומן `skipped` ולא נצבר כניסיונות כושלים.

**שתי הגדרות מסד** שנקבעות פעם אחת. הן אינן ב-`app_settings` במכוון: היא קריאה
לכל משתמש מאומת דרך PostgREST, וסוד לא אמור לשבת שם.

```sql
alter database postgres set app.notify_dispatch_url =
  'https://<ref>.supabase.co/functions/v1/notify-dispatch';
alter database postgres set app.notify_dispatch_secret = '<אקראי>';
```

הניקוז נעשה בשתי דרכים, ובכוונה לא רק באחת: `pg_net` יורה מהטריגר ברגע שנרשם
משלוח, וקריאה חיצונית מתוזמנת (POST בלי גוף, עם אותו `x-dispatch-secret`)
מנקזת את כל מה שממתין — כולל מה שנכשל, עד חמישה ניסיונות. בלי השנייה תקלה
רגעית אצל ספק הדואר הייתה אובדת. אין `pg_net`? הטריגר שותק וה-outbox ממתין
לניקוז החיצוני.

הטריגר הוא `for each statement` ולא `for each row`: התראה אחת שיוצאת למייל
ולארבעה מכשירים היא חמש שורות משלוח, וברמת השורה היא הייתה יורה חמש קריאות
HTTP שכולן מנקזות ממילא את אותו תור.

**סריקת תוקף מסמכי הרכב** היא הזרוע המתוזמנת היחידה במערכת שאין לה טריגר: אין
אירוע שורה שאומר "עבר יום". `supabase secrets set FLEET_SWEEP_SECRET='<אקראי>'`,
ואז תזמון יומי של `POST` בלי גוף אל
`https://<ref>.supabase.co/functions/v1/fleet-expiry-sweep` עם הכותרת
`x-sweep-secret`. בלי הסוד הפונקציה מסרבת ואינה רצה פתוחה, כמו `notify-dispatch`.
הקריאה בטוחה לחזור על עצמה — ה-RPC רושם כל התראה שכבר יצאה ונועל נעילה מייעצת
— ולכן גם הרצה כפולה או ידנית אינה שולחת דבר פעמיים. **עד שהתזמון מוגדר,
ההתראות יוצאות רק בלחיצה על "בדיקת תוקף" במסך הרכבים;** המסך והדשבורד מחשבים
את התוקף בקריאה ואינם תלויים בסוויפ.

## הערות תפעול

- ליצירת משתמשים עם סיסמה משתמשים ב-Edge Function ‏`admin-users` (service role בצד השרת בלבד).
- Nominatim מוגבל לבקשה בשנייה — הפרוקסי דורש משתמש מחובר, מחזיק cache חסום
  ומווסת את עצמו לקצב הזה. חריגה הייתה חוסמת את כתובת ה-IP של האפליקציה כולה
  ולא רק את מי שגרם לה. לשימוש כבד מומלץ לעבור ל-Google Places דרך ה-Adapter
  (`src/lib/address.ts`).
- מומלץ להפעיל Leaked Password Protection בהגדרות ה-Auth בדשבורד של Supabase.
