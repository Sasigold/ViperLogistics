# ViperLogistics — מערכת ניהול כוח אדם להשכרת ציוד לאירועים

מערכת Web מודרנית (Multi-Tenant) לניהול עובדים, נהגים, ראשי צוות, קבלנים ושיבוצים
עבור חברת השכרת ציוד לאירועים. עברית מלאה (RTL) + Dark Mode.

## סטאק

- **Frontend:** Vite + React 19 + TypeScript, Tailwind CSS v4, TanStack Query + Virtual,
  FullCalendar v6 (חינמי), Recharts, ExcelJS, Zustand
- **Backend:** Supabase — Postgres 17 עם RLS מלא, Auth, Edge Functions, Realtime
- **כתובות:** Google Places (Text Search) דרך Edge Function פרוקסי כשהסוד `GOOGLE_MAPS_API_KEY` מוגדר, עם נסיגה אוטומטית ל-Photon/Nominatim (OSM) בלעדיו

### ייבוא אירועים ומשימות מאקסל

הקובץ הוא **שלושה גיליונות**: "אירועים", "משימות" ו"הסבר". גיליון המשימות מקושר
לאירועים דרך עמודת "מזהה שורה" — מזהה חופשי שחי רק בתוך הקובץ ואינו נשמר במסד;
זו הדרך לתאר כמה משימות לאירוע אחד בלי לכפול את שורת האירוע. גיליון "הסבר" נוצר
בקובץ הדוגמה בלבד, ונושא את הערכים החוקיים כפי שהם *בזמן ההורדה*.

המיפוי הוא **לפי טקסט הכותרת ולא לפי מיקום**, ולכן עמודה חדשה אינה שוברת קובץ
שכבר נמצא אצל המשתמשים, ואפשר גם למחוק עמודות שאין בהן צורך. קובץ בן גיליון אחד
עדיין נקלט — אז נוצרים האירועים בלי משימות מפורטות.

**גיליון "אירועים"**

| עמודה | חובה | הערות |
|---|---|---|
| מזהה שורה | לא | לקישור לגיליון המשימות בלבד. באירוע יחיד אפשר להשאיר ריק |
| שם לקוח במערכת | כן | חייב להיות זהה לשם הלקוח במערכת; נפתר בדפדפן, לפני שנשלחת שורה |
| שם לקוח האירוע, מספר אירוע, מיקום, הערות למיקום, נפח במטר, כמות משאיות, איש קשר, טלפון איש קשר, הערות | לא | |
| תאריך אירוע | כן | `YYYY-MM-DD`; מתקבל גם `DD/MM/YYYY` |
| ללא חניה / סבלות / איסוף מספק | לא | "כן" או "לא". תא ריק אינו "לא" אלא "לא נכתב" |
| ספקים | לא | שמות מופרדים בפסיק. הספק חייב להיות מוגדר **אצל אותו לקוח** |
| שדות מותאמים של הלקוח | לפי ההגדרה | עמודה לכל שדה, לפי `form_fields` (0053). שדה שהוגדר "חובה" נבדק בשרת |

**גיליון "משימות"**

| עמודה | חובה | הערות |
|---|---|---|
| מזהה שורה (של האירוע) | כן | אלא אם בקובץ אירוע אחד בלבד |
| סוג משימה | כן | לפי השם או לפי ה-code האנגלי (`setup`/`teardown`) |
| כותרת, תאריך משימה, יציאה מהמחסן, תחילה בשטח, כמות שעות, כמות עובדים, משאית, מיקום המשימה, הערות | לא | תאריך ריק נלקח מתאריך האירוע |
| אופן ביצוע | לא | חייב להיות בחיתוך: פעיל ∩ מותר לסוג המשימה ∩ מותר ללקוח |
| מחסן יציאה | לא | לפי שם המחסן |
| זמן נסיעה בכיוון אחד / נדרש ראש צוות | לא | דריסות של מנוע התמחור. NULL = לפי אזור הגיאופנס והמחשבון |
| מחיר ללקוח | לא | מה שגובים. נכנס **נעול** (`is_manual`) ואינו נדרס בחישוב אוטומטי |
| קבלן | לא | לפי שם הקבלן; פותח שורת `task_contractor_terms` על מחיר ברירת המחדל שלו |
| מחיר לקבלן | לא | מה שמשלמים לו. מחייב שגם עמודת "קבלן" מלאה באותה שורה |

**מה שהייבוא עושה בשרת** (`bulk_import_events` → `create_event` +
`app.apply_import_tasks`):

- **שמות נפתרים בשרת** — סוג משימה, אופן ביצוע, מחסן, קבלן וספק. הלקוח הוא
  היוצא מן הכלל: הרשימה ממילא בזיכרון הדפדפן, וההודעה על שם שגוי צריכה להיאמר
  לפני שנשלחת שורה אחת.
- **הקמה ופירוק אינן מוכפלות.** הן נוצרות לכל אירוע בטריגר, ושורה בגיליון
  המשימות *ממלאת* את הקיימת. שורה שנייה מאותו סוג באותו קובץ היא משימה נוספת
  אמיתית ולכן כן נוצרת.
- **שורה שנפסלה מתגלגלת כולה** — האירוע והמשימות שלו אינם נוצרים, והשגיאה
  מדווחת עם מספר השורה. אין אירוע חצי-מיובא.
- **עמודות הכסף דורשות מפתח משלהן, ומראש:** `pricing.edit` (מחיר ללקוח וזמן
  נסיעה), `tasks.delegate` (קבלן), `contractors.edit_pricing` (מחיר לקבלן).
  הבדיקה היא פר-קובץ ולא פר-שורה: קובץ שנושא מפתח שאין למעלה אותו נדחה כולו,
  ולא מיובא חלקית. שדות התכנון עצמם אינם דורשים את מפתחות השדה שלהם — הכתיבה
  רצה תחת `app.system_write`, אחרת "מותר לייבא אירועים" היה גורר בשקט את
  `tasks.reschedule` ואת כל השאר.
- **סטטוס אירוע וסטטוס משימה אינם מיובאים.** לשניהם מחזור חיים משלהם (0036,
  0063) עם מעברים מותרים והרשאת פרסום, ותא באקסל אינו הדרך לעקוף אותו.

הייצוא כותב את אותן עמודות בדיוק, ולכן קובץ שיצא יכול לחזור פנימה. מה שהמייבא
אינו רשאי לראות יוצא ריק — `task_pricing` ו-`task_contractor_terms` מסוננות
ב-RLS, ופרטי איש הקשר יושבים ב-`event_contacts` מאותה סיבה.

חוזה הקובץ עצמו — הכותרות, הנרמול והבנייה של התבנית ושל קובץ הדוגמה — יושב ב-
`src/features/importExport/eventsWorkbook.ts` ונבדק בלי ExcelJS; הצד השרתי ב-
`0052_import_event_tasks.sql` וב-`0076_import_events_full_fields.sql`.

### מפרט האירוע

לכל אירוע יש **מפרט** — המסמך שהלקוח שולח. בכותרת דף האירוע יושב כפתור "מפרט"
עם מונה הגרסאות, ואותו כפתור יושב גם בכרטיס המשימה במגירת הלו״ז — מנהל קבלן
ועובד קבלן אינם פותחים את `/events/:id`, והמשימה היא המקום שבו הם פוגשים את
האירוע. שניהם פותחים מסך אחד בשני מצבים:

- **צפייה** — הגרסה הפעילה מוטמעת במסך: PDF ב-`<object>`, תמונה כתמונה, וקישור
  חיצוני ב-iframe עם מוצא "פתיחה בלשונית חדשה" (אתרים רבים חוסמים הטמעה).
  HEIC מקבל כרטיס הורדה: אין דפדפן שמרנדר אותו, וריבוע שבור גרוע מהודעה.
- **השוואה** — שתי גרסאות זו לצד זו, החדשה מימין והישנה משמאל, כל אחת עם בורר
  גרסה משלה. בטלפון הן נערמות אנכית. **הבורר בין שני המצבים מוצג למנהל מערכת
  ולמשתמשי לקוח בלבד**: הצפייה היא המסמך שצריך לבצע ולכן היא של כולם (0102),
  ואילו "מה השתנה מול מה שסוכם" הוא דיון מול הלקוח. זו שאלה על *מי* ולא על
  מפתח — שתי הגרסאות גלויות לכל מי שרואה את המפרט ממילא, ומה שנחסך הוא כלי
  שאין לו קהל שלישי.

מתחת לשתיהן יושבת היסטוריית הגרסאות: מי העלה, מתי, ומה שם הקובץ.

**הגרסה הפעילה נגזרת ואינה מסומנת** — היא ה-`version` הגבוה ביותר שאינו מוסר.
אין דגל `is_current` שיכול לסתור את המספור, והסרת הגרסה העליונה מחזירה את
הקודמת לתפקיד בלי שום כתיבה נוספת. המספור עצמו נקבע בשרת תחת נעילה פר-אירוע,
ולכן שתי העלאות במקביל אינן יכולות לקבל אותו מספר. מספר של גרסה שהוסרה אינו
חוזר לשימוש.

הקבצים יושבים ב-bucket **פרטי** בשם `event-specs`, בנתיב `<event_id>/<uuid>.<ext>`.
זה החוזה: הפוליסה על `storage.objects` קוראת את מזהה האירוע מהתיקייה הראשונה,
ולכן ההרשאה על הקובץ היא בדיוק ההרשאה על האירוע — בלי טבלת הצטלבות ובלי סנכרון.
אין URL ציבורי; כל תצוגה עוברת ב-`createSignedUrl` לרבע שעה.

**צפייה במפרט היא חלק מצפייה באירוע** (0102). ‏`events.specs_view` פתוח בברירת
המחדל של המרשם לכל שלושת סוגי המשתמש, ופוליסת ה-select שואלת שתי שאלות בלבד:
האם הקורא מחזיק את המפתח, והאם האירוע נפתח לו. ה-`exists` על `events` הוא מה
שמחיל את כל היקפי הראייה, ולכן עובד שרואה רק את האירוע ששובץ אליו רואה רק את
המפרט שלו. עד 0102 היו שתי שכבות שסגרו את זה: הפוליסה דרשה `user_kind = 'staff'`
(ולכן לקוח וקבלן קיבלו רשימה ריקה), ו-0079/0080 כתבו לשלושת תפקידי השטח דחייה
גורפת על כל מודול האירועים, שהמפרט נלכד בה. מי שנוסע לאירוע הוא בדיוק מי שצריך
לקרוא את המסמך, וההכרעה התהפכה. המפתח נשאר קיים — אפשר עדיין לשלול אותו מאדם
או מתפקיד, וזו רק חדלה להיות ברירת המחדל.

**הלקוח מעלה, המשרד מסיר** (0113). עד 0113 ענה `events.specs_manage` על שתי
שאלות בקול אחד — מי מעלה גרסה ומי מוריד אחת — ושתי התשובות היו "המשרד". ‏0113
מפריד ביניהן, מפני שהמפרט נולד אצל הלקוח: הוא זה שיודע מה צריך לקרות באולם,
והדרך שבה המסמך הגיע עד היום הייתה וואטסאפ לרכז שיעלה אותו בשמו.

- ‏**`events.specs_upload`** — מפתח חדש, נגזר מ-`events.specs_manage` (ולכן איש
  צוות שמנהל מפרטים ממשיך להעלות בלי שורה חדשה), ופתוח למשתמש לקוח בברירת
  המחדל של סוג המשתמש. לקבלן הוא סגור באותה שכבה: עובד הקבלן מבצע את מה שכתוב
  במפרט ואינו צד לתוכנו. הפוליסה על ה-INSERT והשער על הדלי נשענים עליו.
- ‏**`events.specs_manage`** — מכאן ואילך בעיקר ההסרה, ונשאר של הצוות. לקוח
  שהעלה גרסה שגויה מעלה אחריה גרסה נכונה — לשם כך המספור קיים — ואינו מוחק
  מההיסטוריה של האירוע מה שכבר נראה.

עד 0102 הנתיב הזה היה פתוח ובלתי נראה: לקוח יכול היה להוסיף גרסת **קישור**
(הדלי חוסם קובץ, לא שורה), ואיש — גם לא הוא עצמו — לא ראה אותה, כי ה-select
היה סגור.

העלאה היא INSERT
תחת RLS; **הסרה עוברת ב-RPC** ‏(`remove_event_spec`), כי פוסטגרס מחילה את פוליסת
ה-select גם על השורה החדשה ב-UPDATE, ולכן שורה אינה יכולה להעלים את עצמה מעיני
מי שמחק אותה — אותה סיבה בדיוק ש-`soft_delete` הוא `security definer`. הקובץ
נשאר בדלי: ההיסטוריה יורדת מהמסך ואינה נמחקת. כל העלאה, הסרה ושחזור נרשמים
ביומן הפעילות של האירוע.

הסכמה ב-`0077_event_specs.sql` (עם הידוקי ה-linter ב-0078, פתיחת הצפייה ב-
`0102_spec_travels_with_the_event.sql` ופיצול ההעלאה ב-
`0113_customer_spec_and_price_addons.sql`), החבילה ב-`supabase/tests/16_event_specs.sql`,
הלוגיקה הטהורה ב-`src/features/events/specs.ts` (נבדקת ב-`specs.test.ts`) והמסך
ב-`EventSpecsModal.tsx` — שנפתח מדף האירוע ומ-`TaskDrawer.tsx`.

### ניהול רכבים

`trucks` הייתה מאז 0002 טבלת עזר של שם ומספר רישוי, וכל תפקידה היה להיות ערך
ב-dropdown של שיבוץ. ‏0089 מוסיף לצדה את **הרכב כנכס**: `vehicles`, עם מסמכים,
תאריכי פקיעה, בעלות, נהג וכרטיס דלק.

**שתי הטבלאות נשארות שתיים, והרכב הוא מקור האמת.** `vehicles.truck_id` הוא קישור
אופציונלי ו-1:1 לשורת השיגור, וטריגר דוחף מהרכב את מספר הרישוי והשם אל המשאית
המקושרת — כיוון אחד בלבד. כך כל מה שנשען על `trucks` (‏`tasks.truck_ids`,
`task_assignments`, `work_board_view`, `assignment_conflicts`, סקופ ההרשאות)
ממשיך לעבוד בלי לדעת שהמודול קיים, והכפילות אינה יכולה לסטות בשקט. רכב בלי
קישור פשוט אינו ניתן לשיבוץ, ובכרטיס שלו יושב כפתור "יצירת משאית מהרכב".

**סוגי המסמכים הם קטלוג, לא רשימה בקוד.** `vehicle_document_kinds` נזרעת עם טסט,
רישיון רכב, ביטוח חובה/מקיף/צד ג׳, אישור גז, רישיון מנוף, טכוגרף, רישיון מוביל
ואגרת רישוי, ונערכת ב-`/settings` → "סוגי מסמכי רכב". לכל סוג יש `alert_days`
משלו — על ביטוח חובה מתריעים חודש מראש כי החידוש לוקח יום, ועל רישיון מנוף
שלושה חודשים כי הוא דורש בדיקה מתוזמנת — ו-`is_required`, שממנו נגזרת ספירת
"מסמכי חובה חסרים".

**מצב התוקף מחושב בשרת ולא בלקוח.** ה-view ‏`vehicle_document_status` מחזיר
`valid | expiring | expired | no_expiry` מול הסף של הסוג, והוא מה שהמסך,
הדשבורד והסוויפ קוראים — שלושתם אינם יכולים לחלוק זה על זה.

הקבצים יושבים ב-bucket **פרטי** בשם `vehicle-docs`, בנתיב `<vehicle_id>/<uuid>.<ext>`,
בדיוק בחוזה של `event-specs`: הפוליסה קוראת את מזהה הרכב מהתיקייה הראשונה,
ולכן ההרשאה על הקובץ היא ההרשאה על הרכב. אין URL ציבורי, וההסרה עוברת ב-RPC
‏(`remove_vehicle_document`) מאותה סיבה שכתובה למעלה על המפרט.

**הנהג הוא היסטוריה, לא עמודה.** `vehicle_driver_assignments` מחזיקה טווחי
תאריכים עם הצמדה פתוחה אחת לכל רכב; `assign_vehicle_driver` סוגר את הקודמת
ופותח את החדשה באותה טרנזקציה. `vehicles.current_driver_id` ו-`current_driver_name`
מדונרמלים כדי שהרשימה תיקרא בשאילתה אחת, ונכתבים **רק** מהטריגר — כתיבה ישירה
עליהם נדחית, אחרת העמודה הנגזרת הופכת למקור אמת שני.

**ה-PIN של כרטיס הדלק אינו נקרא בשאילתה של מי שאין לו את המפתח.** הכרטיס יושב
בטבלה נפרדת, `vehicle_fuel_cards`, שהקריאה ממנה דורשת `fleet.view_fuel_card`
והכתיבה `fleet.manage_fuel_card`. זו אינה הקפדה עודפת אלא ההבדל בין הפרדה
אמיתית לבין הסתרה בלקוח: התקדים ברפו לשדה רגיש הוא `field_registry`, שחוסם
*כתיבה* אך אינו מסתיר את הערך בקריאה — מי שמחזיק `fleet.view` היה מקבל את הקוד
ב-PostgREST בלי לפתוח את המסך. ‏RLS היא row-level, ולכן השורה הרגישה חייבת להיות
שורה משלה. מאותה סיבה הביקורת על הטבלה הזו אינה `app.audit()` הגנרית אלא טריגר
שמחליף את `pin_code` ואת `card_number` ב-`***`: מי שינה ומתי כן נרשם, אבל
`audit_log` נקרא במפתח אחר לגמרי, והוא לא ייהפך לדלת האחורית.

**התראות פקיעה.** שני סוגים בקטלוג — `vehicle_document_expiring` ו-
`vehicle_document_expired` — כי "עוד 30 יום" הוא מידע ו"פג" הוא אירוע, ומנהל
צריך יכולת לכבות את הראשון בלי לכבות את השני. `fleet_expiry_sweep()` עובר על
המסמכים החיים מול שלושה ספים (הסף של הסוג, 7 ימים, ויום הפקיעה) ושולח דרך
`app.notify` לכל מי שמחזיק `fleet.view` ולנהג הקבוע של הרכב.

שתי תכונות שלו ראויות לציון: הוא **אידמפוטנטי** — כל (מסמך, תאריך פקיעה, סף)
שנשלח נרשם, ותאריך הפקיעה הוא חלק מהמפתח, ולכן חידוש המסמך דורך את ההתראה
מחדש מעצמו בלי איפוס ידני; והוא שולח **התראה אחת לכל מסמך בכל הרצה** גם
כששלושה ספים בשלו יחד (מסמך שנרשם כשהוא כבר פג), כי שלוש שורות פעמון על אותו
ביטוח הן בדיוק מה שגורם לאנשים לכבות התראות. הספים הנבלעים נרשמים ומוחזרים
כ-`suppressed`.

אין `pg_cron` ברפו ואין אירוע שורה שאומר "עבר יום", ולכן ההרצה היא חיצונית:
`supabase/functions/fleet-expiry-sweep` (ראו "התפעול המשותף"). מנהל צי יכול גם
ללחוץ "בדיקת תוקף" במסך — הסוויפ אידמפוטנטי, ולחיצה חוזרת אינה עולה דבר.

הסכמה ב-`0089_vehicles.sql`, סקשני הדשבורד ב-`0090_fleet_dashboard_sections.sql`,
החבילה ב-`supabase/tests/19_vehicles.sql`, הלוגיקה הטהורה ב-
`src/features/vehicles/vehicles.ts` (נבדקת ב-`vehicles.test.ts`) והמסכים ב-
`src/features/vehicles/`.

### יומן פעילות של אירוע

בדף האירוע יושב יומן שמתעד שני דברים באותו ציר זמן: **שינויים** ו**מלל חופשי**.

- שינוי בשדה מעקב באירוע (כמות משאיות, תאריך, סטטוס, לקוח, מיקום, נפח, הערות, תוספות,
  איש קשר, ספקים) נרשם אוטומטית בטריגר — עם הערך הקודם, הערך החדש, מי שינה ומתי.
  הערכים נשמרים כפי שקוראים אותם: מזהה סטטוס הופך לשם הסטטוס, בוליאני ל"כן/לא", תאריך ל-DD/MM/YYYY.
- **וגם שדות המשימות** (0112): תאריך, שעת התחלה בשטח ובמחסן, כמות שעות, כמות
  עובדים, אופן ביצוע וכותרת נרשמים כשורות שינוי עם קידומת שם המשימה
  ("הקמה — שעת התחלה בשטח"). משימה שנולדה ומולאה בשמירה אחת מדברת פעם אחת —
  "נוספה משימה" — ולא בנוסף מטח שינויים מול ברירות המחדל. שינויי סטטוס משימה
  (פרסום/הורדה) וכספים (מחיר לקבלן/ללקוח, הכנסות) אינם ביומן במכוון: לראשונים
  יש התראות משלהם, והיומן גלוי גם לראשי צוות שסכומים אינם עניינם.
- **בורר "הכול / הערות בלבד"** בכותרת היומן מסתיר את הודעות המערכת ומשאיר רק
  את המלל החופשי; הבחירה נשמרת פר-דפדפן. הוא מוצג רק למי שרואה רשומות מערכת —
  לשאר אין בו במה לבחור.
- מי שמחזיק `events.activity_note` יכול להוסיף רשומת מלל חופשי — הסיבה שמאחורי השינוי,
  שיחה עם הלקוח, כל דבר ששווה לזכור.
- היומן לקריאה בלבד אחרי הכתיבה: אין פוליסת UPDATE, ומחיקה שמורה לאדמין.
  שינויים שנעשו בשמירה אחת מקובצים לרשומה אחת בתצוגה.
- `events.activity_log` נגזר מ-`events.view` ו-`events.activity_note` מ-`events.edit`,
  ולכן מי שכבר רואה או עורך אירועים מקבל את היומן בלי הגדרה נוספת.
- **והשטח רואה הערות, ורק אותן** (0129). ‏0122 שאלה מי רשאי לקרוא מלל חופשי
  וענתה "המשרד והלקוח"; הדיווח מהשטח הפך את השאלה. ההערה נכתבת *אל* מי שנוסע
  לאירוע — "הלקוח ביקש להתחיל שעה מאוחר יותר", "הכניסה מאחור" — ולכן היא בדיוק
  מה שהוא צריך. רשומות המערכת, לעומת זאת, הן ההיסטוריה התפעולית: מי שינה איזה
  שדה וממה למה, דיון של המשרד מול הלקוח. הן שדורשות מעכשיו מפתח משלהן,
  `events.activity_system_view`, שנגזר מ-`events.edit` ונכתב במפורש לכל תפקיד
  משרדי (גם "צופה", שאין לו `events.edit`) — ולשלושת תפקידי השטח ולקהל הקבלן
  נכתבת עליו דחייה. באותה מיגרציה נפתחים לשלושת תפקידי השטח `events.activity_log`
  ו-`events.activity_note`, שהיו לכודים בדחייה הגורפת של 0079/0080: הם רואים
  הערות **וגם כותבים אותן**. ‏`events.activity_note_view` (0122) ירד מהמרשם
  הפעיל; השורות שנכתבו עליו נשארות ואינן נקראות עוד.
- **והקבלן כותב בו** (0103). מנהל קבלן מקבל את שני המפתחות במפורש, ואיתם
  `events.view` — שנסגר לו ב-0072 כדי לחסום את הקטלוג ב-`/events`, לפני ש-0082
  הוציא את הקטלוג למפתח משלו. הזרוע שלו ב-`events_select` לא זזה: הוא ממשיך
  לראות רק אירועים שיש בהם משימה שהואצלה לו, ומה שנפתח הוא הדלת אליהם —
  היומן והמפרט. הקטלוג (`events.list`) והייצוא (`events.export`), ששניהם
  נגזרים מ-`events.view`, נסגרים לו במפורש כדי שלא יידלקו בהיסק.

### הלו״ז: התא, הפאנל והכרטיס

הלו״ז מוצג **מוחלף**: הימים רצים לרוחב, ושדות המשימה לאורך — עמודה לכל משימה,
שורה לכל שדה. שלוש הכרעות מרכיבות את מה שקורה בתוך התא.

**מה שנקרא, ומה שנחתך.** רוחב תא הוא שתי אצבעות, ולכן טקסט שאינו נכנס נושא
איתו את המחרוזת המלאה: ריחוף קורא אותה בעכבר, הקשה פותחת אותה בטלפון. שתי
שורות אינן נחתכות כך: שורת ה**צוות** נמדדת לפי הצוות הגדול ביותר שעל הלוח —
שורה לכל אדם, עם תקרה — ושורת ה**הערות** לפי ההערה הארוכה ביותר, עד שש שורות
(0108). הערה היא השדה היחיד בלוח שהוא פרוזה, ושתי שורות קבועות היו מספיק
ל"לקחת מפתחות" ולא להערה שמסבירה איך נכנסים לחניון — וזו בדיוק ההערה שנכתבה
כדי להיקרא. מה שחורג גם משם ממשיך להיקרא בבועה. אורך ההערה נאמד מרוחב העמודה
ומגודל הגופן ולא נמדד: הלוח מוירטואל, והעמודה שההערה הארוכה יושבת בה אינה
בהכרח מצוירת. ‏`whitespace-pre-wrap` מכבד ירידות שורה שנכתבו, והעורך ה-inline
הוא `textarea` ולא `input` — `input` היה מוחק אותן בשקט בכל עריכה.

**תא הוא משטח קריאה קודם כול.** לחיצה אחת גוללת או פותחת בועה; **לחיצה כפולה**
היא העריכה. היא נספרת מ-`click` ולא נלקחת מ-`dblclick`, כי טלפון אינו שולח
`dblclick` — הדפדפן קורא שתי הקשות מהירות כמחוות זום משלו.

**ומה שנפתח תלוי בשאלה של התא** (0108). רוב התאים נפתחים לעורך במקום או לבורר
קטן. שלושה תאים — **צוות**, **ראש צוות** ו**קבלן** — נפתחים ל**פאנל ממוקד**,
מפני שהשאלה שלהם גדולה מתפריט: מי משובץ היא רק מחציתה, והמחצית השנייה היא
*מאיפה* — מי יוצא מהמחסן ומי מגיע לשטח, ומי מהנהגים נוסע באיזו משאית. השתיים
האלה קובעות את שעת ההתחלה במשמרת ואת המיקום שמולו נמדדת החתמת הכניסה, ומעולם
לא נכנסו לבורר ברוחב תא. אותו דבר בהאצלה: התא ידע לומר "לאיזה קבלן", ואילו כמה
עובדים הוא מביא, מאיזה אתר, באיזה תעריף ומי מהסגל שלו יוצא — כל אלה חיו רק
בכרטיס המשימה.

הפאנלים אינם קיצור דרך לכרטיס: הם **אותם רכיבים בדיוק** שהכרטיס מרכיב
(`src/features/tasks/taskPanels.tsx`), ולכן אין שני מקומות שאפשר להם להיפרד.
כמו בכרטיס, כל מה שבהם נשמר **מיד** ובלי כפתור שמירה — `task_assignments`,
`task_contractor_terms` ו-`task_contractor_workers` אינן עמודות של המשימה. בכרטיס
הנייד, שאין בו תאים, אותם שני פאנלים נפתחים משני כפתורים על הכרטיס עצמו.

**ומה שהלקוח רואה בו נקבע פר-לקוח** (0109). עד כאן התשובה לשאלה "מה הלקוח
רואה בלו״ז ומה הוא עורך בו" נגזרה מהמפתחות של התפקיד שלו — כלומר הייתה זהה
לכל הלקוחות, ולא הייתה שאלה שאפשר לענות עליה פר-לקוח בכלל. מעכשיו זו טבלה,
בדיוק כמו שדות טופס האירוע (`customer_form_fields`, 0002/0015): `board_fields`
הוא הקטלוג, `customer_board_fields` הוא מה שנקבע ללקוח מסוים, ולכל שדה שלוש
מדרגות — **מוסתר**, **נראה**, **עריכה**.

שלוש ולא שתיים, וזו כל ההבחנה: "נראה" אינו "ניתן לעריכה". השדות שמזיזים כסף —
משך, כמות עובדים, אופן ביצוע — מריצים מחדש את `app.recalc_task_price`, ולכן
לקוח שערך אותם ערך בפועל את מה שהוא ישלם. הכתיבה בקונפיגורציה היא של **מנהל
המערכת בלבד**, ואין לה מפתח במרשם בכוונה: מפתח אפשר להעניק, ו"רק מנהל מערכת"
נאמר כדי שלא יהיה אפשר.

והאכיפה אינה במסך. ‏`app.enforce_customer_board_edit` הוא אח לטריגר הגנרי של
0012 — אותו מבנה בדיוק, קטלוג אחר — והוא דוחה כתיבה של לקוח לעמודה שהשדה שלה
אינו `editable`, גם כשהמפתח בידו. הלקוח מקבל את הקונפיגורציה ב-
`get_my_permissions` לצד `form_config`, ולכן המסך מצייר בדיוק את מה שהשרת
יקבל — ותא שנראה פתוח ונדחה בשמירה גרוע מתא שנראה נעול.

**ולמשאיות יש רשימה פר-לקוח** (0116). ‏`trucks` היא קטלוג אחד גלובלי מאז 0002,
והבורר בלו״ז הציע את כולו: הלקוח חיפש בתוך צי של חברה שלמה כדי למצוא את
השתיים שהוא מכיר, ויכול היה לבחור אחת שאינה שלו כלל. ‏`customer_trucks` היא
קטלוג פר-לקוח, כמו `customer_execution_methods` — **המשרד קובע אותו והלקוח
משבץ מתוכו**, מפני שהמשאית היא נכס של החברה (רישיון, ביטוח ונהג קבוע, 0089)
ומי שפותח אותה בקטלוג הוא גם מי שיודע של מי היא.

**רשימה ריקה אינה "אין משאיות" אלא "אין הגבלה"** — אותה סמנטיקה של
`app.board_config` הריקה של איש צוות — ולכן התכונה עלתה בלי שאף לקוח איבד
משאית. האכיפה ב-`app.enforce_customer_trucks` ועל `customer_user` בלבד:
אצל המשרד הבורר **מסונן** ולא נעול, כי משאית מחוץ לרשימה בשעת לחץ היא החלטה
תפעולית ולא עקיפה של כלל. שם הטריגר נושא משקל — `tasks_z_customer_trucks`
ממיין אחרון, אחרי `tasks_truck_sync` (0035) שגוזר את `truck_ids` מ-`truck_id`,
ולכן הבדיקה רואה את המערך הסופי ולא את מה שנשלח לפני נרמול.

**ופרסום הוא מתג ולא דלת חד-כיוונית** (0117). ‏0066 שמרה על הכיוון האחד: מעבר
ל"משובץ" דורש `tasks.publish`. הכיוון ההפוך נשאר פתוח, ומי שאינו רשאי לפרסם
יכול היה להוריד משימה מפרסום, לשלוח `task_unpublished` לכל הצוות ולהעלים
משמרת מ-`/my/schedule` של מי שכבר תכנן את יומו לפיה. מעכשיו אותו מפתח שומר על
שני הקצוות — **לכל מי שאינו מחזיק אותו ולא ללקוח בלבד**, כי אי-סימטריה שבה
אפשר להוריד מפרסום אך לא להעלות נקראת כבאג ברגע שנתקלים בה.

וזה מה שפותח ללקוח את שורת הסטטוס: ‏`customer_manager` מחזיק
`tasks.change_status` מאז 0066 ונדחה מ-`tasks.publish` בשתי שכבות, ולכן ברגע
שהמשרד פותח לו את שדה `status` לעריכה הוא מזיז בין "טיוטה" ל"מתוכנן" לשני
הכיוונים ואינו נוגע ב"משובץ" — לא כדי להיכנס אליו ולא כדי לצאת ממנו. במסך,
‏`statusOptions` היא פונקציה אחת שהתא והכרטיס חולקים, ומשימה שכבר פורסמה
מוצגת לו נעולה: בורר שכל בחירה בו נדחית גרוע מבורר סגור.

> **ברירת המחדל היא "רואה, אינו עורך"**, ללקוחות קיימים וחדשים כאחד. זו הכרעה
> ולא נוחות: עד 0109 הלוח של הלקוח היה פתוח לעריכה בכל שדה שהמפתחות שלו
> התירו, ומעכשיו כל שדה נפתח במפורש. שדה בלי `column_name` (צוות, קבלן, מספר
> אירוע) אינו נכתב מהלוח ממילא, ולכן המסך מציע עליו מוסתר/נראה בלבד — וכך גם
> `onsite_end_time`, שנגזר בטריגר מהשעה ומהמשך ולכן זז גם בעריכה שלא נגעה בו.

**ולכל לקוח יש אופן ביצוע ברירת מחדל** (0111). ‏`customer_execution_methods`
ידעה *אילו* אופנים מותרים ללקוח ולא איזה מהם הרגיל, ולכן כל משימה נולדה ריקה
ומישהו מילא את אותו ערך בכל פעם מחדש. הדגל יושב על שורת ההרשאה ולא כעמודה על
`customers`, משתי סיבות: ברירת המחדל חייבת להיות אחד מהאופנים שהותרו — וה-FK
הזה כבר בשורה — וכשמסירים ללקוח אופן, הדגל יורד איתו במקום להישאר מצביע על מה
שכבר אינו מותר. אחד לכל לקוח, לפי אינדקס.

המילוי הוא **טריגר** ולא שורה ב-RPC אחד: משימה נוצרת מטופס האירוע, מהמשימות
האוטומטיות, מהייבוא, מהלו״ז ומכרטיס המשימה — וברירת מחדל שמכירה רק חלק
מהדלתות אינה ברירת מחדל. הוא רץ `before insert`, כלומר לפני שמנוע המחיר
(שהוא `after`) קורא את השורה, ולכן המחיר הראשון כבר מחושב לפי האופן הנכון;
והוא שומר על החיתוך המוכר — אופן שאינו פעיל או שאינו מותר לסוג המשימה אינו
נבחר. בטופס האירוע הבורר מוקדם בערך הזה, וזו הקדמה של מה שיקרה ממילא.

**ומ-0130 הן שלוש: הקמה, פירוק, וכללית לשאר.** בשטח ההקמה והפירוק כמעט אף
פעם אינן אותו אופן — "צוות לשטח" מקימים ו"איסוף" מפרקים — ולכן ברירת מחדל אחת
נכונה לכל היותר לחצי מהמשימות, ומישהו תיקן את השנייה ידנית בכל אירוע. שתי
עמודות נוספות על אותה שורה (`is_default_setup`, `is_default_teardown`), כל
אחת עם אינדקס יחידות משלה; `is_default` **נשאר** ומשמעותו מצטמצמת לברירת
המחדל של סוגי המשימות שאינם הקמה ופירוק (סידור, איסוף, הובלה נוספת) — בלעדיו
הפיצול היה מותיר אותם בלי ברירת מחדל כלל. הטריגר בוחר לפי `task_types.code`,
ובכרטיס הלקוח הרשימה ממילא מקובצת לשלוש קבוצות, ולכל אחת יש עכשיו כוכב משלה.

**ואירוע יכול להיות מאושר לביצוע** (0109). סימון שמנהל המערכת נותן, והלקוח
קורא: בלוח השנה שלו הוא ווי לצד שם האירוע — ווי ולא צבע, מפני שהצבע של הצ׳יפ
שייך לסטטוס — ובדף האירוע הוא תג. ‏`approved_at` ולא בוליאני: "מתי אושר" ו"מי
אישר" הן השאלות שנשאלות אחרי "האם", ובוליאני מאבד את שתיהן. הכתיבה עוברת ב-
`set_event_approved` בלבד, וטריגר חוסם כתיבה ישירה לשתי העמודות — אחרת כל מי
שמחזיק `events.edit` (ובכללם מנהל הלקוח) היה מאשר לעצמו את האירוע שלו. היומן
מדווח עליו כמו על כל שינוי אחר, במילה ולא בחותמת זמן.

**והאישור יורד כשמה שאושר משתנה** (0115). עד כאן הסימון שרד כל עריכה: הלקוח
הזיז את שעת ההקמה בשעתיים, והתג נשאר במקומו — כלומר המשרד אישר מפרט אחד
והשטח קרא אישור על מפרט אחר. מעכשיו **עריכה של הלקוח מבטלת אותו**; של המשרד
לא, מפני שהמשרד הוא מי שמאשר, ואילו כל שמירה שלו הייתה מורידה את האישור הוא
היה הופך לצעד שאי אפשר להשלים.

הגלאי אינו רשימת עמודות שנייה אלא **אותו גלאי של 0112**: שורת יומן שאינה
`note` שנכתבה בטרנזקציה הזו. שאלה אחת, שתי החלטות — ומכיוון שהיומן הוא
הגלאי, בלוקי ההקמה והפירוק נכללים מאליהם. הוא נקרא לתוך משתנה **לפני**
הביטול ולא אחריו, וזו ההגנה ולא ההערה: `approved_at` הוא עמודה נעקבת, ולכן
הביטול כותב שורת יומן משל עצמו — בסדר הפוך כל שמירה של לקוח על אירוע מאושר
הייתה מדווחת כשינוי בגלל עצמה.

הלו״ז אינו עובר ב-`update_event`, ולכן קיבל טריגר משלו על עמודות התכנון —
תאריך, שעות, משך, כמות עובדים, אופן ביצוע, משאיות ומיקום. ‏`status_id` **אינו**
ברשימה: הלקוח מזיז בין "טיוטה" ל"מתוכנן", וזה תכנון שלו ולא שינוי במה שסוכם.

**וכרטיס המשימה המלא הוא של מנהל המערכת** (0108). זו הכרעה על **מסך**, לא על
נתונים, ולכן היא יושבת בלקוח ולא בפוליסה: כל מה שהכרטיס כותב — סטטוס, שעות,
שיבוץ, האצלה — נכתב גם מתאי הלו״ז ומהפאנלים, ואותם מפתחות (`tasks.edit`,
`tasks.assign.*`, `tasks.delegate`) ממשיכים לשמור עליהם בשרת. מה שנסגר הוא
הטופס שמרכז את כולם במקום אחד. השער יושב ב-`TaskDrawer` עצמו ולא באתרי הקריאה,
כדי שמסך שייכתב מחר לא יוכל לפתוח אותו בטעות; אתרי הקריאה שואלים את
`useCanOpenTaskCard` רק כדי לא לצייר כפתור שלא יעשה דבר. ‏`board.open_task`
(0079) לא בוטל — הוא ממשיך לגדר את הכרטיס למי שאינו אדמין ממילא, ואיתו הנפילה
לדף האירוע במקומו.

**והלו״ז חדל לסמן איחורים** (0113). "באיחור" הוגדר כתאריך שחלף בלי שהמשימה
פורסמה לעובד — הגדרה נכונה עם היקף בלתי אפשרי: מאז 0063 אין למשימה סטטוס
סוגר, ולכן כל יום שעבר בלי פרסום נספר לנצח, והלוח נצבע אדום לאורך כל
ההיסטוריה. צ׳יפ שמונה מאות בכותרת ושורות אדומות לאורך חצי הלוח אינם התראה
אלא רעש שהעין לומדת לדלג עליו, ובדרך הוא צובע גם את מה שכבר קרה באמת. ירדו
הצ׳יפ, הרקע האדום על השורה ומשולש האזהרה; **המשימות עצמן לא זזו** — הן
ממשיכות להופיע בעמודת היום שלהן כמו כל משימה אחרת.

**ובוררי השיבוץ נפתחים לכיוון שיש בו מקום** (0113). בורר רב-בחירה (`MultiSelect`)
צף ב-portal עם `position: fixed`, ונפתח **מתחת** לעוגן תמיד. כרטיס "עובדי
הקבלן" הוא האחרון בפאנל השיבוץ, ולכן הבורר שלו יושב בתחתית המסך — הרשימה ירדה
אל מתחת לקצה החלון, למקום שגלילה אינה מגיעה אליו: לא של הדף (הפאנל אינו
בזרימה שלו) ולא של המגירה (המדידה נצמדת לעוגן ומורידה את הרשימה יחד איתו).
מעכשיו הוא נוהג כמו `Popover`: מתחת כברירת מחדל, מעל כשזה הצד שיש בו מקום,
ובכל מקרה עם תקרה שמתאימה למה שיש — הרשימה גולשת בתוך עצמה. כשהוא נפתח כלפי
מעלה הוא נעגן בקצה ה**תחתון** שלו, כדי שסינון שמקצר את הרשימה לא ינתק אותו
מהעוגן. גובה התוכן נמדד מ-`scrollHeight` של הרשימה ולא מגובה הפאנל, אחרת
ההחלטה "להפוך או לא" הייתה מזינה את עצמה ומתנדנדת.

**ו"הובלה בלבד" הוא משתנה של המחשבון** (0118). שורת "ראש צוות" הייתה מותנית
ב-`requires_team_lead` בלבד, ולכן נגבתה גם על משימה שכל תוכנה הוא להסיע ציוד
מנקודה לנקודה — ובהובלה בלבד אין צוות בשטח שראש צוות ינהל. המנוע ידע לתנות
כל שורת מחיר מאז 0017 (`is_true`, `is_false`, `eq`, `ne`, `in`, `not_in`),
וכל מה שחסר היה המשתנה: `execution_methods.is_transport_only`, אותה עמודה
שמנוע מחירי הקבלנים קורא מאז 0092 — **הדגל ולא השם**, שכן השם ניתן לעריכה
במסך ההגדרות.

בעורך התנאים כל משתנה בוליאני הוא מעכשיו **שלושה מצבים** — ‏— / כן / לא —
במקום תיבת סימון: "רק כשזו *אינה* הובלה בלבד" לא היה ניתן לביטוי קודם, אף
שהמנוע תמך בו. הכלל של לקוח מסוים נשאר **נתון ולא קוד**, כמו כל שאר ההבדלים
בין לקוחות; `app.default_pricing_config` לא נגעה, מפני שתנאי מסחרי של לקוח
אחד אינו מה שמחשבון של לקוח חדש צריך להיוולד איתו.

‏0119 הוסיפה את התנאי אצל ארקו לצד התנאי המקורי מהתבנית, וקיבלה **וגם**:
השורה נגבתה רק כשמישהו סימן במפורש "נדרש ראש צוות" *וגם* אופן הביצוע אינו
הובלה בלבד. ‏`requires_team_lead` הוא דריסה ידנית שברוב המשימות נשארת NULL,
ולכן בפועל השורה כמעט לא נגבתה. ‏**0132 מורידה אותו**: התנאי היחיד שנשאר הוא
אופן הביצוע, וכך "בונוס ראש צוות בכל מקרה שאינו הובלה בלבד" נאמר בדיוק
במילים שבהן הוא נאמר.

**וההקמה והפירוק מוצגים לפי מי שקודם** (0114-). בדף האירוע שתי שורות הסיכום
היו מקובעות "הקמה" ואז "פירוק", והמשימות מוינו לפי תאריך בלבד — כך שביום שבו
הפירוק ב-06:00 (ציוד מאתמול) וההקמה ב-18:00 (לערב), המסך סיפר את היום הפוך.
המיון כרונולוגי לגמרי, ולכן בתאריכים שונים הוא ממילא נותן את הסדר המוכר.
הכלל עצמו — `byTaskTime` ב-`grouping.ts` — הוא זה שהלו״ז כבר ממיין בו את
היום, ולא העתקה שלו: שם שעה חסרה שוקעת לתחתית במקום לצוף לראש, וזה נכון גם כאן.

### ארקו: מי מבצע, ומי הסגל שלו

חלק מהעבודה אינה מבוצעת בידי וייפר אלא בידי **ארקו**, שהיא לקוח במערכת. ‏0120
העמידה את השאלה על המשימה — `tasks.performed_by` ∈ `viper | arko`, טקסט עם
`check` ולא enum — ומ-0133 היא נושאת גם את התשובה המעשית: **מי בדיוק עושה את
זה**.

**הדגל הוא פר-לקוח, ואינו שם.** ‏`customers.performed_by_enabled` הוא מה
שהלוגיקה בודקת בכל מקום; ההצמדה לארקו היא עדכון נתונים חד-פעמי לפי שם, ולא
תנאי בקוד. לקוח שהדגל שלו כבוי אינו רואה את השאלה בשום מסך, ובקשה שנושאת
אותה בכל זאת נדחית בשרת.

**מה קורה למשימת ארקו:**

- **המחיר 0.** ‏`app.recalc_task_price` מקצרת בראשה ורושמת
  `breakdown.reason = 'performed_by_arko'` — עבודה שוייפר אינה מבצעת אינה
  הכנסה שלה. הקיצור קודם לנעילת `is_manual`, ולכן גם מחיר שהוזן ידנית מתאפס.
- **היא יורדת מהראייה של וייפר.** זרוע ה-staff ב-`tasks_select` מסננת
  `performed_by <> 'arko'` מאז 0120, ו-0135 סוגרת את שתי הפרצות שנשארו בה —
  הזרוע שנשענת על `task_assignments` וזרוע הקבלן, ששתיהן דווקא של מי שכבר עבד
  על המשימה. **האירוע** נעלם רק כשכל משימותיו החיות הן ארקו
  (`app.event_all_tasks_arko`): אירוע מעורב נשאר גלוי לוייפר, כי יש לה שם עבודה.
- **והיא מתפנה.** לסגור את הראייה ולהשאיר את השורה פירושו משמרת יתומה —
  ‏`app.planned_shifts` נגזרת מ-`task_assignments`, והעובד היה ממשיך לראות
  ב-`/my/schedule` משמרת על משימה שאינו יכול לפתוח. הטריגר מוחק במעבר את
  השיבוצים הפנימיים, את סגל הקבלן ואת ההאצלה, והטריגר הקיים
  `task_assignments_notify_removed` (0110) שולח לכל מי שהוסר `assignment_removed`.
  האצלה שכבר **שולמה** חוסמת את המעבר עצמו, ולא נמחקת בשקט.
- **והמעבר מדבר** (0136). סוג התראה `task_performed_by_changed` למנהלי המערכת,
  לשני הכיוונים, עם הכיוון בכותרת; ו-`performed_by` נכנס לרשימת השדות שיומן
  האירוע רושם, בעברית ("ארקו" / "וייפר") ולא בקוד.

**הבחירה כבר בהוספת האירוע** (0136). עד אז הבורר ישב בדף האירוע בלבד — כלומר
אחרי שהאירוע נוצר ושתי המשימות כבר נולדו על וייפר. מעכשיו `setup_performed_by`
ו-`teardown_performed_by` הם שדות טופס ככל שדה אחר, ו-`app.apply_event_task_block`
קוראת אותם. השער נכתב **בתוך** הפונקציה, כמו שנעשה למחיר ב-0111: היא
`security definer` ורצה תחת `app.system_write` מתוך `create_event`, ולכן
הפוליסות שמעליה — ו-`set_task_performed_by` — פוסחות עליה.

#### הסגל של הלקוח

ארקו מבצעת בעצמה, ולכן היא צריכה **אנשים**. ‏0133 בונה לה רשומת סגל פר-לקוח,
במקביל מדויק לרשומת הקבלן: `customer_workers` (מי בסגל), `customer_worker_roles`
(מי מוגדר ראש צוות ו/או נהג — הגדרה, לא שיבוץ), ו-`task_customer_workers`
(מי משובץ למשימה, באיזה תפקיד, מאיפה הוא מתחיל, ובאיזו משאית).

**ולא מימוש שלה כקבלן.** קבלן הוא ישות כספית — תעריפים, האצלות, קנסות,
תשלומים ופורטל — ולארקו אין דבר מכל אלה: המחיר שלה 0, והיא אינה מקבלת מוייפר
שקל. שלוש טבלאות במקביל לרשומה שכבר נבדקה עולות פחות מלגרור את כל המשמעות
הכספית לאן שהיא אינה שייכת. באותה רוח, **מה שאין כאן במפורש** הוא נוכחות
ושכר: אלה עובדים של הלקוח, ואין לוייפר מה למדוד ומה לשלם להם.

**שני מפתחות, ודגל אחד שמכריע.** ‏`customers.manage_own_staff` ו-
`customers.assign_own_staff` נכנסים לתפקיד `customer_manager` — שהוא של *כל*
לקוח — ולכן כל פוליסה וכל בדיקה שואלת בנוסף את `performed_by_enabled` דרך
`app.own_staff_customer_id()`. לקוח רגיל אינו מקבל דבר גם כשהמפתח בידו, ומסך
"הסגל שלי" (`/my/crew`) אינו מופיע לו בתפריט — אותה גדר-קהל שיש ל-`/my/staff`
של הקבלן, ומאותו נימוק.

**והלוח שלו נפתח לו** (0138). ‏0109 קבע ששדות הלוח של הלקוח סגורים עד שהמשרד
פותח, וזו הכרעה נכונה — אבל לקוח שמבצע בעצמו אינו "לקוח שעורך את התכנון של
המשרד", הוא זה שמתכנן: המשימה מוסתרת מוייפר, מחירה 0, והסגל שעליה שלו. לכן
שני שדות נפתחים לו כברירת מחדל, **ורק לו** (התנאי הוא הדגל ולא "כל לקוח"):
המשאיות והסטטוס. ‏`app.enforce_customer_board_edit` לא זזה ו-`customer_board_fields`
נשארת הטבלה שמכריעה — מה שהשתנה הוא נקודת הפתיחה, והמשרד יכול לסגור אותם
בכרטיס הלקוח כמו כל שדה אחר. לקוח שהדגל שלו נדלק מאוחר יותר מקבל אותם בטריגר.

**השיבוץ עובר ב-RPC** ‏(`customer_assign_worker`), כמו אצל הקבלן ומאותה סיבה:
שם נבדק שהמשימה באמת סומנה כמבוצעת בידי הלקוח, שהעובד שייך לו, שהתפקיד מוגדר
לו, ושהמשאית שנבחרה לנהג היא מרשימת המשאיות שלו (0116). בלו״ז זה כרטיס
"הסגל של הלקוח" באותו פאנל ממוקד שבו יושב הסגל של הקבלן, והוא הכרטיס היחיד
שיהיה שם — 0135 מסירה את ההאצלה במעבר לארקו.

### ראש צוות אחד למשימה

עד 0121 הצוות הפנימי בלבד ידע ראשי צוות (`task_assignments.role`), ולעובד
הקבלן היה תפקיד אחד: עובד. ‏0121 נתן לו תפקידים, ו-0128 מסדר את מה שנשאר פתוח
אחריו:

- **התא מציג את מי שיש.** שורת "ראש צוות" בלו״ז קראה רק `task_assignments`,
  ולכן ראש הצוות שהקבלן מינה נבלע ברשימת "צוות" עם כל השאר. ה-view נסוג עכשיו
  לראש צוות של קבלן ומ-0134 גם לסגל הלקוח, ועמודת `team_lead_kind` אומרת מאיזה
  מאגר הוא בא. סדר ההכרעה הוא סדר המנייה: שיבוץ פנימי גובר, אחר כך הקבלן.
- **ואין שני.** האינדקס של 0121 חסם ראש שני *בקרב סגל הקבלן*, בהודעת
  `duplicate key` גולמית, ולא ידע דבר על ראש צוות פנימי שכבר יושב על המשימה.
  המשימה נושאת ראש צוות אחד, נקודה — ושלושת ה-RPC בודקים את שלושת המאגרים
  ומחזירים "למשימה כבר מוגדר ראש צוות". הנתיב הפנימי נשאר כפי שהוא: המשרד
  *מחליף* ראש צוות, והקבלן אינו דורס את מה שהוא קבע.
- **והמכסה סופרת שורה פעם אחת** (0127). ‏`tcw_limit` הוא `before insert`, אבל
  מאז 0121 הכתיבה היא `insert ... on conflict do update` — ובפוסטגרס טריגר
  `before insert` רץ לפני שההתנגשות מתגלה, ולכן הוא רץ גם בנתיב העדכון וסופר
  את השורה שעומדת להתעדכן. קבלן שאמור להביא עובד אחד, שיבץ אותו, ואז בחר לו
  "ראש צוות" — נמדד כשניים. עדכון של צמד שכבר קיים מדולג מעכשיו; המכסה עצמה
  לא זזה, וראש צוות של קבלן ממשיך להיספר בה ככל עובד אחר, כי זה גם מה שמנוע
  מחירי הקבלן מתמחר.

### נוכחות ומשמרות

**המשמרת אינה טבלה.** היא נגזרת מהמשימות ששובצו לעובד, ב-`app.planned_shifts`,
ולכן היא לעולם לא מתיישנת מול שינוי בשעות המשימה. שלושה כללים מרכיבים אותה:

- **מהיכן מתחילים** — `task_assignments.work_site` (ו-`task_contractor_workers.work_site`)
  קובע פר-משובץ אם הוא יוצא מהמחסן או מגיע לשטח. מי שיוצא מהמחסן מתחיל ב-
  `warehouse_start_time`, כל השאר ב-`onsite_start_time`.
- **מאיזה מחסן** — `warehouses` היא טבלה, והמחסן הוא תכונה של **הלקוח**
  (`customers.warehouse_id`): לכל לקוח מחסן אחד, ומשם יוצאים לכל המשימות שלו.
  `tasks.warehouse_id` קיים כדריסה למשימה בודדת, והוא גם הדרך היחידה שמשימה
  עצמאית — כזו שאין לה לקוח — תוכל לנקוב במחסן. אין נפילה ל"המחסן הקרוב
  ביותר": היא הייתה מתירה לעובד להחתים מהמחסן של לקוח אחר. רדיוס פר-מחסן
  גובר על הגלובלי, ודריסה אישית של העובד גוברת על שניהם.
- **מתי מסיימים** — סיום העבודה בשטח, ועוד זמן הנסיעה חזרה **למי שיצא
  מהמחסן**. הנסיעה הזו היא, בהגדרה, החזרה מהמשימה האחרונה אל המחסן, ולמי
  שהגיע ישירות לשטח אין למה לחזור — הוא סיים כשהעבודה נגמרה. עד 0079 היא
  נוספה לכולם, ולכן גם שולמה. זמן הנסיעה עצמו נשלף מ-`app.task_travel_hours`,
  אותה הכרעה בדיוק שמשמשת את מנוע התמחור (דריסה על המשימה גוברת, אחרת אזור
  הגיאופנס של מיקום האירוע).
- **איחוד** — שתי משימות שהפער ביניהן קטן מ-`merge_gap_minutes` (ברירת מחדל שעתיים)
  הן משמרת אחת, והסיום שלה נלקח מהמשימה האחרונה בה.

**שלושה מרכיבים, שלוש שורות.** עד 0083 שעת היציאה מהמחסן הייתה גם ההתחלה של
המשימה הראשונה, ולכן משימה בת שלוש שעות הוצגה כ-06:00–10:00: הנסיעה נבלעה
בתוכה, ומי שקרא לא ידע מתי הוא באמת מתחיל לעבוד. עכשיו `warehouse_start_at`
הוא שדה משלו (null למי שמגיע לשטח), `start_at` הוא תחילת העבודה, והנסיעה חזרה
יושבת ב-`totals.travel_hours` — וסך המשמרת נשאר מה שהגזירה קובעת. ראש הצוות של
האירוע מקבל מתוך המשימה גם את איש הקשר של הלקוח וגם את נקודת ההתחלה של כל אחד
מהצוות: מי במחסן בשש ומי באתר בשבע.

**שתי הנסיעות מסומנות בצ׳יפ, ולא רק אחת.** בציר השעות, צ׳יפ של משמרת שעובדים
בה כמה אנשים נושא פס מקווקו בראשו שגובהו הוא בדיוק הנסיעה מהמחסן אל השטח —
והסיום, שכולל את הנסיעה חזרה מאז ומתמיד, נראה עד עכשיו כמו שעת סיום עבודה
רגילה. עכשיו יש גם פס תחתון, מסוף העבודה ועד ההגעה למחסן, ובין שניהם יושב מה
שהוא באמת עבודה בשטח (וזה גם הטווח שנכתב בגוף הצ׳יפ). הפס התחתון נגזר
מ-`travel_hours` של המשמרת עצמה ולא מהפרש בין שני אנשים, ולכן הוא מופיע גם
כשכל הקבוצה יוצאת מהמחסן — המקרה שאין לו פס עליון. בצ׳יפ של משמרת יחידה
(טבלת השיבוץ) הסימון הוא אייקון משאית לצד השעות, ובחלונית הרחיפה מופיעה שעת
סיום העבודה לצד משך הנסיעה. שני הפסים חסומים בגובהם, ואם יחד הם חורגים הם
מצטמצמים באותו יחס — כדי שהצ׳יפ לא יאבד את שמות העובדים.

מגירת "פרטי המשמרת" (`shift_task_breakdown`) מחשבת את הרצף מהמשימות ולא מהשורה
שנלחצה, ולכן היא חייבת לחשב **את אותו דבר**: עד 0079 היא החזירה `max(end_at)` —
סיום העבודה בשטח — בעוד שהגזירה מוסיפה את הנסיעה, ואותה משמרת נגמרה בשעה אחת
בלוח ובשעה אחרת במגירה שנפתחה מתוכו. לחיצה על משימה בתוך הרצף פותחת את פרטיה
באותה מגירה (חזרה בכפתור), ולא מנווטת החוצה: מתוך המשמרת השאלה היא "מה אני עושה
כאן", והקישור לדף האירוע יושב בתוך הפאנל למי שרשאי לפתוח אותו.

החישוב יושב ב-SQL ולא בדפדפן במכוון: לוח המשמרות, שער "מותר לך להתחיל?" בשעון,
ועמודת מתוכנן-מול-בפועל בדוח חייבים להסכים, ומימוש שני היה הופך את הראשון לעותק
שמתיישן. מאותה סיבה `app.attendance_calc` היא פונקציה טהורה: התצוגה המקדימה במסך
ההגדרות רצה עליה עצמה דרך `preview_attendance_pay`.

**השעון כותב רק דרך RPC.** ל-`attendance_entries` אין פוליסת INSERT לעובד. הכתיבה
עוברת ב-`attendance_clock_in`/`attendance_clock_out`, ושם נאכפים שני הכללים
שנקבעו פר-עובד: "נדרש מיקום" (החתמה מחוץ לרדיוס נדחית) ו"מותר להתחיל לפני
המשימה". בדיקה שהייתה יושבת בדפדפן בלבד היא קוסמטית — הטבלה חשופה דרך PostgREST.

נקודת הייחוס נגזרת במשמרת עצמה ולא בשעון: מי שיוצא מהמחסן נמדד בכניסה מול
המחסן, ומי שמגיע לאתר מול האתר. ביציאה, מי שהגיע לאתר נמדד מולו — משם הוא גם
התחיל — ולמי שיצא מהמחסן יש **שתי** נקודות סיום לגיטימיות, האתר והמחסן שאליו
חזר, ונבחרת הקרובה מביניהן (0082). קודם לכן היציאה נמדדה מול האתר בלבד, והעובד
שעמד במחסן שאליו המערכת עצמה שלחה אותו — היא סופרת לו את הנסיעה הזו — נחסם.
שתי הנקודות כבר יושבות על שורת המשמרת (`start_lat/lng` ו-`end_lat/lng`), ולכן
אין כאן שליפה חדשה אלא בחירה, ומי שרחוק משתיהן עדיין נחסם.

שני חריגים מכוונים בחסימת המיקום: קריאה חסרה נדחית תמיד (זה בשליטת העובד), אבל
אתר או מחסן בלי קואורדינטות מתקבל ומסומן `no_site_coords` (זה פער נתונים במשרד), ודיוק
ה-GPS מנוכה מהמרחק לפני ההשוואה כדי לחסום רק מי שמוכח מחוץ לטווח. פתח המילוט הוא
`attendance_record_entry`, שבגופו אין בכלל בדיקת מיקום — ולכן אין דגל שעובד יכול
להעביר כדי להגיע לפטור.

**עובד מדווח, מנהל מכריע.** שעון שלא עבד — סוללה, קליטה, או שכחה — לא אמור להיגמר
בשעות שנעלמו, ולכן `attendance_submit_entry` נותן לעובד לדווח משמרת שהסתיימה.
הדיווח נכתב לאותה טבלה עם `status = 'pending'`, ו**אינו נספר בשום סיכום** עד
ש-`attendance_review_entry` מכריע: `attendance_report` מוציא כל שורה שאינה
`approved` מהסיכומים ומהצבר השבועי שמזין את התקרה השבועית, ומחזיר אותה כשורה
מסומנת עם השכר שישולם *אם* תאושר. דחייה מחייבת נימוק, והוא מה שהעובד רואה.

הדיווח מוגבל בגופו של ה-RPC — חלון אחורה (`self_entry.max_backdate_days`), אורך
מרבי, איסור על דיווח עתידי, ואיסור על חפיפה לשעות שכבר נרשמו, שנבדק שוב ברגע
האישור כדי שהחתמת שעון שנוצרה בינתיים לא תשולם פעמיים. שעת סיום היא חובה: משמרת
פתוחה היא מצב שהשעון מנהל. `attendance.status` (וגם `reviewed_by`/`reviewed_at`)
רשומים ב-`field_registry` תחת `attendance.approve_entry` — בלי זה פוליסת ה-UPDATE
שמתירה לעובד לגעת בשורה שלו הייתה מתירה לו גם לאשר את עצמו. `attendance.submit_entry`
הוא יכולת של כל עובד, `attendance.approve_entry` נגזר מ-`attendance.edit_entry`,
וההתראה למאשרים נשלחת דרך `app.profiles_with` — הצד ההפוך של `app.has`.

**השכר מחושב בקריאה ולא נשמר.** אין טבלת שכר ואין חישוב מחדש: הרשומה מחזיקה שעות,
`worker_pay_settings` מחזיקה תעריף, השלמה לשעות והאם העובד זכאי לשעות נוספות,
ו-`app_settings['attendance.overtime']` מחזיקה את המדרגות. `attendance_report`
מחזיר את השעות לכולם ואת הסכומים רק למי שמחזיק `attendance.view_pay` — מאותה
שאילתה, כי רכז משמרות צריך את הראשון בלי השני.

**ההשלמה נמדדת מתחילת המשמרת, ולכן איחור מקצר אותה.** "מובטחות 6 שעות" שילמו
6 שעות גם למי שהגיע ברבע השעה השנייה, כלומר תמרצו בדיוק את מה שהן נועדו לכסות.
מ-0084 התקרה יורדת בגובה האיחור — הגיע ב-10:15 למשמרת של 10:00, התקרה היא 5:45,
והאיחור עולה לו את עצמו פעם אחת ולא פעמיים. מעל סף שנקבע פר-עובד
(`late_topup_forfeit_minutes`) ההשלמה נשמטת כליל: זו החלטה של המשרד על איחור
שאינו "כמה דקות", והיא יושבת בכרטיס העובד ולא בקוד. בלי משמרת משובצת אין נקודת
ייחוס, ולכן אין איחור.

**שתי תוספות שאינן שעות, לצד הבונוס.** `team_lead_bonus` הוא סכום לכל משימה
במשמרת שבה העובד רשום כראש צוות — נספר על המשימות עצמן ולא על המשמרת כיחידה —
ו-`shift_bonus` הוא סכום קבוע לכל משמרת. שלושתם (עם הבונוס הידני) יוצאים
כשורות נפרדות בפירוט ומצטרפים ל-`bonus`, שממשיך להיות מה שהוא היה: כמה מהסכום
אינו שעות. אף אחד מהם אינו נוגע במדרגות השעות הנוספות ובתקרה השבועית, מאותו
נימוק שהוציא את הבונוס מהן ב-0033.

**דיווח ידני נושא מיקום במילים.** זה בדיוק המקרה שבו אין GPS לאמת מולו — השעון
לא עבד — ולכן `clock_in_place` ו-`clock_out_place` הם חובה בדיווח, רשומים
ב-`field_registry` תחת `attendance.edit_entry`, ומכאן ניתנים לתיקון בידי מי
שמאשר. ההשלמה, השעות הנוספות והסכומים נגזרים מהשעות ומהגדרות העובד, ולכן תיקון
שעות מעדכן אותם מאליו.

**בונוס למשמרת הוא שורה, לא שעות.** `attendance_entry_bonus` מחזיקה סכום שקלי
פר-משמרת, ו-`app.attendance_calc` מוסיפה אותו כשורה נפרדת ב-`lines` ולסך
לתשלום. הוא במכוון אינו נוגע ב-`paid_hours`, במדרגות השעות הנוספות ובתקרה
השבועית: שעות פיקטיביות היו הופכות בונוס של 100 ש״ח לשווה יותר לעובד שממילא
עשה שעות נוספות באותו יום. הסך של המשמרת כבר כולל אותו, ולכן הוא נספר בסך
החודשי של העובד בלי חיבור נוסף — ו-`totals.bonus` קיים רק כדי לומר כמה מהסכום
אינו שעות.

הוא **טבלה נפרדת ולא עמודה על `attendance_entries`**, מאותו נימוק שהוציא את
`hourly_rate` ל-`worker_pay_settings`: `ae_select` מתירה לכל מי שמחזיק
`attendance.view_all` לקרוא כל שורת נוכחות, ועמודת סכום שם הייתה נקראת ישירות
דרך PostgREST בידי רכז משמרות שאינו רשאי לראות שכר. הפוליסה על הטבלה הנפרדת
בודקת את הרשאת הכסף עצמה, ו-`attendance_report` משמיט את `bonus` ואת
`bonus_note` מהשורה לפי אותה הכרעה שמשמיטה את `total`.

הכתיבה עוברת ב-`attendance_set_bonus` ולא בפרמטר על `attendance_save_entry`,
כי היא נשמרת במפתח אחר: `attendance.manage_bonus` (נגזר מ-`attendance.manage_pay`)
ולא `attendance.edit_entry`. מי שמתקן שעות אינו בהכרח מי שרשאי לקבוע סכום כסף.
אפס מוחק את הבונוס במקום לאפס אותו, ובונוס על רשומה שנדחתה נחסם — הוא לא היה
משולם לעולם.

**עובד קבלן מחתים כמו כל אחד אחר.** הוא מקבל שורת `profiles` עם
`contractor_worker_id` שמקשר אותה לשורת הסגל, ולא נתיב הרשאות מקביל: `app.has`
מחזיר `false` כשאין profile, ולכן בלי השורה הזו שום דבר במערכת לא היה עובד עבורו.
התפקיד `contractor_worker` נסגר במפורש על המודולים `portal` ו-`contractors`, אחרת
הוא היה יורש מברירות המחדל של `contractor_user` את דף הכספים של הקבלן על כל מה שבו.
בכל השאר הוא עובד מן השורה: אותם `/calendar`, `/board`, `/my/schedule`,
`/my/attendance` ו-`/attendance` של כל עובד, מצומצמים בזרוע הקבלן של
`tasks_select` למשימות שפורסמו והוא רשום עליהן.

**הגשר נוצר בשיבוץ, לא לפניו.** לקבלן שתי רשימות עובדים: `contractor_workers`,
הסגל שהוא מקליד בעצמו, ו-`profiles` עם `contractor_id` — החשבונות. חשבון
שהמשרד יצר במסך העובדים נושא `contractor_id` בלי `contractor_worker_id`, ולכן
לא היה בשום רשימה שאפשר לשבץ ממנה. `contractor_assignable_workers` מאחד את
השתיים, ו-`contractor_assign_worker` יוצר את שורת הסגל וכותב את הקישור ברגע
השיבוץ הראשון. זה אינו נוחות: `app.planned_shifts_many` מצרפת דרך
`profiles.contractor_worker_id`, ולכן בלי הגשר העובד היה משובץ ובכל זאת בלי
משמרת ובלי יכולת להחתים. הסרה משיבוץ אינה מוחקת את שורת הסגל — הורדה ממשימה
אינה פיטורים.

> `navigator.geolocation` דורש הקשר מאובטח. בפרודקשן ובלוקלהוסט זה קיים; שרת פיתוח
> שנגישים אליו דרך כתובת IP ברשת המקומית לא יוכל לבקש מיקום.

### רווחיות פר-משימה

`task_pnl` (0070) עונה על "כמה חייבתי ללקוח, וכמה זה עלה לי בפועל" ברזולוציה
של משימה. שלוש הכרעות מרכיבות אותו.

**ההקצאה לא נכתבה מחדש.** ‏`app.payroll_task_alloc` (0041) כבר פיזרה את שכר
המשמרת בין המשימות שבה — משוקלל לפי `hours_count`, בנפילה לחלוקה שווה — אלא
שסיכמה ל-`by_customer` לפני ההחזרה. 0070 מחלץ את החישוב ל-`app.payroll_task_amounts`
ומשאיר את הקורא הישן עטיפה דקה מעליו, בפלט זהה. אותה תזה של 0039 ו-0044:
מימוש שני של אותו חישוב מתיישן.

**שני בסיסי מדידה, ומוצהרים.** ההכנסה היא `task_pricing.price`, שמחושב
מ-`worker_count` × `hours_count` — כלומר **מהתכנון**. העלות נמדדת מהשעות
**שהוחתמו**. אפשר היה להריץ מחדש את `app.price_calc` עם השעות שבפועל ולהציג
"מחיר לפי ביצוע", אבל מספר כזה מעולם לא הוצג ללקוח ולא חויב, ובטבלה לצד עלות
אמיתית הוא נקרא ככסף; הוא גם היה ריק בדיוק במשימות המעניינות, כי
`app.recalc_task_price` מחזירה מחיר רק ללקוח ב-`pricing_mode='auto'` בלי
`is_manual`. במקומו כל שורה נושאת **מתוכנן מול בפועל בשעות ובראשים** — עובדה
שמסבירה למה השוליים זזו, ולא תרחיש נגדי.

**הרווח כאן כולל נטל מעביד, וזה מפריד אותו מ-`/reports/profitability`.**
‏`app.margin_summary` (0044) מחסרת שכר בלי הנטל; `task_pnl` מחסרת
`payroll × (1 + pct/100)`, כמו `finance.profit_summary` (0069). ההפרש בין שני
המסכים הוא בדיוק `payroll × pct/100`, והוא מוצהר ב-`meta`.

`app.task_pnl_rows` היא **`security definer` במכוון**: ‏`task_contractor_terms`
נקראת רק בידי מי שמחזיק `contractors.view_pricing`, ושאילתת invoker בידי קורא
שמחזיק את צרור הרווח אבל לא את המפתח הזה הייתה מחזירה אפס — עלות קבלן 0 ורווח
מנופח בגובה כל הקבלנות, בלי שום סימן. מה שהופך את זה לשקול הוא
ש-`app.margin_require()` כבר סירבה לכל היקף נתונים מצומצם.

הצרור נושא מפתח אחד מעבר לזה של `margin.*`: **`dashboard.all_workers`**. שכר
פר-משימה על משימה שמשובץ אליה עובד אחד הוא השכר של אותו עובד לאותו יום, וזה
בדיוק הקו ש-`app.payroll_by_worker` כבר מותחת. מה שאינו חוסם הוא `customers.view`:
השורה כאן היא משימה ולא לקוח, ולכן המפתח משמיט את שם הלקוח ואינו סוגר את הדוח.

### מה נספר בכסף, ומה לא

**אירוע שבוטל אינו הכנסה ואינו ספירה** (0114). מאז 0037 הוא יורד מהלו״ז, ולוח
השנה מסתיר אותו מאחורי מתג — אבל אף אגרגט לא ידע על כך דבר, ועבודה שלא תתבצע
נספרה כהכנסה בדשבורד, בדוחות, ברווחיות הלקוחות וברווחיות פר-משימה. שני מסכים
סמוכים החזיקו שתי תשובות לשאלה "מה היה החודש".

**ותוספת המחיר כן נספרת.** ‏`task_price_addons` (0113) יושבת מחוץ ל-
‏`task_pricing.price` **בכוונה** — חישוב מחדש היה מוחק אותה, או נועל את המשימה
על `is_manual` בגלל 80 ₪ של המתנה — ולכן "המתנה בשער, 450 ₪" הופיעה בכרטיס
האירוע (שמחבר אותה בקליינט) ונעלמה מכל סיכום כספי.

המימוש הוא **שלושה views ולא ארבעים פרדיקטים**: תנאי שנכתב ארבעים פעם הוא
ארבעים הזדמנויות לשכוח אותו פעם אחת, והשכחה אינה נופלת כשגיאה אלא כמספר
שנראה סביר.

| view | מה הוא |
|---|---|
| `app.live_events` | אירועים שלא נמחקו ולא בוטלו |
| `app.live_tasks` | משימות שלא נמחקו ושהאירוע שלהן לא בוטל. משימה בלי אירוע נשארת |
| `app.task_revenue` | המחיר שהלקוח משלם: `task_pricing.price` ועוד התוספות החיות. אותו שם עמודה (`price`), ולכן זו החלפת שם טבלה בכל אתר סיכום |

‏`security_invoker` בשלושתם, כמו `work_board_view`, ובסכמת `app` שאינה חשופה
ב-PostgREST — כמו `app.customer_identities` (0079). זה גם מה שמנטרל את המלכודת
האמיתית: בענפים שבהם האירוע מגיע ב-`left join`, פרדיקט ב-`where` היה הופך את
ה-join לפנימי ומוחק לקוח שאמור להיקרא אפס.

מנוע הדוחות נסגר ב-`app.report_source_sql` וב-`app.report_join_sql` (0044) —
המקור וה-join, ולא התנאי: שם כל פרדיקט נושא ציטוט מוכפל, וכאן זו החלפת שם
בלבד. הקטלוג (‏`0043`) לא נגע, ומדד `revenue` ממשיך להיות `impl='sql'` על
`col='price'`.

**שלושה יוצאים מן הכלל, ובכוונה:**

- ‏`events.funnel` — כל עניינו ההתפלגות לפי סטטוס אירוע. להסתיר ממנו את "בוטל"
  אינו תיקון אלא שקר על הצנרת. הוא הצרכן היחיד שנשאר על `events` הגולמית.
- ‏`pricing.quality` — שואל על ה**מחשבון** (מה תומחר, מה ידני, מה לא נגע בו
  אדם), ולכן ממשיך לקרוא `task_pricing`: תוספת ידנית אינה הופכת משימה
  ל"מתומחרת". הוא כן עבר ל-`app.live_tasks`.
- ‏`app.payroll_*` — השכר נגזר ממשמרות שהוחתמו, ושעה שעבדו עליה היא עלות
  ששולמה גם אם האירוע בוטל אחריה. הורדתה הייתה מייפה את הרווח.

ו-`work_board_view.customer_price` נשאר המחיר בלבד: 0113 בחרה שהתוספת תגיע
למסך כרשימה עם משפט ולא כמספר שנבלע, ולסכם אותה לתוך תא בלוח היה מבטל את
ההכרעה ההיא.

### הצד של הלקוח בכסף: הוצאה, סיכום חודשי, ועמלה

‏`task_pricing.price` הוא מספר אחד ששני צדדים קוראים הפוך — לוייפר הוא הכנסה,
ללקוח הוא מה ששילם — ו-0074 נתן ללקוח את הצד שלו בשם הנכון (`spend.summary`,
המפתח `finance.customer_spend`). ‏0143 מוסיף את מה שהוא עדיין לא יכול היה
לשאול: **כמה אירועים היו לי, כמה כסף, וכמה עמלה — חודש בחודשו.**

**הדגל, לא השם.** ‏`customers.commission_pct` ו-`customers.commission_min_event`
הם מה שהלוגיקה בודקת בכל מקום; ההצמדה לקיסר היא `update` חד-פעמי לפי שם, בדיוק
כמו הדלקת `performed_by_enabled` לארקו ב-0120. ‏`commission_pct is null` פירושו
"אין עמלה" ולא "אפס אחוז": ההבדל הוא בין כרטיס שנעלם לכרטיס שכתוב בו 0 ₪ בכל
חודש, והסקשן מחזיר `null` באותה משמעות בדיוק. לקוח עמלה נוסף בעתיד הוא שורה
במסד, לא שורת קוד.

**סקשן אחד, `customer.monthly`, ושלושה ווידג׳טים** — כמו שלישיית ההוצאה
שלפניו, ומאותו נימוק: שלושה כרטיסים על המסך הם שאילתה אחת בשרת. חמש הכרעות
שיושבות בו:

| ההכרעה | למה |
|---|---|
| הסכום מ-`app.task_revenue` בלבד, ולא מ-`event_income` | ל-`event_income` אין ענף `customer_user` באף פוליסה (0068), והפונקציה היא `security invoker` — הטבלה הייתה חוזרת **ריקה בשקט**, והלקוח היה מקבל מספר אחר מהמשרד בלי שגיאה ובלי יומן |
| סכום האירוע נמדד על **כל** משימותיו | אירוע שנחתך בקצה הטווח היה יורד מתחת לסף העמלה מסיבה טכנית, ומאבד ללקוח כסף בגלל בורר תאריכים |
| הענף מותנה גם ב-`app.customer_id()` | ‏`app.has` מחזיר `true` לאדמין בהגדרה, ובלעדיו "האירועים שלי" היה מציג לו את כל החברה |
| הסף חמור, והעיגול פר-אירוע | "גבוה מ-2,000" פירושו ש-2,000 בדיוק אינם מזכים; והעמלה החודשית היא סך מה שכל אירוע באמת מזכה בו |
| לקוח עמלה סופר רק אירועים שהוא **גובה** עליהם | שני הצדדים אינם אותה שאלה: מי שמשלם לוייפר שואל "כמה אירועים היו לי", ואירוע בלי חיוב הוא עדיין אירוע; מי שגובה עמלה שואל "על כמה אני גובה". `commission_pct` הוא מה שמכריע, לא השם |

**והכרטיסים והטבלה עונים על שתי שאלות שונות, בכוונה.** הכרטיסים קוראים את
הטווח שנבחר; הטבלה מציגה חלון של שנים־עשר חודשים שאינו נחתך בו — אחרת "לחודש"
היה שורה אחת, כי הטווח של הלקוח נעול על החודש הנוכחי. אותו נימוק שבגללו שני
כרטיסי הצי (0090) אינם קוראים את הטווח.

**וכותרת אחת נגזרת מהקונפיגורציה** ולא מהשם: אותו סכום הוא "סכום לתשלום
לוייפר" ללקוח שמבצע בעצמו, ו"סכום כולל של האירועים" ללקוח שמביא עבודה ומקבל
עליה עמלה. ‏`sectionKpi.label` מקבל מאז 0143 גם פונקציה של הנתון, וזה כל
ההבדל בין השניים.

### הדשבורד של הלקוח אינו שלו לסדר

‏`dashboard.customize` נרשם ב-0038 כמותר כברירת מחדל, ובנימוק נכון — לסדר את
הדשבורד של עצמך אינו נתון שנחשף אלא העדפת תצוגה. מה שלא נאמר שם הוא שהקהל כלל
גם את הלקוח. ‏0144 סוגרת אותו, יחד עם בורר הטווח (`dashboard.change_range`,
מפתח חדש שנשאר פתוח לצוות ולקבלן); הייצוא כבר היה סגור מ-0066.

**מלכודת ששווה לזכור:** ‏`app.has` **אינו** מסתכל על `applies_to` (0026, 0042),
ו-`register_permission` **אינו** מעדכן `default_allowed` ב-`on conflict`. כלומר
צמצום הקהל ברישום לבדו אינו שולל דבר — הוא בשביל המטריצה ובשביל השומר של 0014,
והשלילה עצמה יושבת ב-`kind_permission_defaults`, ב-`role_permissions` וב-מחיקת
ההענקות הפרטניות.

**ומה שהופך את זה ליותר מכפתור מוסתר:** ‏`dl_write_own` (0040) התירה לכל משתמש
מאומת לכתוב את שורת הפריסה של עצמו בלי שום בדיקת מפתח, ולכן הנעילה עד 0144
הייתה מסך בלבד ובקשת PostgREST ישירה הייתה עוברת. הפוליסה שואלת מעכשיו גם את
`dashboard.customize`. ‏`dl_select` לא זזה: לקרוא את הפריסה שלך אינו לשנות
אותה, ובלעדיה אין ללקוח מסך.

### הלו״ז זוכר מאיפה יצאת

מי שלוחץ על משימה בלו״ז ואין לו `board.open_task` מגיע לדף האירוע (0108) —
וזה הנתיב הרגיל של הלקוח, לא קצה. עד עכשיו החזרה הנחיתה אותו בראש הלוח:
הגלילה האופקית התאפסה, והחודש חזר לזה ש-`?date=` אמר בכניסה הראשונה.

החזרה היא `navigate(-1)`, כלומר היא נוחתת על ה**כתובת** שממנה יצאנו — ולכן די
בכך שהלוח יכתוב לכתובת של עצמו את הנקודה לפני שהוא עוזב. ‏`?date=` מחזיר את
החודש דרך האפקט שכבר קיים, ו-`?at=` גולל לעמודה ומבזיק אותה. זה ה-idiom של
המסך (`?task=`, `?date=`) ולא מנגנון חדש: אין באפליקציה שימוש אחד
ב-`location.state`.

הכתיבה היא `history.replaceState` ולא `setParams`, משתי סיבות שכל אחת מהן
לבדה מספיקה: ‏`setParams` הוא ניווט של ה-data router וה-push לאירוע קוטע אותו
באותו tick — הכתובת שחוזרים אליה הייתה יוצאת בלי העוגן; ו-`replace` של הראוטר
מנפיק `location.key` חדש, שהיה מבטל את הזיהוי ש-`BackButton` עושה ל-`'default'`
כדי לחזור הביתה מטאב שנפתח ישר על deep link במקום לצאת מהאפליקציה.

הגלילה עצמה ממרכזת (היעד הוא עמודה אחת ולא רצועת יום) ו-RTL-aware לפי האזהרה
שכבר בקובץ — ‏`virtualizer.scrollToIndex` קורא היסט אופקי כ-`scrollLeft * -1`
וכותב אותו בלי הסימן, ולכן הסקרולר מונע ישירות. ‏`?at=` נשאר בכתובת אחרי
השחזור: ניקויו עולה כתיבת היסטוריה נוספת ואינו קונה דבר.

## אבטחה והרשאות

כל הרשאה היא **שורה ברישום** (`permission_registry`) עם מפתח מנוקד — `tasks.assign.worker`,
`contractors.edit_pricing` — ולא ערך enum. הוספת יכולת חדשה היא `INSERT`, ולכן מודול שייכתב
בעתיד מקבל הרשאות מלאות ומופיע במסך הניהול בלי שינוי קוד.

ההכרעה נעשית במקום אחד, `app.has(key)`, בסדר הזה:

| # | שכבה | טבלה |
|---|---|---|
| 1 | אדמין | `profiles.is_admin` |
| 2 | חריגה אישית (מותר/חסום) | `user_permission_grants` |
| 3 | תפקידים שהמשתמש חבר בהם | `role_permissions` |
| 4 | ברירת מחדל לסוג משתמש | `kind_permission_defaults` |
| 5 | ברירת מחדל של המפתח | `permission_registry.default_allowed` |
| 6 | המפתח הרחב שממנו נגזר | `permission_registry.implied_by` |
| 7 | חסימה | — |

שלב 6 הוא מה שמאפשר לפצל הרשאה גסה לדקות בלי לשבור: `tasks.reschedule` נגזר מ-`tasks.edit`,
ולכן מי שקיבל "עריכת משימות" ממשיך להזיז משימות עד שאדמין יחליט אחרת. תפקיד צר "סוגר מודול"
(חסימה מפורשת) כדי לא לרשת יכולות בטעות.

**איפה זה נאכף**

| שכבה | מנגנון |
|---|---|
| שורות — אילו נתונים רואים | `permission_scopes` בתוך פוליסות ה-SELECT: לקוחות, קבלנים, סוגי משימה, סטטוסים, חלון תאריכים, "רק מה שמשויך אליי" |
| עמודות — עריכה | טריגר גנרי אחד, `app.enforce_field_perms()`, שקורא את `field_registry` לפי שם הטבלה. יושב על הטבלה ולא על ה-RPC ולכן מכסה את כל נתיבי הכתיבה |
| עמודות — צפייה | תצוגות `*_secure` שנוצרות מ-`field_registry`, מיסוך `work_board_view`, ו-`event_activity_feed` שמשמיט שינויים בשדות שאסור לקורא לראות |
| פעולות | `app.require(key)` בתוך ה-RPCs |

**‏`is_admin` אינו GRANT.** שכבת ההרשאות של האפליקציה יושבת *מעל* הרשאות
Postgres ואינה מחליפה אותן, ולכן פונקציית `public` שהיא **security invoker**
חייבת שהקורא יוכל להריץ גם כל עוזר ב-`app` שהיא קוראת לו — אחרת התוצאה היא
`permission denied for function …` (42501) לכל משתמש, מנהל מערכת כולל.
זה מה שהשבית את "רווחיות לפי משימה" מיום שנכתבה: `public.task_pnl` הוא
invoker במכוון (ספירת ה-`truncated` חייבת לראות את מה שהקורא רואה), ו-0070
שלל מ-`authenticated` את ההרצה של `app.task_pnl_rows` שהוא קורא לו. ‏0087
מחזיר את ההענקה, כמו ש-0044 עושה לעוזרים של `customer_profitability`.
בדיקה שרצה בזהות superuser לא יכולה לגלות את זה — GRANTs נעקפים שם — ולכן
0087 נושא בהערותיו את השאילתה שמאתרת את הדפוס בכל המסד.

**מנהל מערכת אינו עובד, ואינו מוגבל בהיקף נתונים.** במסד הוא שורת `staff` עם
`profiles.is_admin`, וכך זה נשאר: `user_kind` מכריע עשרות פוליסות, את
`permission_roles.user_kind` ואת `kind_permission_defaults`, וערך אנום רביעי
היה נוגע בכולן כדי לתאר מישהו שממילא עוקף את כולן. מה שהשתנה (0085) הוא
המקומות שבהם ההבחנה באמת חסרה:

- **הטופס שואל "סוג משתמש" בארבע אפשרויות**, ו"מנהל מערכת" היא אחת מהן: היא
  פותחת שורת `staff` **בלי תפקיד צוות**. עד כאן היה צריך לרשום מנהל כ"צוות",
  והטופס ממלא `worker` כברירת מחדל — כך שהמנהל נכנס לרוסטר לוח המשמרות
  ולרשימות השיבוץ. מי שגם מנהל וגם עובד נפתח כ"צוות" ומקבל את המתג "מנהל
  מערכת"; רק הוא, ולא כל מנהל, מקבל שעון נוכחות ומשמרות.
- **הרוסטר הוא של עובדים.** ‏`app.shift_roster` דורש תפקיד צוות (או שורת סגל
  אצל קבלן, או שיבוץ בפועל בטווח המוצג), ולא "כל פרופיל `staff`". שורה שאי
  אפשר לשבץ אליה היא שורה שלעולם תישאר ריקה.
- **‏`app.scope_rows` שותקת לאדמין.** זו הייתה הסיבה ל"למה כמנהל מערכת אין לי
  הרשאה לרווחיות לפי משימה": שערי הכספים (0041/0044/0058/0059/0069/0070/0074)
  נועלים קורא ש"היקף הנתונים שלו מצומצם", ודי היה בתפקיד ישן שנושא היקף —
  `worker`/`driver`/`team_lead` נושאים `own` על `tasks` מאז 0011 — כדי לסגור
  את כולם בפניו. `app.has` עוקף את שכבת ההרשאות לאדמין וכל פוליסת RLS נפתחת
  ב-`app.is_admin() or`; רק שאלת ההיקף המשיכה להיענות מהטבלה.

**מי אתה, לא רק מה מותר לך.** מפתח עונה על "מה מותר", ולמנהל מערכת הוא עונה
תמיד כן. זה נכון להרשאות ולא למסך ששייך לאדם מסוים, ולכן `NavItem` ו-`handle`
של נתיב נושאים גם `audience` — פרדיקט על מי שקורא, לצד המפתח:

| פרדיקט | מי | מה הוא גודר |
|---|---|---|
| `forEmployees` | מנהל מערכת רק אם יש לו תפקיד צוות; כל השאר כרגיל | `/my/schedule`, `/my/attendance` |
| `forContractors` | מי שיש לו `contractor_id`, או `contractor_user` | `/my/staff` |

התפריט (`visibleNavSections`) ו-`RouteGate` קוראים את אותו פרדיקט, ולכן מה
שאינו בתפריט גם אינו נפתח בהקלדת הנתיב.

**מסך אחד לכולם.** ללקוח ולקבלן אין מסכים משלהם. הם נכנסים לאותו shell, לאותם
נתיבים ולאותם קומפוננטים כמו עובד, וכל הבדל בין מה שהם רואים נובע ממפתח במרשם
או מ-RLS — לא מ-`user_kind`. עמודה שנשענת על join שה-RLS מרוקן (צוות, ראש צוות,
קבלן) נושאת `viewPerm` ונעלמת, ולא מוצגת ריקה; סקשן בדשבורד שאין עליו מפתח חוזר
`null` מ-`dashboard_stats` ולא מצויר; ופילטר שיש בו אפשרות אחת נשמט.

מה שהחזיק את זה קודם הייתה הפניה לפי `user_kind`, שהייתה גם מה שמנע ממסך צוות
להיות נגיש ב-URL. במקומה כל נתיב מצהיר על המפתח שלו ב-`handle`, ו-`RouteGate`
דוחה נתיב שלא הצהיר על כלום. זה חזק יותר: ההפניה חסמה סוג משתמש אחד מתת-עץ אחד,
והשער חוסם כל משתמש מכל נתיב שאין לו את המפתח שלו.

הקבלן היה האחרון שנשאר מחוץ לזה. `/portal` היה shell שלם עם chrome משלו, וארבע
לשוניות שהחזיקו את לוח השנה, הלו״ז, הסגל והנוכחות שלו; ההפניה שהחזיקה אותו שם
היא גם מה שהפך `board.view` ו-`calendar.view`, שהתפקידים שלו כבר החזיקו מ-0066,
לקוד שאי אפשר להגיע אליו. ‏0071 מסיר אותה, וכל לשונית הופכת לנתיב שכבר קיים:
‏`/calendar`, `/board`, `/attendance`, `/my/staff`. ‏`/portal` נשאר כדף הכספים
שלו, בתוך ה-shell כמו כל מסך אחר.

מה שאפשר את זה הוא ששכבת ה-`default_allowed` של ארבעת מפתחות ה-`portal.*`
כובתה: כל עוד כל איש staff פתר אותם `true`, לא היה אפשר לגדר בהם נתיב, וזו
בדיוק הסיבה שהחסימה נעשתה בהפניה ידנית ולא בשער. הקבלנים ממשיכים להחזיק אותם
דרך `kind_permission_defaults` ודרך התפקיד.

**מה שהלקוח רואה בכספים הוא כמה הוא הוציא — ולא כמה אנחנו הכנסנו.** אלה אותו
`task_pricing.price` משני צדדים, וללקוח הוצג הצד שלנו: `pricing.view`, שהוא
צריך כדי לקרוא את התמחור של המשימות שלו, גורר `pricing.revenue` וממנו
`finance.income_view`; ו-`dashboard.view` גורר `reports.view`. אף אחד מהם לא
הוענק — כולם נגזרו. ‏0074 סוגר את השלושה בשכבת ה-kind *וגם* בשכבת התפקיד
(שגוברת עליה, ולכן שורת allow קיימת הייתה מנצחת חסימה של ה-kind), ופותח
במקומם מפתח אחד, `finance.customer_spend`, שאינו נגזר משום דבר. ללקוח גם אין
נוכחות — לא שעון, לא משמרות ולא דוח — לא למנהל ולא לעובדים שלו.

**מה שעובד השטח רואה.** אותו לוח, אותו לוח שנה ואותו דף אירוע כמו כולם —
מצומצמים בשלושה מפתחות שנרשמו ב-0079 כדי שיהיה אפשר לכבות בהם כלים בלי לכבות
את המסך:

| מפתח | מה הוא שולט בו | ברירת המחדל של "עובד" |
|---|---|---|
| `calendar.filter` | שורת הסינון, החיפוש והצ׳יפים בלוח השנה | כבוי |
| `board.filter` | שורת הסינון והחיפוש בלו״ז | כבוי |
| `board.columns` (מ-0011) | בורר התצוגה ובורר השדות בלו״ז | כבוי |
| `board.open_task` | פתיחת כרטיס המשימה בלחיצה | כבוי |

שלושתם `implied_by` של מפתח הגישה של המודול, ולכן מי שכבר פותח את המסך ממשיך
להחזיק אותם בלי שורת הענקה — התוספת אינה מורידה דבר מאיש, היא רק מאפשרת דחייה.
הדחייה עצמה נכתבה לתפקיד **"עובד"** בלבד; נהג, ראש צוות וכל תפקיד שהוגדר במערכת
ממשיכים כרגיל, ומי שרוצה להתנהג כמו עובד שטח נקבע במסך ההרשאות ולא במיגרציה.

בלי `board.columns` הלו״ז אינו "בלי בורר" אלא **נעול על תצוגה אחת** — טבלה בכל
רוחב מסך, גוון לכל אירוע, ימים ריקים גלויים, צפיפות מינימלית, מיון לפי שעה
ופרוס. ‏`localStorage` אינו נקרא ואינו נכתב במצב הזה: העדפה שנשמרה בדפדפן הזה
בתפקיד אחר הייתה משנה מסך שאין בו כפתור להחזיר אותה. ובלי `board.open_task`
לחיצה על משימה מובילה **לדף האירוע** — כרטיס המשימה הוא מסך עריכה, ומי שאינו
עורך צריך את מה שסביב המשימה ולא את השדות שלה.

`events.view` נפתח לתפקיד "עובד" באותה מיגרציה, ושאר מודול האירועים נכתב מחדש
כדחייה מפורשת — כולל מפתחות שנרשמו אחרי 0011 (יומן הפעילות, המפרט) והיו נדלקים
לו בהיסק מ-`events.view`. "לראות את האירוע" אינו "לראות את מי שינה בו מה".

**המפרט יצא מהכלל הזה ב-0102.** הדחייה הגורפת נכתבה על מודול שלם ולא כהכרעה על
המסמך עצמו, והתוצאה בשטח הייתה הפוכה מהכוונה: מי שנוסע לאירוע — עובד, נהג, ראש
צוות, עובד קבלן ומנהלו — הוא בדיוק מי שצריך לקרוא את מה שהלקוח שלח, והוא היחיד
שלא ראה אותו. שורות הדחייה על `events.specs_view` נמחקו (ולא הופכו ל-true, כדי
שהתפקיד יישען שוב על המרשם), והמפתח נרשם מחדש כ-`default_allowed` לשלושת סוגי
המשתמש. יומן הפעילות **לא** זז — הוא באמת "מי שינה בו מה" ולא מסמך העבודה.

**דף האירוע אינו רשימת האירועים.** ‏`events.view` שלט בשלושה דברים בבת אחת —
זרוע ה-staff ב-`events_select`, הנתיב `/events/:id` והנתיב `/events` — ולכן
0079 פתח לעובד גם קטלוג שאין לו בו מה לעשות. ‏0082 מוציא את הרשימה למפתח
`events.list` (נגזר מ-`events.view`, ולכן איש אינו מאבד אותו) וסוגר אותה
לשלושת תפקידי השטח. השובל בכותרת מקשר לאב רק כשהאב באמת נפתח לקורא, אחרת
"אירועים" הוא טקסט ולא קישור אל "אין לך הרשאה".

**משימה שטרם פורסמה אינה מזמינה גם את האירוע שלה.** ‏0063 קבעה את הכלל בצד
המשימות — מי שכל זיקתו למשימה היא השיבוץ רואה רק את מה שפורסם — אבל
`events_select` נשענה על אותה זיקה בדיוק בלי לשאול על הסטטוס, ולכן טיוטה
שהרכז עוד עובד עליה הופיעה בלוח השנה של העובד. ‏`app.on_event_as_staff` (0082)
מרכזת את השאלה, כמו שזרוע הקבלן כבר עשתה מאז 0066.

**ראש הצוות של האירוע אינו מפתח — הוא תפקיד על השורה.** אותו אדם הוא ראש צוות
באירוע אחד ועובד מן השורה בבא, ולכן `app.is_event_team_lead` נבדקת פר-אירוע
ולא במרשם. היא פותחת שלושה דברים שראש צוות בשטח צריך כדי לנהל את היום ושעובד
מן השורה אינו צריך: יומן האירוע, הוספת תיעוד בו, ושם וטלפון של איש הקשר. המסך
מכריע את אותה שאלה מ-`team_lead_id` שכבר מגיע בלו״ז, בלי שאילתה נוספת, והשרת
מכריע אותה בעצמו בפוליסות על `event_activity` ועל `event_contacts`.

**"חסר" הוא מדידה, לא נתון.** ‏`showOutcome` כבר החזיק את "מתוך" ואת "נוספות"
אצל מי שמאשר את המשמרת ולא אצל מי שעבד אותה, ואריח "שעות חסרות" נשאר מחוצה לו
בטעות. הוא מצטרף אליהם. מנגד, פתיחת שורת נוכחות חדלה לדרוש מפתח עריכה: המגירה
כבר מציירת כל שדה כ-`disabled` למי שאין לו מפתח, ולכן העובד פותח את המשמרת שלו
וקורא ממה היא מורכבת — והשכר שלו מופיע גם בשעון עצמו, מאותו `attendance_report`
שמשמיט סכומים למי שאין לו `attendance.view_own_pay`.

> ‏`app.event_visible` (0005) הייתה `security definer` ששואלת רק
> `has('events.view')` — בלי היקפי השורות. כל עוד לא היה לעובד שטח את המפתח
> הזה ההשמטה לא הזיקה; מרגע ש-0079 הדליק לו אותו היא החזירה `true` על **כל**
> אירוע, ואיתה נפתחו הפוליסות שנשענות עליה. ‏0082 מחזיר אותה ל-invoker: היא
> מפסיקה לשכפל את `events_select` ומתחילה לשאול אותה, ולכן היא לא יכולה עוד
> לסטות ממנה.

**מי שרואה את המשימה רואה של מי היא.** שם הלקוח *במערכת* הוסתר מעובד השטח בלי
החלטה — הוא מגיע מטבלה שהמפתח לפתיחתה, `customers.view`, הוא מפתח מודול שלם
(פרטי קשר, תמחור, שדות טופס), ו-`work_board_view` הוא `security_invoker`.
‏0079 מצר אותו: **הזהות בלבד** — שם וצבע — נגלית דרך `app.customer_identities`,
view בסכמה שאינה חשופה ב-PostgREST, שה-view של הלוח מצטרף אליו במקום ל-
`customers`. השורה עצמה כבר סוננה ב-`tasks_select`, ולכן "של מי המשימה" אינו
מידע נוסף; הרחבה של `customers_select` לעומת זאת הייתה פותחת גם את
`contact_phone`. ‏`shift_task_breakdown` כבר עשה בדיוק את זה מאז 0034, ולכן
הכלל אינו חדש — הוא רק חדל להיות מקומי.

**אדם אחד יכול להיות גם עובד שעתי שלנו וגם קבלן שמביא סגל.** מה שמנע את זה
לא היה הסכימה — `profiles_contractor_kind` הוא גרירה חד-כיוונית ולא בלעדיות,
ופרופיל `staff` תמיד היה רשאי לשאת `contractor_id` — אלא שלוש שורות ששאלו
`v_kind = 'contractor_user'` במקום לשאול אם יש למשתמש קבלן. ‏0075 מחליף את
השאלה, ומוסיף תפקיד `staff_contractor` עם `user_kind` **ריק**: תפקיד בלי סוג
עובר את המסנן של `app.my_role_ids()` לכל אחד, ושכבת התפקידים היא `bool_or`
ולכן הוא רק מוסיף. סוג המשתמש חוזר לתאר איפה החשבון נולד, לא מה מותר לו.

> תפקיד שמוצמד למשתמש מסוג לא תואם נבלע בשקט ב-`app.my_role_ids()` — הוא
> מסומן במסך ואינו מעניק דבר. מסך ההרשאות מציג אותו עכשיו כ"אינו בתוקף" עם
> כפתור הסרה, ושינוי סוג משתמש מנקה את מה שהפקיע.

**מנהל קבלן גובר על עובד קבלן** (0103). קבלן קטן הוא לרוב גם העובד הראשון של
עצמו, ושני הכובעים על אדם אחד סתרו זה את זה בשני מקומות:
`contractor_assignable_workers` השמיטה במפורש חשבונות שנושאים תפקיד מנהל
("הם אינם סגל"), ולכן הוא לא הופיע בבורר השיבוץ ולא יכול היה לשבץ את עצמו;
ו-`app.shift_roster` מכניס חשבון קבלן רק דרך שורת הסגל שלו
(`contractor_worker_id`), שלמנהל אין — ולכן הוא נעדר מלוח המשמרות ומרשימת
העובדים של הדוח. שניהם נפתחים: המנהל מוצע לשיבוץ ככל אחד אחר (מי שרק מנהל
פשוט לא נבחר), ומרגע השיבוץ הראשון `contractor_assign_worker` יוצר לו שורת סגל
וקושר אליה את הפרופיל — וממנה נגזרות המשמרת, השעון ושורת הדוח. הרוסטר מקבל גם
נפילה לאחור: חשבון קבלן שכבר נרשמה לו נוכחות בטווח הוא עובד, שורת סגל או לא.

הכלל עצמו — הכובע המנהל אינו נגרע על ידי כובע העובד — נאמר בשלוש שכבות. בשכבת
השדות (0103) הדחייה על איש הקשר יושבת על **קהל** הקבלן וההיתר חוזר על **תפקיד**
המנהל, ו-`app.can_view_field` קורא תפקיד לפני קהל. בשכבת ההרשאות `bool_or` על
שורות התפקידים כבר נותן להענקה לגבור על דחייה — **אבל רק אם ההענקה קיימת
כשורה**, וזה בדיוק מה שנשבר: `portal.attendance` הגיע למנהל הקבלן מברירת המחדל
של הקהל (שכבה 4), ולתפקיד `contractor_worker` יש עליו שורת דחייה מפורשת (שכבה
3) — כך שמנהל שהוצמד לו גם תפקיד העובד **איבד את דוח העובדים**: לא "נוכחות הסגל
שלי", לא לוח המשמרות, ולא מסנן העובדים בדוח.

זו מחלקה של באגים ולא באג יחיד, ולכן 0104 עונה לה פעמיים: **`app.my_role_ids()`
משמיט את תפקיד עובד הקבלן ממי שנושא גם תפקיד מנהל** — כלל אחד, במקום שכל
ההכרעות (הרשאות, שדות, היקפים) עוברות בו — ובסיס התפקיד של מנהל הקבלן נכתב
מחדש כהענקות מפורשות, כולל שני המפתחות שהיו עד אז של תפקיד העובד בלבד (דיווח
ידני והשכר של עצמו). הצמצום בטוח מפני שלתפקיד `contractor_worker` אין שורות
ב-`permission_scopes` ולא ב-`field_permissions`: מה שהוא מסיר הן הדחיות שלו.

**איש הקשר של הלקוח אינו של עובד הקבלן** (0103). `event.contact_name/phone`
נרשמו `default_can_view = true` (0011), ולקהל ה-staff נכתבה דחייה בברירת המחדל
(0004) — אבל לא לקהל הקבלן, ולכן כל עובד קבלן עם התחברות ראה שם וטלפון במגירת
המשמרת שלו (`shift_task_breakdown` שואל `can_view_field`). הדחייה נכתבת עכשיו
לקהל `contractor_user`, ומנהל הקבלן — שמתאם מול איש הקשר בשטח — מקבל אותה
בחזרה בשורת תפקיד, לצפייה בלבד. הדחייה יושבת על הקהל ולא על התפקיד
`contractor_worker` בכוונה: חשבון עובד שנוצר דרך `contractor_assign_worker`
נולד בלי תפקיד כלל, ודחייה על התפקיד הייתה מדלגת עליו.

**מה שנשאר מחובר לעמודה המשוקפת** (0105). ‏0096 העביר את האמת של ההאצלה
ל-`task_contractor_terms` (שורה לכל קבלן) והפך את `tasks.contractor_id` לשיקוף
של הקבלן הראשי, מתוחזק בטריגר על ה-terms. חמישה נתיבים המשיכו לדבר עם העמודה
כאילו היא האמת, וכולם נכשלו בשקט:

- **הייבוא מאקסל** כתב את העמודה ולכן לא האציל דבר — הקבלן שבקובץ נעלם,
  ו"מחיר לקבלן" נפל על "נכתב בלי קבלן". עכשיו הוא כותב שורת terms.
- **`bulk_update_tasks`** הציע `contractor_id` בטלאי; עכשיו הוא מאציל דרך
  `contractor_delegate`, וערך ריק מסיר דרך `contractor_undelegate` — כלומר
  מכבד את חסימת התשלום.
- **התראת ההאצלה** ישבה על `AFTER UPDATE OF contractor_id ON tasks`, כלומר על
  השיקוף: הקבלן השני לא קיבל אותה כלל, וביטול האצלה של הראשון שלח אותה למי
  שכבר קיבל. היא עברה ל-`AFTER INSERT` על שורת ה-terms.
- **האריח "משימות לפי קבלן"** בדשבורד ספר דרך השיקוף, ולכן משימה שהואצלה
  לשניים נספרה אצל אחד.
- **והעמודה עצמה נעשתה קריאה בלבד**: טריגר דוחה כתיבה ישירה אליה (מלבד השיקוף,
  שרץ תחת `app.system_write`). זה גם מה שמחזיר את ההגנה של 0057 — הסרה או
  החלפה של קבלן ששולם עליו — שנשענה על טריגר שירד ב-0096; הנתיב הנתמך,
  `contractor_undelegate`, בודק `paid_at` בעצמו.

**וההאצלה נבדקת מעל ה-RLS של טבלת הכסף** (0105). ‏0098 העביר את זרועות הקבלן
בפוליסות לבדיקת `exists` על `task_contractor_terms` — שורה שנושאת מחירים, ולכן
`tct_select` פותחת אותה רק למי שמחזיק `contractors.view_pricing`. תת-שאילתה
בתוך פוליסה נשפטת תחת ה-RLS של הקורא, ולכן ה-`exists` החזיר `false` לעובד
הקבלן, ו**המשימות שלו נעלמו לו מהלוח** ואיתן המשמרת שנגזרת מהן. הבדיקה עברה
ל-`app.assignment_on_my_contractor` — אותה שאלה בדיוק, `security definer`,
שרואה את שורת ה-terms בלי לפתוח את המחירים שבה.

**הגדרות השכר והשעון של הסגל הן של המשרד** (0106). ‏0103 פתח אותן למנהל הקבלן
דרך `portal.worker_settings`, וההכרעה התהפכה: מה שנשאר לו במסך "העובדים שלי"
הוא **לראות את הרשימה ולהוסיף עובד**. מעקב האיחורים והסרה מהסגל ירדו איתן —
הראשון קובע על מי חל קנס האיחור *שלו* (0091), והשני מוחק שורה שנוכחות ותשלומים
מצביעים עליה — ושניהם מאחורי המפתח המשרדי `contractors.manage_workers`.

המנגנון עצמו נשאר על מכונו, והוא הסיבה שההכרעה הפוכה אבל הדלת פתוחה:
`portal.worker_settings` הוא מפתח ייעודי ולא `attendance.manage_pay` המשרדי —
אותו נימוק של `portal.approve_attendance` (0091): המשרדי מתיר לכתוב את ההגדרות
של כל אדם במערכת, והזרוע ב-`wps_write` מוגבלת לסגל של הקבלן הכותב. הכתיבה
עוברת ב-RPC ‏(`portal_set_worker_settings`) ולא בטבלה, מפני שהטריגר הגנרי על
העמודות (`app.enforce_field_perms`) קורא מ-`field_registry` ש-`hourly_rate`
דורש מפתח משרדי; ה-RPC מכריז על ההיקף שלו, מדליק `app.system_write` סביב
הכתיבה ומכבה מיד. שניהם נשענים על המפתח, ולכן מי שאינו מחזיק אותו נדחה בשניהם
— והענקה אישית במסך ההרשאות מחזירה לקבלן מסוים את היכולת בלי מיגרציה.

**וכלי התכנון שמעל הלו״ז אינם של הקבלן** (0106). ‏`board.columns` (בורר התצוגה
והשדות) ו-`board.filter` (שורת הסינון והחיפוש) נגזרים מ-`board.view`, כלומר
נדלקים בהיסק לכל מי שפותח את הלוח. שלושת תפקידי השטח סגורים להם מאז 0079, ושני
תפקידי הקבלן מצטרפים אליהם: הלוח עצמו נשאר, נעול על תצוגה אחת.

**עובד הקבלן אינו משבץ, וגם לא של קבלן אחר** (0108). ‏0091 §6ב כיבה לקהל
הקבלנים את `portal.assign_workers`, ו-0075 §2 הוריד משני תפקידי הקבלן את
`contractors.assign_workers` — אבל את שכבת ה**קהל** של השני איש לא נגע בה, והיא
נשארה `true` מאז 0011. חשבון של עובד קבלן נולד לרוב **בלי תפקיד כלל** (‏
`contractor_assign_worker` יוצר אותו בשיבוץ הראשון), ולכן הוא נפל בדיוק לשכבה
הזאת. שני שערים לא עצרו אותו: הלקוח מדליק את הבורר על כל אחד מהשניים, וה-RPC
מקבל כל אחד מהשניים — והוא `security definer`, ולכן `tcw_contractor_insert`,
שדורשת דווקא את מפתח הפורטל, לא נשאלה. גרוע מכך: `contractors.assign_workers`
הוא המפתח ה*משרדי*, ובענף "היקף זר" שב-RPC הוא פתח לו לשבץ סגל של **כל** קבלן.
ההכרעה מתהפכת בשכבת הקהל, ונאמרת שוב כדחייה מפורשת על התפקיד הצר. מנהל הקבלן
אינו מאבד דבר — הוא משבץ דרך `portal.assign_workers`, שהוא מחזיק בשורת תפקיד
מפורשת (0104 §2), וכך גם העובד שמביא סגל (`staff_contractor`).

**הכובע הקבלני נשאל על העמודה, לא על סוג המשתמש** (0108). זו אותה שאלה שבגללה
נכתב 0075, בשלושה מקומות שנשארו: הדו-כובע — `staff` עם `contractor_id` — **לא
ראה בלו״ז את המשימות שהואצלו לקבלן שלו**, ומכאן שמסך הכספים שלו החזיר אפסים
(‏`contractor_dashboard` הוא `security invoker`: שורת ה-terms נראתה לו, ושורת
ה-`tasks` שמעליה לא). שלוש נגיעות ב-`tasks_select`, וכמותן ב-`events_select`:

- **זרוע הקבלן** מפסיקה לשאול `user_kind() = 'contractor_user'` ושואלת
  `app.contractor_id() is not null`. חשבון `contractor_user` תמיד נושא
  `contractor_id` (‏`profiles_contractor_kind`, 0001), ולכן זו הרחבה לדו-כובע
  בלבד.
- **היקף `own`** מכיר בהאצלה. משימה שהואצלה לקבלן שלי היא "שלי" באותו מובן
  שבו שיבוץ הוא שלי (0081) — וזה מה שחסם אותו בפועל, כי הוא נושא גם תפקיד שטח
  שההיקף שלו `own`.
- **שער הפרסום** (0082) נכתב על עובד שטח. מנהל קבלן רואה את המשימה שהואצלה
  אליו בכל סטטוס, והדו-כובע — שהוא אותו קבלן בדיוק — אינו רואה פחות ממנו.

**קנס גדול מהמחיר הוא חוב, לא הנחה** (0108). ‏`app.recompute_contractor_price`
חתם את התוצאה ב-`greatest(0, …)` (0092), ולכן שני עובדים שלא התייצבו על משימה
בת 300 ש״ח הוצגו כ"אפס" ולא כ-200 ש״ח שהקבלן חייב. הריצפה יורדת בשני הצדדים:
בשרת, ובשורת "סך לתשלום" שבכרטיס ההאצלה — שהחזיקה עותק שני של אותה ריצפה,
ולכן גם הציגה מספר אחר ממה שנכתב ל-`price`. ה-`price_parts` לא השתנה.

**וגם לא מתוך טופס האירוע** (0111). ‏`app.apply_event_task_block` (0017) כותבת
את המחיר מ-`setup_price` / `teardown_price` שבמטען, והיא `security definer` —
כלומר היא **עוקפת** את `tp_write` לגמרי, ושאלה `pricing.edit` לבדה. זו הייתה
הדלת האחורית של האיסור שנקבע יום קודם. מעכשיו היא שואלת את אותה שאלה: צוות
או מנהל מערכת, ולא מי שמחזיק את המפתח. בנוסף היא מכבדת את קונפיגורציית
הטופס — שדה מחיר שהוסתר ללקוח מסוים בכרטיס הלקוח אינו נכתב גם בשביל הצוות,
וזו הדרך שבה מנהל המערכת חוסם עריכת מחיר ללקוח אחד בלי לגעת באחרים. ההערה
שהייתה שם כבר ידעה ששדה מוסתר "עשוי בכל זאת להישלח מטיוטה שנשמרה
ב-localStorage"; מה שנשלח כך פשוט נכתב.

**הלקוח אינו כותב את המחיר שהוא משלם** (0109). ‏`tp_write` (0017) שאלה
`pricing.edit` לבדה — ומפתח הוא דבר שאפשר להעניק בטעות במסך ההרשאות, גם למי
שהוא הצד המשלם. הפוליסה שואלת מעכשיו גם **מי הכותב**: מנהל מערכת או איש צוות
עם המפתח, ולא מי שמחזיק אותו. במקביל `pricing.edit` ו-`pricing.manage_rules`
נסגרים בשכבת הקהל `customer_user`, כדי שכל תפקיד לקוח שייכתב בעתיד ייוולד
סגור — אותו נימוק של 0074 §1. ‏`pricing.view` נשאר פתוח: בלעדיו הלקוח אינו
קורא את התמחור של המשימות שלו, וזה הנתון שההוצאה שלו נבנית ממנו.

**ובטופס האירוע השדה מוצג נעול** (0113). השרת דוחה את הכתיבה מ-0109/0111,
אבל המסך המשיך להזמין את הלקוח להקליד מספר: הוא הזין, שמר, קיבל "נשמר", וחזר
למסך שמראה את המחיר הישן — הבטחה שהמערכת אינה מקיימת. מעכשיו `setup_price` /
`teardown_price` מוצגים לו **גלויים ומנוטרלים**, עם ההערה "נקבע על ידי המשרד",
ואינם נשלחים כלל. הם גם אינם נספרים כשדה חובה חסר, אחרת שדה שסומן חובה
בקונפיגורציה של הלקוח היה נועל אותו על צעד שאין ממנו יציאה.

**ותוספת מחיר היא שורה עם משפט** (0113). אירוע חורג — קומה בלי מעלית, שעתיים
המתנה בשער, משאית שנייה שהוזמנה באמצע היום — נגמר בהפרש בחשבונית שאיש אינו
יודע להסביר, ובשיחת טלפון שמנסה לשחזר מהזיכרון מה קרה שם. ‏`task_price_addons`
נותנת למשימה שורות תוספת: **סכום והערה**, וההערה היא מה שהלקוח קורא בכרטיס
התמחור של האירוע, מתחת למשימה שהתוספת יושבת עליה.

- **שורות ולא עמודה**: אירוע חורג לא נושא חריגה אחת, ותוספת בלי פירוט היא
  בדיוק המספר חסר ההסבר שהיא באה להחליף. **ההערה אינה אופציונלית** — זה
  ‏`CHECK` במסד, ואפס אינו סכום חוקי.
- **לצד `task_pricing.price`, לא בתוכו**: המחיר שם הוא תוצר המחשבון ו-
  ‏`recalculate_task_price` כותב אותו מחדש; תוספת שהתמזגה לתוכו הייתה נמחקת
  בחישוב הראשון, או נועלת את המשימה על `is_manual` בגלל 80 ש״ח של המתנה.
  הסכום שהלקוח רואה הוא הצירוף.
- **סכום שלילי מותר** — "זיכוי על איחור שלנו" היא אותה ישות עם אותו משפט מוצג.
- **הכתיבה על `pricing.edit`, ורק לצוות** — אותה זרוע `user_kind = 'staff'`
  שבפסקה שמעליה, ומאותה סיבה. הקריאה על `pricing.view`, ולכן הלקוח רואה את
  התוספות של המשימות שלו ואילו הקבלן אינו רואה אותן כלל.
- **הסרה רכה, ב-RPC** ‏(`remove_task_price_addon`), מאותה סיבה שב-`remove_event_spec`.
  שתי פוליסות כתיבה נפרדות ולא `for all` אחת: פוליסה מתירנית מסוג `for all`
  חלה גם על SELECT ונוספת ב-OR לפוליסת הקריאה, ולכן היא הייתה מחזירה למסך
  תוספות שכבר הוסרו. הוספה, הסרה ושחזור נרשמים ביומן הפעילות של האירוע.

העריכה יושבת בכרטיס "מחיר ללקוח" שבכרטיס המשימה, מתחת למחיר עצמו: התוספת אינה
דרך אחרת לקבוע אותו אלא מה שנוסף עליו אחרי שנקבע — וזה גם הסדר שבו הלקוח קורא
אותה. הסכמה ב-`0113_customer_spec_and_price_addons.sql`, החבילה ב-
`supabase/tests/25_price_addons.sql`, והמסך ב-`src/features/pricing/PriceAddons.tsx`.

**וקבלן שמשבץ אינו בוחר מאיפה עובדיו מתחילים** (0111). נקודת ההתחלה קובעת את
שעת ההתחלה במשמרת ואת המיקום שמולו נמדדת ההחתמה — כלומר היא מזיזה כסף —
והיא נקבעת פעם אחת על שורת ההאצלה, בידי המשרד. ‏`contractor_assign_worker`
קיבלה `p_work_site` מהקורא ונפלה חזרה לשורת ה-terms רק כשהוא היה `null`, ולכן
הקבלן דרס משם את מה שנקבע לו. מעכשיו: בלי `contractors.assign_workers` הערך
שנשלח נזרק ושורת ההאצלה קובעת — תמיד. הפרמטר נשאר בחתימה כי למשרד יש שימוש
אמיתי בדריסה נקודתית. בהתאם, פאנל השיבוץ של קבלן מצטמצם לרשימת הסגל שלו:
כרטיס "מי משובץ" (שמות הצוות **שלנו**) וכרטיס "נקודת התחלה" יורדים אצלו, ושמו
של קבלן אחר על אותה משימה אינו מוצג לו.

- קבלן **אינו יכול** לשנות מיקום/זמן/לקוח/כמות — משטח הכתיבה היחיד שלו הוא
  `task_contractor_workers` (החלפת עובדים מהסגל שלו בלבד, עד הכמות שהוגדרה),
  והוא עובר ב-`contractor_assign_worker` ולא בכתיבה ישירה.
- שיבוץ מפוצל למפתח פר-תפקיד (עובד / נהג / ראש צוות / משאית), ותמחור קבלנים מופרד
  לצפייה / עריכה / סימון תשלום.
- `users.set_admin` אינו נגזר משום הרשאה אחרת — "עריכת משתמשים" אינה דרך להפוך לאדמין.
- מנהל קבלן אינו מחזיק את המפתחות ה*משרדיים* `contractors.assign_workers` ו-
  `contractors.manage_workers`. הוא החזיק אותם מאז 0011, שם הם נועדו לתאר את
  הסגל של עצמו, ו-`contractor_assign_worker` קיבל אותם כ"היקף זר" — כלומר הם
  פתחו לו לשבץ על משימה של קבלן אחר. `portal.*` נותן לו את שלו, וזה הכול.
- **קוד שגיאה מתאר מחלקה, לא סיבה.** `42501` שמור ל-`app.require` ול-RLS;
  כלל עסקי שנשא אותו הוצג למשתמש כ"אין לך הרשאה" גם כשההרשאה שלו תקינה.
  ‏`errorMessage` מעדיף עכשיו הודעה שנכתבה בגוף ה-RPC על פני התווית של הקוד.
- Audit Log על כל שינוי, Soft Delete עם סל מיחזור, התראות Realtime.
  ליומן הביקורת אין מסך — הוא נקרא דרך ה-API בלבד, מאחורי `settings.audit_log`.
- **ומחיקה לצמיתות שמנקה את דרכה** (0124/0137). ‏`hard_delete` מוציא מהסל את
  מה שכבר נמחק — מנהל מערכת בלבד, ורק פריט שכבר בסל. ‏0124 טיפלה בילד היחיד
  של `events` שאינו `on delete cascade` (‏`tasks`), ו-0137 עושה את אותו הדבר
  לשאר הרשימה הלבנה, שכולה החזירה `23503` גולמי — ההודעה "מקושר לשורות
  אחרות". שלוש קטגוריות: **קישור טהור נמחק** (‏`event_suppliers`, סגל שמשובץ
  למשימה); **הצבעה רכה מתאפסת** — המשאית של משימה, של שיבוץ ושל עובד היא
  תכנון ולא היסטוריה, ומשאית שירדה מהצי משאירה את המשימה במקומה בלי משאית
  (‏`array_remove` על `tasks.truck_ids`, לא NULL); ו**כל השאר נחסם בשמו** —
  לקוח עם אירועים, סוג משימה שמשימות מצביעות עליו, חשבון שיש לו נוכחות.
  ההודעה נוקבת במה חוסם, כי "מקושר לשורות אחרות" אינו אומר למי שקורא אותה מה
  לעשות.

**הוספת הרשאה למודול חדש** — במיגרציה:

```sql
select app.register_module('billing', 'חיוב', 'חשבוניות ותשלומים', 'Wallet', 120);
select app.register_permission('billing.view', 'billing', 'צפייה בחיוב', p_category => 'access');
select app.register_permission('billing.issue_invoice', 'billing', 'הפקת חשבונית',
       p_dangerous => true, p_implied_by => 'billing.view');
select app.register_field('invoice', 'total', 'סכום', 'billing', 'invoices', 'total',
       p_sensitive => true, p_edit_permission_key => 'billing.issue_invoice');
create trigger invoices_field_perms before update on invoices
  for each row execute function app.enforce_field_perms();
select app.rebuild_secure_view('invoices');
```

ובצד הלקוח, המסך החדש מצהיר על המפתח שלו בטבלת הנתיבים:

```tsx
{ path: '/billing', handle: { perm: PERM.BILLING_VIEW }, element: page(<BillingPage />) },
```

נתיב בלי `handle.perm` נדחה ל-`RouteGate` ולא נפתח. זו הכוונה: השאלה "מי רשאי
לפתוח את זה" נשאלת ברגע שמוסיפים נתיב, ולא נזכרים בה אחר כך.

## התראות

שלושה ערוצים: **פעמון** במערכת, **מייל**, ו**התראה למכשיר** (Web Push, בדפדפן
ובאפליקציה המותקנת). `app.notify()` — הנקודה היחידה שכל ההתראות עוברות בה —
כותב את שורת הפעמון ורושם שורת משלוח לכל ערוץ שמותר, ו-`notify-dispatch`
מנקז אותן.

### מי מקבל מה

ההכרעה יושבת כולה ב-`app.notification_enabled(profile, type, channel)`
(‏0046), ולקוח שקורא ל-`my_notification_settings()` מקבל אותה מוכנה. הסולם,
והראשון שנוגע מכריע:

1. נמען לא פעיל או מחוק ⇐ לא
2. הערוץ כבוי במערכת ⇐ לא
3. הסוג ב-`muted_types` של הערוץ ⇐ לא
4. חריג אישי שקבע מנהל (`notification_policy_overrides`)
5. מדיניות הקהל (`notification_policies`)
6. ברירת המחדל בקטלוג (`notification_types`)

המצב שמתקבל הוא אחד מארבעה, ומ-0086 כל אחד מהם מצביע על תשובה אחת: `off`
ו-`opt_in` ⇐ לא נשלח, `opt_out` ו-`forced` ⇐ נשלח. שני הזוגות נשארים כי הם
ברירות המחדל שבקטלוג ומה ששמור כבר בטבלת המדיניות.

**אין למשתמש דעה.** עד 0086 ישבה בתחתית הסולם שכבה חמישית — ההעדפה האישית
ב-`notification_preferences` — וכל עובד יכול היה לכבות לעצמו "שובצתי למשימה".
היא ירדה: שורה שנכתבה פעם אחת המשיכה להכריע לנצח, המנהל ראה במטריצה "דלוק
כברירת מחדל" והעובד לא קיבל, ושניהם צדקו. הטבלה נשארת (השורות הן תיעוד של מה
שאנשים ביקשו בעבר) ואינה נקראת עוד; `set_notification_preference` מחזירה 42501,
וה-RLS שלה נסגר למי שמנהל התראות. מה שנשאר בידי המשתמש הוא רישום *המכשיר*
ל-push — הרשאת דפדפן, לא העדפה.

הקהלים הם `admin`, `staff`, `contractor_user`, `customer_user`. שימו לב
ש-`admin` אינו `user_kind` אלא `profiles.is_admin`, והוא גובר — אחרת כל שינוי
שנועד לעובדים היה חל גם על המנהלים.

**המנהל קובע הכול** ב-`/settings` ← לשונית "התראות", מאחורי המפתח
`notifications.manage` (נגזר מ-`settings.edit`): שם נדלקים הערוצים, שם נקבעת
המדיניות לכל קהל, ושם נקבעים החריגים לאדם בודד. **המשתמש** רואה
ב-`/my/notifications` מה יגיע אליו, לקריאה בלבד — ולכן `notifications.preferences`
הוא מפתח של צפייה.

סוג התראה חדש נרשם ב-`app.register_notification_type(...)` ומופיע משם בשני
המסכים. אין רשימה מקבילה ב-TSX, ובדיקה ב-`07_notifications.sql` נכשלת אם טריגר
פולט סוג שלא נרשם.

### מה נשלח, ומתי (0110)

כל שכבת הפולטים נכתבה מחדש ב-0110. החוקים:

**מסלול הלקוח → מנהלי המערכת:** לקוח שפתח אירוע (`event_created`), ערך אירוע
(`event_updated`), העביר אירוע ל"בוטל" (`event_cancelled`) או העלה מפרט
(`spec_uploaded`). פעולה זהה של המשרד שקטה — אירוע שהמשרד ערך אינו חדשות
למשרד. בכיוון ההפוך: לחיצת "אישור לביצוע" (`set_event_approved`, ‏0109) שולחת
`event_approved` למשתמשי הלקוח — רק במעבר מלא-מאושר למאושר.

‏`event_updated` נפלט מ-0112 מסוף `update_event` ולא מטריגר שורה: כך גם עריכה
שנוגעת רק בלוויינים — איש קשר, ספקים, בלוקי הקמה/פירוק — מדברת. ההתראה יוצאת
רק כששמירה שינתה משהו בפועל: יומן הפעילות, שכל כותביו סינכרוניים באותה
טרנזקציה, הוא גלאי השינוי — שמירה שלא כתבה שורת יומן שקטה. עריכת הכנסות-בלבד
אינה מתריעה (ההכנסות אינן ביומן, בהחלטה), וביטול נשאר בלעדי ל-`event_cancelled`.

**ומעבר בין זרועות הביצוע** (`task_performed_by_changed`, ‏0136): משימה שעברה
מוייפר לארקו או בחזרה, למנהלי המערכת בלבד ובשני הכיוונים. לעובד זו אינה
חדשות — הוא ממילא מקבל `assignment_removed` כשהשיבוץ שלו יורד (0135) — ולמי
שאחראי על שתי הזרועות זו בהחלט חדשות: המעבר מזיז עבודה, ראייה וכסף בבת אחת.
הכיוון כתוב בכותרת, כי "השתנה" בלי כיוון מחייב לפתוח את המשימה כדי לדעת מה קרה.

**מחזור הפרסום של משימה:** מעבר לסטטוס "משובץ" שולח `task_published` לכל הקהל —
הסגל המשובץ, מנהלי כל קבלן שהמשימה הואצלה לו, ועובדי קבלן משובצים שמקושרים
לאפליקציה; ירידה מהסטטוס שולחת `task_unpublished` לאותו קהל. הקהל מחושב
ב-`app.task_audience()` — שורה אחת לאדם גם כשהוא חובש שני כובעים. שיבוץ פרטני
*אחרי* הפרסום מודיע לנוסף עצמו (`task_assigned` / `assignment_removed`,
ולקבלן שהואצל — `task_published`); לפני הפרסום הכול שקט (הכלל מ-0063/0064).
כשקבלן משבץ עובד משלו, המנהלים מקבלים `contractor_worker_assigned` והעובד
מקבל `task_assigned`.

**שינוי זמנים במשימה משובצת** (`task_time_changed`): תאריך, שעת התחלה במחסן או
שעת התחלה בשטח. כשרק שעת *המחסן* השתנתה, שומעים רק מי שמסומנים למחסן
(`work_site='warehouse'` על השיבוץ). שינוי `contractor_worker_count` בשורת
ההאצלה שולח `contractor_worker_count_changed` למנהלי אותו קבלן.

**השעון** (`attendance_clock_in` / `attendance_clock_out`): כל כניסה ויציאה
מגיעה למנהלי המערכת — על כולם, כולל עובדי קבלן — ולמנהלי הקבלן על העובדים
שלהם. כניסה אחרי תחילת המשמרת המתוכננת מסומנת בכותרת "ביצע כניסה באיחור";
לעובד סגל אין דקות חסד, ולעובד קבלן נספרות `contractors.lateness_grace_minutes`
(‏0092) — אותו סף שמזין את קנסות האיחור. ערוץ המייל לשני הסוגים האלה כבוי
בברירת מחדל (`opt_in`) — זה הסוג הרועש במערכת, והפעמון והפוש הם הערוצים
הנכונים לו.

דיווח הנוכחות הידני (`attendance_submitted` / `attendance_approved` /
`attendance_rejected`) ותוקף מסמכי הרכב (`vehicle_document_*`) נשארו כפי שהיו.
שלושה סוגים פרשו — `task_changed`, `event_status_changed`, `contractor_task` —
והם נשארים בקטלוג ככבויים, כי שורות היסטוריות עדיין מצביעות עליהם.

"מנהלי קבלן" בכל האמור לעיל הם `app.contractor_managers()`: מי שמקושר לקבלן
ומחזיק `portal.view` — המפתח שכל `contractor_user` יורש כברירת מחדל ותפקיד
`contractor_worker` דוחה במפורש.

### תחולה

בנוסף למטריצה, המנהל קובע **על מי** כל סוג חל: לקוחות, קבלנים או עובדים
(`notification_scope_modes` + `notification_scopes`, לשונית ההתראות ← "תחולה").
ברירת המחדל היא "כולם" — הטבלאות דלילות ושורה קיימת רק כשמנהל צמצם; "נבחרים"
בלי אף בחירה משתיק את הסוג לגמרי.

ההבדל מהשתקה (`muted_types`) מהותי: התחולה נבחנת בפולט עצמו
(`app.notification_in_scope`), על *הנושא* של ההתראה — הלקוח שהאירוע שלו,
העובד או הקבלן שהפעולה נוגעת בהם — ונושא שמחוץ לתחולה אינו יוצר שורה בכלל.
"לא רלוונטי" אינו "מושתק ביומן".

### מייל

**הערוץ כבוי בברירת מחדל.** שדרוג לא אמור להתחיל לשלוח מיילים מעצמו. להפעלה:

```sql
update app_settings
   set value = jsonb_set(value, '{enabled}', 'true'::jsonb)
 where key = 'notifications.email';
```

באותו מפתח יושבים גם `from` (כתובת השולח) ו-`muted_types` — סוגים שלא יישלחו
במייל גם כשהערוץ דלוק, ולא משנה מה המשתמש ביקש.

### התראה למכשיר (Web Push)

**גם הוא כבוי בברירת מחדל, ובשני מקומות בלתי תלויים:** מפתח ההגדרות, וברירת
המחדל בקטלוג שהיא `opt_in`. שלושה שלבים להפעלה, פעם אחת:

```sh
# 1. זוג מפתחות VAPID
deno run -A jsr:@negrel/webpush/cmd/generate-vapid-keys > vapid.json

# 2. הסודות לפונקציה. המפתח הפרטי אינו עולה למסד לעולם.
supabase secrets set VAPID_KEYS="$(cat vapid.json)" \
                     VAPID_SUBJECT="mailto:ops@yourdomain.com"
```

```sql
-- 3. המפתח הציבורי והדלקת הערוץ. אפשר גם מהמסך, בלשונית ההתראות.
update app_settings
   set value = jsonb_build_object(
         'enabled', true,
         'vapid_public_key', '<המפתח הציבורי מתוך vapid.json>',
         'muted_types', '[]'::jsonb)
 where key = 'notifications.push';
```

המפתח **הציבורי** יושב ב-`app_settings` כי הדפדפן זקוק לו כדי להירשם, והוא
פומבי מעצם הגדרתו. המפתח **הפרטי** אינו שם ולא יהיה שם: `app_settings` פתוחה
לקריאה לכל משתמש מאומת דרך PostgREST (‏0005), ולכן כל סוד שיושב בה גלוי לכל
עובד וכל לקוח.

שלוש נקודות תפעוליות:

- **החלפת זוג המפתחות מבטלת כל מנוי קיים.** אחרי רוטציה יש להריץ
  `truncate push_subscriptions` ולבקש מכולם להפעיל מחדש מהמסך.
- **‏iOS:** ‏Web Push עובד מ-16.4, ורק כשהאפליקציה מותקנת במסך הבית. המסך
  מזהה את המצב ומסביר מה לעשות במקום להציג כפתור שאינו עושה דבר.
- **חובה HTTPS** (‏`localhost` נחשב מאובטח).

מנוי שמת (‏410/404 משירות הדחיפה) נמחק אוטומטית על ידי `notify-dispatch`, ושורות
המשלוח שלו נופלות איתו בקסקייד.

### התפעול המשותף

**משתני סביבה ל-`notify-dispatch`:** `NOTIFY_DISPATCH_SECRET` (בלעדיו הפונקציה
מסרבת ולא רצה פתוחה), `RESEND_API_KEY` למייל, ו-`VAPID_KEYS`/`VAPID_SUBJECT`
ל-push. בלי מפתח הספק המשלוח מסומן `skipped` ולא נצבר כניסיונות כושלים.

**שתי הגדרות מסד** שנקבעות פעם אחת. הן אינן ב-`app_settings` במכוון: היא קריאה
לכל משתמש מאומת דרך PostgREST, וסוד לא אמור לשבת שם.

```sql
alter database postgres set app.notify_dispatch_url =
  'https://<ref>.supabase.co/functions/v1/notify-dispatch';
alter database postgres set app.notify_dispatch_secret = '<אקראי>';
```

הניקוז נעשה בשתי דרכים, ובכוונה לא רק באחת: `pg_net` יורה מהטריגר ברגע שנרשם
משלוח, וקריאה חיצונית מתוזמנת (POST בלי גוף, עם אותו `x-dispatch-secret`)
מנקזת את כל מה שממתין — כולל מה שנכשל, עד חמישה ניסיונות. בלי השנייה תקלה
רגעית אצל ספק הדואר הייתה אובדת. אין `pg_net`? הטריגר שותק וה-outbox ממתין
לניקוז החיצוני.

הטריגר הוא `for each statement` ולא `for each row`: התראה אחת שיוצאת למייל
ולארבעה מכשירים היא חמש שורות משלוח, וברמת השורה היא הייתה יורה חמש קריאות
HTTP שכולן מנקזות ממילא את אותו תור.

**סריקת תוקף מסמכי הרכב** היא הזרוע המתוזמנת היחידה במערכת שאין לה טריגר: אין
אירוע שורה שאומר "עבר יום". `supabase secrets set FLEET_SWEEP_SECRET='<אקראי>'`,
ואז תזמון יומי של `POST` בלי גוף אל
`https://<ref>.supabase.co/functions/v1/fleet-expiry-sweep` עם הכותרת
`x-sweep-secret`. בלי הסוד הפונקציה מסרבת ואינה רצה פתוחה, כמו `notify-dispatch`.
הקריאה בטוחה לחזור על עצמה — ה-RPC רושם כל התראה שכבר יצאה ונועל נעילה מייעצת
— ולכן גם הרצה כפולה או ידנית אינה שולחת דבר פעמיים. **עד שהתזמון מוגדר,
ההתראות יוצאות רק בלחיצה על "בדיקת תוקף" במסך הרכבים;** המסך והדשבורד מחשבים
את התוקף בקריאה ואינם תלויים בסוויפ.

## הערות תפעול

- ליצירת משתמשים עם סיסמה משתמשים ב-Edge Function ‏`admin-users` (service role בצד השרת בלבד).
- **חיפוש כתובות ב-Google Places** — הפרוקסי `geocode-proxy` משתמש ב-Google
  Places (Text Search) כשהסוד `GOOGLE_MAPS_API_KEY` מוגדר. הפעלה:
  1. ב-Google Cloud Console: פרויקט עם חיוב (billing) פעיל.
  2. הפעלת **Places API (New)** — לא ה-Places API הישן.
  3. יצירת API key, ותחת API restrictions הגבלתו ל-Places API (New) בלבד.
     אין הגבלת referrer — הקריאה מצד השרת והמפתח לעולם לא מגיע לדפדפן.
  4. Supabase Dashboard → Edge Functions → Secrets → הוספת
     `GOOGLE_MAPS_API_KEY` (או `supabase secrets set GOOGLE_MAPS_API_KEY='<key>'`).
     נכנס לתוקף אוטומטית, בלי פריסה מחדש.

  **בלי הסוד הפונקציה ממשיכה עם Photon/Nominatim (OSM) כרגיל** — פריסה בטוחה,
  ומחיקת הסוד היא מתג כיבוי שמחזיר ל-OSM ללא שינוי קוד. הגנות עלות שכבר
  קיימות: debounce של 300ms בהקלדה, מינימום 3 תווים, cache של 24 שעות בצד
  השרת ו-pageSize 10; מומלץ בנוסף להגדיר התראת תקציב (Budget Alert) ב-GCP.
- Nominatim (נתיב הנסיגה) מוגבל לבקשה בשנייה — הפרוקסי דורש משתמש מחובר,
  מחזיק cache חסום ומווסת את עצמו לקצב הזה. חריגה הייתה חוסמת את כתובת ה-IP
  של האפליקציה כולה ולא רק את מי שגרם לה.
- מומלץ להפעיל Leaked Password Protection בהגדרות ה-Auth בדשבורד של Supabase.
